## 三、核实结论

逐条对照当前代码 + `.224` 真机验证，不直接采信扫描器评级。

### ✅ AUTH-VULN-01　CSRF 绕过（报告 High，成立，**已实测**）

`backend/auth_gateway.py:1007-1017`

```python
def _origin_host_mismatch(url: str) -> bool:
    u = urlparse(url)
    if not u.netloc:
        return False                      # ← 洞 1
    host = u.netloc.split(":")[0]         # ← 洞 2
    return host != request.host.split(":")[0]
```

**实测矩阵**（`POST /auth/login` + 正确密码；403 = 被 CSRF 拦下，200 = 绕过；
用正确密码保证两种情况都不增加失败计数）：

| `Origin` 头 | HTTP | 含义 |
|---|---|---|
| （不传） | 200 | 无来源，走放行分支 |
| `https://evil.example.com` | **403** | 对照组：标准跨站被正确拦下 |
| `https://attack.test` | **403** | 对照组：同上 |
| `192.168.100.224`（无 scheme） | **200** | ✅ **绕过** —— `netloc=""` → `return False` |
| `https://192.168.100.224:x@evil.example.com` | **200** | ✅ **绕过** —— `split(":")[0]` 取到 host |
| `https://192.168.100.224@evil.example.com`（无冒号） | 403 | 正确拦截，`netloc` 整体不等于 host |

两个洞都成立，且行为与代码分析逐条对上。

**影响边界**：SameSite=Lax 已经挡住了携带 cookie 的跨站登录，所以这条**不能**用来盗取
会话；实际可利用的是**登录锁定 DoS** —— 诱导受害者浏览器发 5 次错误密码即可锁其 IP 15 分钟。

**修法**：比较 `u.hostname`（它会正确解析 userinfo），且 `not u.netloc` 时**判为跨站**
而非放行；同时要求 scheme 存在。

### ✅ AUTH-VULN-01　CSRF 绕过（报告 High，成立）

`backend/auth_gateway.py:1007-1017`

```python
def _origin_host_mismatch(url: str) -> bool:
    u = urlparse(url)
    if not u.netloc:
        return False                      # ← 洞 1
    host = u.netloc.split(":")[0]         # ← 洞 2

```

**洞 1 —— 无 scheme 的 Origin 直接放行**
`Origin: 192.168.100.224`（浏览器不会产生，但脚本/扩展可以）→ `urlparse` 得到
`netloc=""` → 走 `return False` → 判定「无跨站」→ CSRF 检查通过。

**洞 2 —— userinfo 冒号冒充**
`Origin: https://192.168.100.224:x@evil/` → `netloc="192.168.100.224:x@evil"` →
`split(":")[0]` = `"192.168.100.224"` → 与 `request.host` 相同 → 放行。

**影响边界**：SameSite=Lax 已经挡住了携带 cookie 的跨站登录，所以这条**不能**用来盗取
会话；实际可利用的是**登录锁定 DoS** —— 诱导受害者浏览器发 5 次错误密码即可锁其 IP 15 分钟。

**修法**：比较 `u.hostname`（它会正确解析 userinfo），且 `not u.netloc` 时**判为跨站**
而非放行；同时要求 scheme 存在。

### ✅ AUTH-VULN-04　请求体无上限 —— 报告的机制说错了，实际更严重

**报告的说法**：CPU DoS，PBKDF2 闸门饥饿。

**实测纠正**：先按报告思路推断「单个 100MB body 就能写满磁盘」，**被实测推翻**：

1. `POST /auth/login` 60MB → HTTP 401（0.7s），`df` 全程 11341KB 不变
2. nginx 错误日志给出真相：
   `a client request body is buffered to a temporary file /var/lib/nginx/body/0000000001`
3. `df -k /var/lib/nginx/body` → **`tmpfs` 502320 498500 1% /tmp**
   OpenWrt 的 `/var` 是指向 `/tmp` 的软链，`/tmp` 是内存盘 —— 写的是 **RAM**，不是那块
   只剩 11MB 的 overlay
4. 6 并发 × 100MB → **4×502 + 2×500**，6 个请求全失败
5. `dmesg`：
   ```
   Out of memory: Killed process 13071 (python3)
     total-vm:565552kB  anon-rss:461600kB
   ```
   `request.get_json()` 把 100MB body 物化 + 中间副本 → RSS 涨到 **461MB** → 内核 OOM

**根因**：`/auth/login`、`/auth/logout`、`/auth/status`、`/auth/portal`、`/auth/static/`
这 5 个 location **都没有 `client_max_body_size`**，落到 nginx 全局默认 **128M**
（`/etc/nginx/uci.conf:25`）。而登录请求体实际只需要 `{"password":"..."}` 几百字节。

**真实影响**：
- **未认证**即可触发 —— 6 条 `curl` 就够
- 网关进程被 OOM kill 后**没有任何机制把它拉起来**，`/auth/*` 全部 502
- 面板（5443）不受影响，但公网入口等于全断，只能人工恢复

## 三、报告没提、但实测挖出的两个问题

### 🔴 init 脚本 `sleep 1` 竞态（本次恢复服务时发现）

`/etc/init.d/nftables-web-auth` 的降权守卫：

```sh
python3 auth_gateway.py >>"$AUTH_LOG" 2>&1 &
echo $! > "$PID_FILE"
sleep 1
real_uid=$(awk '/^Uid:/ {print $2}' "/proc/$(cat "$PID_FILE")/status")
if [ "$real_uid" = "0" ]; then
    echo "降权未生效 —— 停掉它" >&2
    kill "$(cat "$PID_FILE")"; rm -f "$PID_FILE"; return 1
fi
```

它假设 Python 在 1 秒内能执行到模块级的 `_drop_privileges()`（`auth_gateway.py:1173`）。

**实测「进程启动 → 降权完成」耗时**（`.224`，每组 3–4 次）：

| 机器状态 | 降权耗时 | 距 1s 阈值 |
|---|---|---|
| 空闲 | 0.372 – 0.390s | 余量 0.61s |
| 4 进程满载 | 0.790 – 0.857s | **余量仅 0.14s** |
| 8 进程满载 | 1.443 – 1.636s | **超出阈值 44%–64%** |

机制成立：机器一忙，健康的进程就被守卫当成「降权失败」杀掉。

**实测观察到的故障现场**：刚 OOM 完、tmpfs 还在回写时执行 `restart`，报
「进程起来了但 uid 仍是 0，降权未生效 —— 停掉它」，网关彻底起不来；
**同一条命令在机器空闲时完全正常**（`Started nftables-web-auth (PID 22851, uid 1000)`）。

这个守卫本意是防降权失败，现在自己在制造故障，且失败后果是网关永久下线。
**修法**：改成轮询等待（最多 ~10s），进程退出或 uid 变为非 0 才收敛。

### 🟡 审计日志在 tmpfs，重启即丢

`/var/log/nftables-web-auth.log` 落在内存盘。配合无上限，意味着
「一次运行期间无限增长」+「重启后完全消失」，两头都不理想。
