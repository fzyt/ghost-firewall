## 三、核实结论

逐条对照当前代码 + `.224` 真机验证，不直接采信扫描器评级。

### ✅ AUTH-VULN-01　CSRF 绕过（报告 High，成立，**已实测**）

`backend/auth_gateway.py:1007-1017`

```python
def _origin_host_mismatch(url: str) -> bool:
    u = urlparse(url)
    if not u.netloc:
        return False                      # ← 洞 1
    host = u.netloc.split(":")[0]         # ← 洞 2
    return host != request.host.split(":")[0]
```

**实测矩阵**（`POST /auth/login` + 正确密码；403 = 被 CSRF 拦下，200 = 绕过；
用正确密码保证两种情况都不增加失败计数）：

| `Origin` 头 | HTTP | 含义 |
|---|---|---|
| （不传） | 200 | 无来源，走放行分支 |
| `https://evil.example.com` | **403** | 对照组：标准跨站被正确拦下 |
| `https://attack.test` | **403** | 对照组：同上 |
| `192.168.100.224`（无 scheme） | **200** | ✅ **绕过** —— `netloc=""` → `return False` |
| `https://192.168.100.224:x@evil.example.com` | **200** | ✅ **绕过** —— `split(":")[0]` 取到 host |
| `https://192.168.100.224@evil.example.com`（无冒号） | 403 | 正确拦截，`netloc` 整体不等于 host |

两个洞都成立，且行为与代码分析逐条对上。

**影响边界**：SameSite=Lax 已经挡住了携带 cookie 的跨站登录，所以这条**不能**用来盗取
会话；实际可利用的是**登录锁定 DoS** —— 诱导受害者浏览器发 5 次错误密码即可锁其 IP 15 分钟。

**修法**：比较 `u.hostname`（它会正确解析 userinfo），且 `not u.netloc` 时**判为跨站**
而非放行；同时要求 scheme 存在。

### ✅ AUTH-VULN-01　CSRF 绕过（报告 High，成立）


### ✅ AUTH-VULN-04　请求体无上限 —— 报告的机制说错了，实际更严重

**报告的说法**：CPU DoS，PBKDF2 闸门饥饿。

**实测纠正**：先按报告思路推断「单个 100MB body 就能写满磁盘」，**被实测推翻**：

1. `POST /auth/login` 60MB → HTTP 401（0.7s），`df` 全程 11341KB 不变
2. nginx 错误日志给出真相：
   `a client request body is buffered to a temporary file /var/lib/nginx/body/0000000001`
3. `df -k /var/lib/nginx/body` → **`tmpfs` 502320 498500 1% /tmp**
   OpenWrt 的 `/var` 是指向 `/tmp` 的软链，`/tmp` 是内存盘 —— 写的是 **RAM**，不是那块
   只剩 11MB 的 overlay
4. 6 并发 × 100MB → **4×502 + 2×500**，6 个请求全失败
5. `dmesg`：
   ```
   Out of memory: Killed process 13071 (python3)
     total-vm:565552kB  anon-rss:461600kB
   ```
   `request.get_json()` 把 100MB body 物化 + 中间副本 → RSS 涨到 **461MB** → 内核 OOM

**根因**：`/auth/login`、`/auth/logout`、`/auth/status`、`/auth/portal`、`/auth/static/`
这 5 个 location **都没有 `client_max_body_size`**，落到 nginx 全局默认 **128M**
（`/etc/nginx/uci.conf:25`）。而登录请求体实际只需要 `{"password":"..."}` 几百字节。

**真实影响**：
- **未认证**即可触发 —— 6 条 `curl` 就够
- 网关进程被 OOM kill 后**没有任何机制把它拉起来**，`/auth/*` 全部 502
- 面板（5443）不受影响，但公网入口等于全断，只能人工恢复

## 四、报告没提、但实测挖出的两个问题

### 🔴 init 脚本 `sleep 1` 竞态（本次恢复服务时发现）

`/etc/init.d/nftables-web-auth` 的降权守卫：

```sh
python3 auth_gateway.py >>"$AUTH_LOG" 2>&1 &
echo $! > "$PID_FILE"
sleep 1
real_uid=$(awk '/^Uid:/ {print $2}' "/proc/$(cat "$PID_FILE")/status")
if [ "$real_uid" = "0" ]; then
    echo "降权未生效 —— 停掉它" >&2
    kill "$(cat "$PID_FILE")"; rm -f "$PID_FILE"; return 1
fi
```

它假设 Python 在 1 秒内能执行到模块级的 `_drop_privileges()`（`auth_gateway.py:1173`）。

**实测「进程启动 → 降权完成」耗时**（`.224`，每组 3–4 次）：

| 机器状态 | 降权耗时 | 距 1s 阈值 |
|---|---|---|
| 空闲 | 0.372 – 0.390s | 余量 0.61s |
| 4 进程满载 | 0.790 – 0.857s | **余量仅 0.14s** |
| 8 进程满载 | 1.443 – 1.636s | **超出阈值 44%–64%** |

机制成立：机器一忙，健康的进程就被守卫当成「降权失败」杀掉。

**实测观察到的故障现场**：刚 OOM 完、tmpfs 还在回写时执行 `restart`，报
「进程起来了但 uid 仍是 0，降权未生效 —— 停掉它」，网关彻底起不来；
**同一条命令在机器空闲时完全正常**（`Started nftables-web-auth (PID 22851, uid 1000)`）。

这个守卫本意是防降权失败，现在自己在制造故障，且失败后果是网关永久下线。
**修法**：改成轮询等待（最多 ~10s），进程退出或 uid 变为非 0 才收敛。

### 🟡 审计日志在 tmpfs，重启即丢

`/var/log/nftables-web-auth.log` 落在内存盘。配合无上限，意味着
「一次运行期间无限增长」+「重启后完全消失」，两头都不理想。

## 七、第二批：会话生命周期三项 + 一项加固（2026-10-16 已实施）

第一批（第四节）修完之后剩下的可修项，这批一并做掉。

### MISC-02　吊销表读失败时已吊销令牌复活（唯一的 fail-open）

`auth_gateway.py` 原实现：

```python
except (OSError, json.JSONDecodeError):
    return {}          # 空表 → is_revoked 对所有 jti 返回 False
```

吊销文件一次写坏（写一半、磁盘满、权限丢），**所有显式登出吊销掉的令牌全部复活**，
而且是静默的。这与项目里「限流表损坏 fail-open、恢复链 fail-closed」的取舍相反：
限流表坏了顶多多试几次，吊销表坏了是已失效的凭据重新可用。

修复分两级：
1. 进程内维护 **last-known-good** 副本，每次成功读都更新；读失败时退回它
2. 连 LKG 都没有（进程刚起、文件就是坏的）→ `load_revoked()` 返回 `None`
   表示「判不出来」，`is_revoked()` 据此 **fail-closed 判为已吊销**

### MISC-01　改密码不吊销任何会话

原来的 `auth_change_password` 只做了 `session.clear()` —— 那只清**当前浏览器自己**
的面板会话。所有设备上的面板 session、以及所有 `gw_token` JWT 都照样有效；
滑动续期意味着只要一直用，它们可能永不过期。

核实过程中还发现报告没提的一点：**面板自身的会话也一样没和密码绑定**
（`session['authenticated'] = True`，无任何密码派生信息）。同一个洞。

修复：引入**令牌世代号** `auth_token_epoch`（存在共享配置里）。

| | 绑定方 | 行为 |
|---|---|---|
| 改密码时 | `auth_change_password` | 先 `epoch += 1` 落盘，**再**写密码 |
| 网关 JWT | `issue_token` 写入 `ep` 字段 | `_verify_or_deny` 比对 `ep` 与配置，不符即拒 |
| 面板 session | 登录时盖 `session['auth_epoch']` | `before_request` 与 `/api/auth/status` 都比对 |

**顺序不能反**：先 epoch 后密码 → 密码写入失败时代价只是大家被登出（安全、可重登）；
反过来则密码已变但旧会话全活着，用户以为改成功了 —— 方向完全错了。

无 `ep` 字段的旧令牌按 `0` 处理，所以第一次改密码（0→1）就能把存量令牌一次性清掉，
不需要额外的兼容期。配置读不到时回落 0，不叠加第二层拒绝（配置读取失败本来就有
独立的降级处理，再叠一层只会变成一次瞬时读失败把所有人踢下线）。

### AUTH-01　dummy PBKDF2 从未被调用到

`_verify_password` **内部本来就有** dummy 路径（stored 为空/畸形时照样真跑一次
PBKDF2，注释里明说是为了堵时序枚举）。但调用点是：

```python
ok = bool(password) and bool(stored) and _verify_password(password, stored)
#                              ^^^^^^^^^^^^^^ 短路时函数一次都不跑
```

实测 **0.001ms vs 95ms**，差 5 个数量级 —— 一个「这台机器配没配密码」的状态枚举口。

修复：先算再判，短路只留在最后的布尔表达式里：

```python
_ok = _verify_password(password, stored)
ok = bool(password) and bool(stored) and _ok
```

### P3　HSTS 与 Cache-Control 覆盖面

此前只有静态资源、门户页、登录页三处**逐个手写**了响应头，
`/auth/status`、`/auth/login`(POST)、`/auth/logout`、`/auth/portal`
这些同样带会话信息的端点一个都没有。新增 `@app.after_request` 用 `setdefault` 兜底
（已显式设过的保持原值，不覆盖静态资源的 `no-cache` 和 HTML 页的 CSP）：

`Cache-Control: no-store` / `Pragma: no-cache` / `X-Content-Type-Options: nosniff` /
`X-Frame-Options: DENY` / `Referrer-Policy: no-referrer` /
`Strict-Transport-Security: max-age=31536000`（仅 HTTPS 语境，**不带**
`includeSubDomains` —— 网关可能与路由器上其它服务共用域名，把子域钉死会误伤）。

### ⚠️ 实施过程中挖出的两个额外 bug（报告与第一份核实报告都没有）

这两条都不是 Shannon 报的，是把上面的修复拿到 `.224` 真机验证时撞出来的。

#### 1. 面板改一次密码，网关就再也登不上（既有 bug，来自 `5aa8ed6` / 9-13）

`init` 脚本的 `prepare_nftweb_files` 特意把共享机密文件设成
`chgrp nftweb` + `640`，注释写得很清楚：

> 640 对「其他」仍然完全关闭，暴露面和原来的 600 等价，**但网关读得到**。

而 `auth_gateway` 是降权后以 **uid 1000** 运行的。

但 `app.py` 里 `_write_password_hash()` 和 `_init_app_secret()` 写完都是
`os.chmod(path, 0o600)` —— **把组读权限抹掉了**。于是：

```
面板上改一次密码
  → /etc/nftables/nftables-web-password 变成 -rw------- root nftweb
  → 网关 uid 1000 读不到密码文件
  → 网关登录一律 401 AUTH_FAILED（面板本身正常，因为它跑在 root）
  → 改回去也没用，必须手工 chgrp + chmod 才能恢复
```

`.224` 实测闭环：权限 600 时网关登录 401，`chgrp nftweb && chmod 640` 后立刻 200。

修复：抽 `_apply_shared_secret_perms()`，`chgrp nftweb` + `chmod 640`，
与 init 脚本对齐；组不存在时退回 600（不比原来更开放）。

#### 2. `logout` 只认 cookie，`verify` 却认 Bearer —— 脚本客户端永远登不掉

```python
# auth_logout：只读 cookie

# _verify_or_deny：Bearer 优先（给脚本/客户端用）
raw = request.cookies.get(COOKIE_TOKEN, "")
authz = (request.headers.get("Authorization") or "").strip()
if not raw and authz.lower().startswith("bearer "):
    raw = authz[7:].strip()
```

两处**不对称**：用 `Authorization: Bearer` 的客户端在 `verify` 处完全正常，
调 `logout` 也拿到 HTTP 200 看着像成功了，但 `payload` 是空 → `revoke_jti`
根本没被调用 → 令牌照样有效到过期，滑动续期下可能永不过期。

修复：抽出 `_extract_token()`，两个入口共用。顺带加了一条断言检查
`logout` 返回的是 JSON 而不是裸字符串 —— 这正是我在实现过程中**自己犯过
的错**（新函数被插到了 `@app.route` 和 `def auth_logout` 之间，导致装饰器
挂到了 `_extract_token` 上，logout 路由变成返回一个字符串，200 但什么都不做）。

#### 3. 我自己实现里的漏洞：删掉吊销表等于复活所有已吊销令牌

这条是**把上面的 MISC-02 修复拿上线后被真机实测抓到的**，不是 Shannon 报的。

最初的实现里，`load_revoked()` 对 `FileNotFoundError` 一律 `return {}` 并把
last-known-good 也清空 —— 理由是「文件不存在 = 从未吊销过」。但这句话只在
**进程启动至今一次都没成功读到过**时成立。

`FileNotFoundError` 实际有两种含义完全不同的场景：

| 场景 | 含义 | 应有行为 |
|---|---|---|
| 进程全新启动，文件从来就不存在 | 确实从未吊销过 | 返回空表，正常放行 |
| 刚才还读得好好的，现在没了 | 故障（被删/被清/挂载掉了） | 退回 last-known-good |

混为一谈的后果：只要有人 `unlink` 掉吊销表，**所有已吊销的令牌立刻复活**。

`.224` 实测复现（修复后第一次跑线上脚本就撞上）：

```
3) 登出后 verify:      401   ← 修复生效
4) 吊销表写坏后:       401   ✅ LKG 兜住了
5) 吊销表整个删掉后:   200   ❌ 令牌复活了
```

修复：判据改成「本进程有没有成功读到过」—— 读到过就说明文件本来该在，
现在没了是故障，走 LKG；一次都没读到过才是正常初始状态。

**这条的意义**：单元测试当时覆盖了「文件损坏」和「文件不存在」两种形态，
但没有覆盖「**先存在、后消失**」这个时间序列。故障注入的维度不止空间维度，
还有时间维度。

## 八、第三批：`revoke_jti` 的落盘结果必须被如实汇报（2026-10-16 已实施）

### 起因：`.224` 上 logout 整条 500

第二批真机验证时 Bearer logout 返回 200 但令牌没失效。顺藤摸下去发现根因：
`revoke_jti` 结尾是一句裸的 `os.chmod(path, 0o600)`，而吊销表的属主在一次
验证脚本误操作后变成了 root —— chmod 抛 `PermissionError`，**把已经 fsync
落盘、吊销早已成立的那次 logout 打成 500**。

客户端看到的是「服务端出错」，完全不知道自己那张令牌还能用多久。更糟的是
`revoke_jti` 不止被 logout 调用：登录时的旧令牌吊销、滑动续期时的旧令牌吊销
都走它，抛异常会让这两条链路整条断掉。

### 三处修改

1. **建文件就收紧**：`open(path, "a+")` 换成 `os.open(..., O_RDWR|O_CREAT, 0o600)`。
   旧写法先按 umask 建出 0644 再 chmod，中间有一个**世界可读窗口**。
   注意事后 `stat` 抓不到这个差异 —— 两种写法最终态都是 0600，
   要测只能拦截 `os.open` 看建文件那一刻传进去的 mode。
2. **权限收紧失败 ≠ 吊销失败**：数据已 fsync、吊销已成立时，chmod 失败只记审计
   （`revocation_chmod_failed`），不再整条失败。
3. **返回「是否真落盘」**：`revoke_jti` 改返回 `bool`，三个调用点分别处置：

| 调用点 | 吊销失败时 | 理由 |
|---|---|---|
| `auth_logout` | 500 + `REVOCATION_FAILED`，**仍然清 cookie** | 令牌确实还活着，报 200 就是撒谎；但本机凭据要立刻撤干净 |
| `auth_login` | 放行 + 审计 `login_old_token_not_revoked` | 一张写坏的吊销表若能拦住登录 = 所有人被锁在门外 |
| 滑动续期 | 放行 + 审计 `refresh_old_token_not_revoked` | 这里抛异常会被外层 `except Exception` 接成 `_deny()`，等于每次需要续期的请求都 401 |

### 一个反直觉的点：表读不了时并不会全体拒绝

`.224` 上把吊销表改成 `root:root 0600`（网关 uid 1000 读不到）后，令牌**照常按
已知状态判**，而不是全体 401 —— 因为网关进程内已经有 last-known-good。
这不是漏洞，是 MISC-02 的设计。

真正会 fail-closed 的是「进程启动至今**一次都没成功读到过**」。而这条路径在
`.224` 上构造不出来：init 脚本每次启动都会把吊销表 `chown` 回 nftweb、
`chmod 600` 修好。该路径由单元测试覆盖。

`.224` 上真正该断言的是另一件事 —— **表读不了，已吊销的令牌不许复活**，
已实测通过。

`tests/mutation_check_auth_session.py` 30 → **37 处变异，捕获 37，漏过 0**

## 九、第四批：凭据优先级 + 剩下两条 P2（2026-10-16 已实施）

这一批处理第八节末尾挂着的两条待定夺项，外加第八节发现的那处优先级不一致。

### 1. `_extract_token` 优先级翻成 Bearer 优先

原实现的顺序是「cookie 在前、Authorization 在后」，而它自己和 `_verify_or_deny`
上方的注释都写着「Bearer 优先」—— 注释和实现对不上。实际后果：脚本客户端只要
机器上还留着浏览器 cookie，Bearer 就被无视而拿 401，明明带着有效令牌却登不进去。

**为什么这样翻是安全的（不是把跨站面放大）**：

- 浏览器**无法**被诱导跨站发送 `Authorization` 头。它不是 CORS 安全列表头，
  跨站 XHR 带它会触发预检；HTML 表单、`<img>`、`<script>` 更设不了。
- 本项目全链路**没有任何** `Access-Control-*` 响应头（已全库确认），预检拿不到放行。
- 浏览器正常访问不带该头，行为完全不变（走 cookie 分支）。
- `Authorization` 是客户端**显式**摆出来的凭据，优先级高于 cookie 这个
  「顺带带上」的东西，本就应当如此。

已配套补了一条：scheme 必须大小写不敏感（RFC 7235 §2.1）。不少客户端库发的是
小写 `bearer`，一旦写成 `startswith("bearer ")`，这些客户端会静默地全部掉到
cookie 分支 —— 又是一个不报错的坑。

### 2. 审计日志体积上限（AUTH-VULN-05）

`audit()` 原来是无脑 `open(path, "a")` 追加，没有任何上限。

**报告把机制写成「占满磁盘」，这是错的**：`.224` 上 `/var` 是 `/tmp` 的软链、
落在 tmpfs 上（实测 490 MiB），所以吃的是 **RAM**。在一台只有 1 GB 内存的路由上，
无上限的审计日志能把整机拖垮 —— 这是可用性问题，也顺带是取证问题
（进程 OOM 被杀时日志可能一起没）。

改法：超过上限（默认 2 MiB，可由 `AUTH_AUDIT_LOG_MAX_BYTES` 覆盖）就单文件轮转，
`.1` 覆盖上一代，总占用恒定 ≤ 2× 上限（4 MiB，占 `.224` 可用内存的 0.5%）。
轮转用 `os.replace`（原子）；轮转失败时**就地截断** —— 宁可丢历史也不能让文件
继续无限长。面板的日志视图读的是当前文件尾部若干行，轮转后照常可读。

判据是 `当前大小 + 这一行 > 上限` 而不是 `当前大小 >= 上限`：先判后写会让当前文件
最多溢出**一整行**，于是「总占用 ≤ 2×上限」这条硬边界差一点点不成立。
写测试时正是这条没被盯住，被变异脚本逮了个正着。

### 3. 会话绝对上限默认值非零（AUTH-VULN-03）

`TOKEN_ABS_TTL_DEFAULT` 与面板 `DEFAULT_CONFIG` 都从 `0`（不启用）改成 **43200**
（12 小时）。原默认 0 意味着滑动续期可以无限续命：一张被截获的令牌只要受害者还在用，
攻击者那张永不过期，而登出只吊销得到「受害者手上那一张」。

**只改默认值是不够的**，这里有两条独立的漏洞，都堵了：

1. **存量配置里躺着一个显式的 0**。已经装过的机器配置早就落了这个值，改默认值
   对它们毫无影响。可以合理认为这不是管理员主动选的：这个字段**前端从来没有
   输入框**（已全库确认），旧版 `DEFAULT_CONFIG` 写的又是 0。已加
   `_migrate_auth_absolute_timeout()` 在 `load_config()` 里迁移，并让面板**启动时
   落盘**（网关读的是磁盘，只改内存等于没迁）。
2. **网关执行点的 `else` 分支**。`_absolute_ttl()` 原来 `else 0`，也就是配置缺失/
   非法就等于「绝对上限关闭」。已改成回落到默认值 —— 这是最后一道口子。

> 这一批唯一带主观判断的地方：现在**没有任何途径把绝对上限关掉**（0 与非法值都
> 回落默认）。理由是这个字段从来没有 UI、没有文档说明，也没有「关闭」这个使用场景；
> 而 12 小时对路由器管理面板是宽松的，需要更长的可以调到 604800（7 天上限）。
> 如果确实需要「可关闭」这个语义，得新增一个显式的关闭值，而不是复用 0。

  「轮转分支被进入了几次」。
- **旧变异条目的锚点会随实现一起失效**：`logout：_extract_token 退回只读 cookie`
  那条的锚点正是被本轮改掉的旧实现体，源里一换它就静默失配（被跳过、不计入
  漏过，但覆盖悄悄没了）。已重新锚到当前实现，并把它升级成一条更强、仍然独立的
  变异「完全不认 Bearer」。

## 十、第五批：真实用户流程跑出来的两个洞（2026-10-16 已实施）

前四批的验证都是「打 API、看状态码」。这一批补了一条**像用户那样从头用一遍**的
端到端脚本（走面板 5443 与 nginx 8443 真实入口，开两个浏览器代表两台设备），
结果当场撞出两个真问题 —— 都不是 Shannon 报告里的，且**前四批的测试全都测不到**。

### 洞 1：限流表被删 = 所有人永久登不进（自伤式拒绝服务）

**机制**：`.224` 上 `/etc/nftables` 是 `drwxr-sr-x root:nftweb` —— **组只有 r-x，
没有写权限**。网关降权后以 uid 1000 运行，**建不出这张表**。init 脚本以 root 预建了
它，所以平时不暴露；但表一旦缺失（误删、tmpfs 被清、`prepare_nftweb_files` 失败），
`_mutate_ratelimit` 里的 `open(path, "a+")` 抛 `PermissionError`，整个 `auth_login`
走 `except Exception` → **HTTP 500**。

而且**没有任何自愈路径**：uid 1000 永远重建不出这张表。

实测：移走表后连续两次登录都是 500，表也不会被重建。

**修法**（照面板侧 `_ratelimit_degrade` 的既有约定 —— 面板早就有这个降级，网关是漏的）：

- 整段包 try，**任何异常都不许抛到登录链路**
- 降级到进程内内存计数，**并只警告一次**
- 取舍：这里选 **fail-open**（放行 + 审计）。代价是抗暴力破解能力暂时下降，
  收益是不会把人锁在门外 —— 与项目既定的「限流表损坏 fail-open、吊销表损坏
  fail-closed」一致
- 建表改用 `os.open(..., 0o600)`，去掉了结尾那个裸的 `os.chmod`（和 `revoke_jti`
  当初同一个坑）

### 洞 2：改密码后**门户页面**照样能打开（我自己的修复只做了一半）

第二批做的 MISC-01（改密码递增 epoch 作废全部会话）有个致命缺口：
**epoch 校验只写在 `_verify_or_deny` 里，`_authenticated` 没查。**

- `/auth/verify`（nginx `auth_request` 打的）→ 查 epoch → 改密后 401 ✅
- `/auth/portal`（浏览器直接访问的门户页面）→ 不查 epoch → 改密后**仍然 200** ❌

也就是说，用户改完密码看到的是「页面还能打开」，而页面背后的 API 已经在拒绝。
这种前后不一致比两边都失效更难排查 —— 而门户页面本身就是最该被关掉的那一扇门。

前面的测试为什么没抓到：**所有涉及 epoch 的测试都只打了 `/auth/verify`**，
正好是查 epoch 的那条路径。

**修法**：把 epoch 判据抽成 `_payload_epoch_ok()`，两条鉴权路径共用，
各写一份迟早会漏掉一边。同时 `_authenticated` 的取令牌也改走 `_extract_token`
（原来只读 cookie，和第二批修的 logout 是同一类的不对称）。

### 这一批自己踩的坑

- **「只测 helper 不测接线」又发生了一次**：降级后的计数我直接调
  `_mutate_ratelimit` 验证，全绿；部署到 `.224` 一实测，7 次连续错密码全是 401、
  一次 429 都没有 —— 因为 `auth_login` 的上锁判据是 `_is_locked()`，它**只读文件**，
  压根不看降级时写在内存里的计数。计数照记、锁定判定恒 False，暴力破解防护在降级
  期间被悄悄关掉。已让 `_is_locked` 同时查内存，并补了**打真实 `/auth/login`**
  的断言（`test_auth_policy_bounds.py` 3b 节）。
- **真机脚本本身的前 10 条断言全是错的**：面板 session cookie 真名是
  `nftables_web_session`（不是 Flask 默认的 `session`）、真实入口是 `GET /`
  （`/login` 对未登录返 401）、以及「共享 cookie jar + 手动 Cookie 头」混用会让
  「不带凭据访问」这种反向用例测出 200（是 jar 在骗人）。三处都写进脚本注释了。
- **变异锚点会随实现一起失效**：把 epoch 逻辑抽成 helper 之后，三条锚在旧内联代码
  上的变异静默失配（跳过、不计入漏过，覆盖悄悄没了）。已重新锚到 helper 里。

### 这一节挖出来的三个问题

#### 1. `auth_lan_bypass` 默认为 `True` —— 全新安装的网关对内网免认证 **[待用户定夺]**

**现象**：第一次跑 `journey.py` 得到 33/36，三个失败项：

```
FAIL  无凭据访问网关 /auth/portal → 401        <- HTTP 200
FAIL  **设备 A 的网关令牌立即 401**             <- HTTP 200
FAIL  **设备 B 的网关令牌也 401**               <- HTTP 200
```

**根因**（三处代码的组合）：

- `app.py:663` —— `DEFAULT_CONFIG["auth_lan_bypass"] = True`
- `auth_gateway.py:888` —— `if not cfg.get("auth_lan_bypass", False): return False`
  （配置缺失时 fail-closed，注释写着「配置缺失时应当要求认证（fail-closed），
  而不是默认放行」）
- `auth_gateway.py:898` —— `if addr.is_loopback: return True`

**`setup.sh` 写的配置里没有 `auth_lan_bypass` 这个键**，所以新装机器合并
`DEFAULT_CONFIG` 后拿到 `True`；再叠加 loopback 无条件放行，于是从 `127.0.0.1`
发起的请求根本走不到鉴权分支。

**这是前面五批从未暴露的问题**：`.224` 上老配置的 `auth_lan_bypass` 早就被调成
`false` 了，所以 journey.py 才会 36/36。**测试环境的一个残留设置，把一个
全新安装的默认行为遮住了整整五批。**

**实证**（第二次干净安装，`auth_lan_bypass` 保持默认值）：

```
直打 8444 /auth/portal : HTTP 200  {"device_id":"hCll2mPaGM-YtlaRby4avA","services":[],"success":true,"user":"lan"}
经 nginx 8443          : HTTP 200
```

经面板关掉之后：

```
关闭后无凭据访问 : HTTP 401
```

随后 `journey.py` 恢复 36/36。

**为什么这条要用户定夺而不是我直接改**：`auth_lan_bypass=True` 意味着
**路由器同一个 LAN 里的任何设备**（访客 Wi-Fi、客人的手机、同事）访问 8443
公网入口时都免认证直通所有 `public_access=true` 的服务。按这个产品「管住自家
公网入口」的定位，默认打开是反直觉的；但对纯家用场景，关掉意味着自己家里
每台设备访问都要登录一次。**这是产品取舍不是 bug**，默认值改哪边都会影响
一类用户的首次使用体验，所以留给用户拍板。

需要说明的是：网关自己的 fail-closed 兜底（`auth_gateway.py:888`）在实践中
已经是死代码——`DEFAULT_CONFIG` 总会把这个键写进配置，兜底分支永远走不到。

#### 2. `setup.sh` 的 nginx include 自动插入在 BusyBox sed 上必然失败 **[已修复]**

第一轮安装日志稳定打出：

```
[WARN ] 主 nginx.conf 缺少 include conf.d/*.conf，尝试添加...
[WARN ] 自动插入 include 失败，请手动在 http 块内添加: include conf.d/*.conf;
```

原写法：

```sh
sed -i '/^http {/,/^}/{ /^}/i\    include conf.d/*.conf;\n' "$nginx_conf"
```

三个缺陷叠在一起（`.224` 上用 BusyBox sed 逐一复现）：

1. **范围首端 `/^http {/` 里的 `{` 是裸花括号**。BusyBox 的正则解析器把它当
   区间量词的起始，直接报 `sed: unterminated {` 并放弃执行——不是「文件不需要改」，
   是根本没跑。
2. 就算转义了，**范围末端 `/^}/` 要求 `}` 在第 0 列**，而 OpenWrt 的 `nginx.conf`
   里 http 的闭合括号是缩进的（`  }`），区间同样匹配不上。
3. `i\` 文本里的 `\n` 和 `*.conf` 的 `*` 都没有按字面处理。

**本机为什么没出事**：OpenWrt 的 nginx 实际用 `-c /etc/nginx/uci.conf` 启动
（`/etc/nginx/uci.conf` → `/var/lib/nginx/uci.conf`），那份渲染产物第 34 行
本来就有 `include conf.d/*.conf;`。也就是说 **`setup_nginx` 花力气去改的
`/etc/nginx/nginx.conf` 根本不是服务在用的文件**，这次失败没有实际后果。
但它不是无害的：一旦 uci 渲染产物不含 conf.d（`uci set nginx.global.uci_enable=false`
或非 OpenWrt 的 nginx），网关配置就永远不会被加载，而 setup.sh 的自愈手段是坏的。

**修复**：改用 awk 按花括号配平定位 http 的闭合位置，并自带「已插过就不插」的判断：

```awk
function bal(s,   t) { t = s; return gsub(/\{/, "{", t) - gsub(/\}/, "}", t) }
/^[[:space:]]*http[[:space:]]*\{/ { inhttp = 1; has = 0; depth = 0 }
{
    if (inhttp && $0 ~ /^[[:space:]]*include[^#]*conf\.d\/\*\.conf/) has = 1
    if (inhttp && !has && depth + bal($0) <= 0) { print "    include conf.d/*.conf;"; has = 1 }
    print
    if (inhttp) depth += bal($0)
}
```

改写之前先在 `.224` 上对**真实的 `nginx.conf`** 实测了四个性质，全部通过：

- **幂等**：连跑三次，include 出现次数恒为 1（不依赖调用方的 grep 守卫）
- **位置正确**：插在 http 块闭合括号之前
- **`nginx -t` 通过**
- **抗嵌套**：http 里有 `server { ... }` 子块时，插在子块之后、http 闭合之前

第二轮安装日志变成：

```
[INFO ] 已备份原 nginx 配置
[WARN ] 主 nginx.conf 缺少 include conf.d/*.conf，尝试添加...
[OK   ] 已添加 include conf.d/*.conf 到主配置
```

`/etc/nginx/nginx.conf:19` 确认已插入。
