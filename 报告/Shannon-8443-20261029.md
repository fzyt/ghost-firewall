## 三、本轮新增代码面（host 分发，上轮不存在）

host 分发是本轮相对上轮唯一的新攻击面：**每服务一个 nginx server 块**，服务挂在域名根路径。

| 面 | 位置 | 复核结论 |
|---|---|---|
| 对外域名校验 | `app.py` `_sanitize_rp_host` | 只允许纯主机名、不放通配、拒绝 `/ : * @ ; ? #` 与换行；值直接进 nginx `server_name` → 无指令注入面 |
| host server 块认证 | 设备实际 nginx conf | ✅ `auth_request /_auth` 在位；`/_auth` 是 `internal`；未认证 302 → `/auth/login?next=…` |
| 代理头伪造 | 设备实际 nginx conf | ✅ 两个 server 块的 `/_auth` 都有 `proxy_set_header X-Real-IP $remote_addr` —— 客户端自造 `X-Real-IP` 覆盖不掉；`client_ip()` 也只采信回环对端的代理头 |
| host 模式路径改写 | 设备实际 nginx conf | ✅ host 模式**零改写**（无 `sub_filter`、无 `proxy_redirect`）—— 路径与 WS 天然正确，无注入面 |
| cookie Domain | `auth_gateway.py` `_effective_cookie_domain` | IP 主机名下退回 host-only（RFC 6265 §5.3 会整条拒收带 Domain 的 IP cookie）；父域之下才带 Domain |
| 门户链接 | `auth_gateway.py` `auth_portal` + `static/portal.js` | `a.href = s.url` —— `s.url` 拼自规则里的 host，`_sanitize_rp_host` 已挡住脚本协议 |

**Z5（本地进程边界）**：Shannon 的架构 agent 指出 `client_ip()` 对**任何回环对端**采信 `X-Real-IP`，因此设备上的本地进程可以自造内网源 IP 触发 LAN 免认证。
**复核结论：实际影响低。** 认证服务只绑 `127.0.0.1:8444`；面板 `app.py` 不反代到 8444（只用于配置与探活），全仓无「未认证端点把用户可控头转发到 8444」的链路。要利用它必须先在路由器上拿到本地代码执行 —— 那时直接读密码文件更划算。

### 4.6 动态实测：滑动续期把用户踢下线（对应 #10）—— 本轮最重要的发现

**机制（代码 + 设备 nginx 配置双证）**：

1. `auth_gateway.py:1277-1302`：nginx 的 `auth_request` 打到 `/auth/verify` → `_verify_or_deny()`。当剩余有效期不足一半（`exp - now < ttl * 0.5`，即 30 分钟会话的后 15 分钟）时，走滑动续期：先 `revoke_jti()` 吊销旧 jti，再 `issue_token()` 签新令牌，最后 **`_set_cookies(resp, new_tok, ...)`（`:1302`）—— 新令牌只通过这次响应的 `Set-Cookie` 下发**。
2. 设备 nginx 的 `/_auth` 是 `auth_request` 的子请求目标。nginx 的 `auth_request` 模块**默认丢弃子请求响应头**，`Set-Cookie` 不会传给客户端 —— 除非显式 `auth_request_set $var $upstream_http_set_cookie` 捕获后再 `add_header`。
3. 设备实际配置（`/etc/nginx/conf.d/00-nftables-web-gateway.conf`）两个 server 块各只有两条 `auth_request_set`：
   ```
   auth_request_set $auth_user   $upstream_http_x_auth_user;
   auth_request_set $auth_device $upstream_http_x_auth_device;
   ```
   **没有任何一条捕获 Set-Cookie。**
4. 而续期本身**已经生效**（旧 jti 已被吊销）—— 这正是最糟的组合：**服务端把旧凭据作废了，新凭据却没送到客户端。**

**动态实测（`.233`，2026-10-29 10:13 → 10:29）**：

登录拿 `gw_token`（`exp - iat = 1800s`），然后每 45 秒用**同一个 cookie** 请求受保护路径 `/siyuan/`，同时从设备侧读审计日志与吊销表：

```
[10:27:24] 剩余= 942s HTTP 401 网关拒绝=no Set-Cookie=no token_refreshed=0 吊销表字节=2
[10:28:09] 剩余= 897s HTTP 401 网关拒绝=no Set-Cookie=no token_refreshed=0 吊销表字节=32   ← 越过 900s 阈值
```

设备审计日志里的完整因果链：

```json
{"ts": "2026-10-29T10:28:09", "event": "token_refreshed", "ip": "192.168.100.249",
 "device": "t4MyHpaieMLsCQPS3UbwQQ", "uri": "/siyuan/"}
{"ts": "2026-10-29T10:28:54", "event": "verify_denied",   "ip": "192.168.100.249",
 "uri": "/siyuan/", "reason": "revoked"}
```

吊销表：`{"1LYARb9WShv-e5-M": 1793241786}` —— 旧 jti 已入吊销表，`exp` 正是那个旧令牌的到期时刻。

**结论（已实测确认）**：

- 服务器端续期成功发生（`token_refreshed`），旧凭据**当场作废**；
- 客户端**全程没有收到任何 `Set-Cookie`** —— 新令牌被 nginx 丢弃在 `auth_request` 子请求里；
- 45 秒后，浏览器手上那个旧 cookie 变成一枚被吊销的令牌 → `verify_denied / revoked` → 302 跳登录页。

**用户可感知的后果**：会话建立约 15 分钟后，第一次点服务卡片就会被踢回登录页，而且必须重新输入密码（浏览器手里的 cookie 已经作废，重试无用）。**滑动续期这个功能在生产上是 100% 失效的** —— 它只把旧凭据作废了，从没把新凭据发出去。

**这不是本轮 host 分发引入的回归**：该逻辑自 `bfde5ec fix(auth): 会话生命周期加固` 起就存在，所有部署（`.233` / `.224`）都受影响。

**修复方向（两条，建议都做）**：

1. **不要在 `auth_request` 路径上做续期**。子请求是机器对机器的判定，令牌下发必须走一条**客户端能直接拿到响应头**的路径。把续期从 `_verify_or_deny()` 挪到 `/auth/status`（它是被普通 `proxy_pass` 转发的，响应头会原样到达浏览器），`auth_request` 只做纯校验、不动令牌。
2. 若坚持在 `auth_request` 路径续期，则 nginx 必须显式捕获并转发：
   ```nginx
   auth_request_set $auth_set_cookie $upstream_http_set_cookie;
   add_header Set-Cookie $auth_set_cookie always;
   ```
   —— 但一个响应可能带多张 `Set-Cookie`（`gw_token` + `gw_device`），`$upstream_http_set_cookie` 只能取一张，这条路更脆。

> 附带发现：`/auth/status` 目前**既不续期也不下发新 cookie**，所以即使把续期挪过去，还要确认门户页每次打开都会调用 `/auth/status`（`portal.js` 确实会调），才能保证浏览器拿到新令牌。

### 4.8 动态实测：登录页开放重定向（对应 #30）——  phishing 链

**机制**：`backend/static/login.js` 的 `safeNext()` 是登录后的回跳目标守卫：

```js
function safeNext() {
  var raw = new URLSearchParams(location.search).get('next') || '/';
  if (raw.charAt(0) !== '/') return '/';
  if (raw.charAt(1) === '/') return '/';          // 挡 //evil.com
  if (raw.indexOf('\\') !== -1) return '/';       // 挡 /\evil.com
  if (/^[a-z][a-z0-9+.-]*:/i.test(raw)) return '/'; // 挡 javascript: / data:
  return raw;
}
```

四个守卫都正确，但**没有任何一个检查控制字符**。而 WHATWG URL 规范在解析时会**剥掉 tab(0x09) / LF(0x0a) / CR(0x0d)** —— 于是 `/\t/evil.com` 被解析成 `//evil.com`（协议相对 URL → 跳到 `https://evil.com/`）。

**Node 层先验证解析结果**：

```
next="/%09/evil.com"   safeNext="/\t/evil.com"  -> https://evil.com/
next="/%0a/evil.com"   safeNext="/\n/evil.com"  -> https://evil.com/
next="/%0d/evil.com"   safeNext="/\r/evil.com"  -> https://evil.com/
next="//evil.com"      safeNext="/"             -> https://siyuan.fzyto.top:8443/   ← 挡住
next="javascript:..."   safeNext="/"             -> https://siyuan.fzyto.top:8443/   ← 挡住
```

**真机端到端验证**（Playwright + `--host-resolver-rules` 指到 `.233`，走真实 TLS/SNI；用 `page.route` 拦截并**中止**任何跳出 `.233` 的请求，**不真连外部站点**）：

```
next="/%09/evil.invalid"   最终URL=chrome-error://chromewebdata/
   ⛔ 跳出本站的请求: https://evil.invalid/
next="/%0a/evil.invalid"   最终URL=chrome-error://chromewebdata/
   ⛔ 跳出本站的请求: https://evil.invalid/
next="/%0d/evil.invalid"   最终URL=chrome-error://chromewebdata/
   ⛔ 跳出本站的请求: https://evil.invalid/
next="//evil.invalid"      最终URL=https://siyuan.fzyto.top:8443/check-auth?to=%2F
   （未跳出本站）
next="/safe/path"          最终URL=https://siyuan.fzyto.top:8443/safe/path
   （未跳出本站）
```

**结论（已实测确认）**：受害者在**合法的网关登录页**输入密码 → 登录成功 → 浏览器立刻被弹到 `https://evil.invalid/`。
这是典型的**凭据钓鱼链**：用户看到的是自己网关的真实域名与真实的 HTTPS 证书，输入的是真密码，登录成功后却被送到攻击者站点（此时页面可以伪装成"会话过期，请重新登录"再骗一次密码）。三组对照（`//` 被挡、正常路径留站内）证明这是**绕过**而不是行为变化。

**修复**（一行即可）：在 `safeNext()` 里把控制字符剥掉再判，或直接拒绝含控制字符的 `next`：

```js
if (/[\u0000-\u001f\u007f]/.test(raw)) return '/';
```

更稳妥的写法是**先归一化再判**：删掉所有 tab/LF/CR 之后再跑现有的四条守卫（否则 `/\t/evil.com` 归一化成 `//evil.com` 后会被 `charAt(1) === '/'` 挡住）。

> 附带提醒：同一个 `?next=` 参数还被 nginx 的 `error_page 401 = @to_login` 用作回跳目标（`return 302 https://$host:8443/auth/login?next=$request_uri;`），服务端侧 `$request_uri` 未做 URL 编码，含 `&`/`#` 的路径会在拼接时产生参数注入 —— 本轮未验证其可利用性，但值得一并检查。

#### #52 的实测（这条改了我的结论）

代码（`auth_gateway.py:323-344`）：

```python
with PBKDF2_GATE:
    try:
        algo, iters, salt, hash_hex = stored.split("$", 3)
        ...
        iters = int(iters)
        if iters < PBKDF2_ITERATIONS_MIN: raise ValueError("iters")
    except Exception:
        # 迭代数取下限：既去掉那个数量级差异 …
        hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"),
                            b"nftables-web-dummy", PBKDF2_ITERATIONS_MIN)
        return False
    digest = hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"),
                                 salt.encode("utf-8"), iters)   # ← 用存储哈希的 iters
```

- `PBKDF2_ITERATIONS_MIN = 100000`（`:83`）
- 面板默认 `PBKDF2_ITERATIONS = 200000`（`app.py:14`）
- **设备上的实际存储哈希**：`pbkdf2_sha256$200000$caf3ca19…`

**注释里"取下限就消掉数量级差异"只在真实哈希也恰好用下限时成立。** 实测（直接在 `.233` 上跑）：

```
真实路径 200000 轮: 94.9 ms
dummy 路径 100000 轮: 48.6 ms
差值: 46.3 ms (1.95x)
```

46 ms 的差在网络上采样几次就能稳定区分 → **「本机是否配了网关密码」这个状态仍可被枚举**。上轮 AUTH-01 修掉的是「毫秒级短路」（几十万轮 vs 不到 1ms），但把 oracle 从「数量级」降到了「2 倍」，没消掉。

**修法**：dummy 路径不要固定用 `PBKDF2_ITERATIONS_MIN`，而要用**存储哈希里那个实际的 iters**；若哈希损坏无法解析，则用一个**固定的高迭代数**（≥ 面板默认值 200000），保证 dummy 路径**不慢于**真实路径。

#### 顺带实测否掉的一条 agent 观察

Shannon agent 在 worker 日志里记：「限流器按 `client_ip()` 分键，且**客户端的 `X-Forwarded-For` 被采信** —— 每个不同的 XFF 产生了独立的计数」，并据此怀疑可以伪造 XFF 绕过限流、进而触发 LAN 豁免。

**实测否掉**：设备 nginx 的**每一个** location（含 `/_auth`、`/auth/login`、`/auth/status`、`/auth/portal`、服务 location）都有 `proxy_set_header X-Real-IP $remote_addr;`，而 `client_ip()` **优先读 X-Real-IP**。实测两次带不同 `X-Forwarded-For`（`10.9.9.9` / `10.9.9.10`）的失败登录，限流表里**都记在真实 IP `192.168.100.249` 名下**：

```json
{"192.168.100.249": {"fails": [1793245821.47975, 1793245821.6002185]}}
```

→ **XFF 伪造无效**，限流与 LAN 判定都锚在真实来源 IP 上。agent 那条观察多半是把**思源上游自己的限流器**（6807 端口那个测试实例）当成了网关的。

### 5.3.1 安全模型层面的两条根本问题

这轮最值得记住的不是单个 bug，而是两个**结构性问题**：

1. **密钥/会话的权限边界画错了（#33）**。设计意图是「认证网关降权到 `nftweb`、面板留 root」，但**面板的会话签名密钥和网关的令牌密钥是同一个文件**，且该文件属组 `nftweb` 可读 ⇒ **面向公网的降权进程持有 root 面板的会话签名能力**。降权做到一半，反而给攻击者递了把万能钥匙。
   **建议**：面板用**独立**的 session 密钥文件（只 root 可读），网关用**另一个**只含自己派生材料的文件（`nftweb` 可读）。两者彻底分离。

2. **「安全状态」和「配置项」混在同一份 JSON（#35 / #37 / #38 / #41 / #44）**。`auth_token_epoch`、`trusted_ip4`、`panel_allowed_nets` 这些是**安全状态**，却和普通设置一样走通用读写路径，靠注释和告警维持语义。结果是：#35 能把「改密码作废全部会话」的保证撤销掉、#37 让新装机器天然 LAN 免认证、#41/#44 让整份防火墙配置和可信 IP 列表进缓存/进 world-readable 文件。
   **建议**：把安全状态字段拆到**独立文件 + 独立写路径**（像 `nftables-web-auth-ratelimit.json` 那样），通用 `/api/config` 一律不碰。

### 5.4 建议的修复优先级

**P0 —— 安全模型（先修这条，否则其它修了也白搭）**

0. **#33 面板签名密钥与网关令牌密钥共用同一个文件**。拆分：面板用**独立**的 session 密钥（只 root 可读），网关用**另一个**只含自己派生材料的文件（`nftweb` 可读）。这一条是**架构级**改动，但它是 #33 的根。

**P0 —— 可用性 / 可被利用**

1. **#30 登录页开放重定向（钓鱼链）**。`safeNext()` 缺控制字符检查，tab/LF/CR 被 WHATWG URL 规范剥掉后 `/\t/evil.com` → `//evil.com`。**已实测确认**。修法：先剥掉 `[\u0000-\u001f\u007f]` 再跑现有四条守卫（或直接拒绝含控制字符的 `next`）。**改动量最小、收益最大。**
