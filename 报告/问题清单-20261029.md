### P0-1　滑动续期把用户踢下线（可用性事故 · 网关侧） · ✅ 已修复（v0.8.7）

| | |
|---|---|
| **位置** | `backend/auth_gateway.py:1300-1302`（`_verify_or_deny` 滑动续期） |
| **现象** | 令牌快到期时，网关签发新令牌并吊销旧令牌，但**新令牌只经 `_set_cookies(resp, new_tok, ...)` 下发**；而设备 nginx 的 `/_auth` 是 `auth_request` 子请求目标，**默认丢弃子请求响应头**，配置里只有 `auth_request_set $auth_user / $auth_device` 两条，**没有捕获 Set-Cookie**。 |
| **实测证据** | 设备审计日志：`10:28:09 token_refreshed` → `10:28:54 verify_denied/reason=revoked`；吊销表 `{"1LYARb9WShv-e5-M": 1793241786}`；客户端全程无 Set-Cookie。**旧令牌被吊销、新令牌没到客户端 → 用户被踢回登录页。** |
| **影响** | 每一个登录用户在 **15 分钟后**被强制重新登录。自 `bfde5ec` 起存在，所有部署都中招。 |
| **修法** | 二选一：① 把续期从 `_verify_or_deny()` 挪到 **`/auth/status`**（普通 `proxy_pass`，响应头原样到浏览器）；② nginx 加 `auth_request_set $auth_set_cookie $upstream_http_set_cookie;` + `add_header Set-Cookie $auth_set_cookie always;`（一次响应两张 cookie 时 `$upstream_http_set_cookie` 只取一张，更脆）。 |
| **必须补的回归测试** | 登录 → 把令牌推进续期窗口 → 再请求受保护路径 → **断言客户端拿到的新 cookie 仍然可用**。 |

### P0-2　登录页开放重定向（钓鱼链 · 网关侧） · ✅ 已修复（v0.8.7）

| | |
|---|---|
| **位置** | `backend/static/login.js:67-78`（`safeNext()`） |

### P0-3　面板签名密钥与网关令牌密钥共用同一个文件（安全模型 · 跨面） · ✅ 已修复（v0.8.7）

| | |
|---|---|
| **位置** | `backend/app.py:150` 附近 + `backend/nftables-web-auth.init:75-100` |
| **问题** | 设计意图是「认证网关降权到 `nftweb`、面板留 root」，但**面板的会话签名密钥和网关的令牌密钥是同一个文件**，且该文件属组 `nftweb` 可读 ⇒ **面向公网的降权进程持有 root 面板的会话签名能力**。降权做到一半，反而给攻击者递了把万能钥匙。 |
| **实机核对** | `.233` 上 `nftables-web-secret` = `0640 root:nftweb`；网关进程 `Uid: 1000`（nftweb），面板 `app.py` = `Uid: 0`（root）。**降权本身是生效的，但共享密钥让降权失去意义。** |
| **修法** | 拆成两个文件：面板用**独立**的 session 密钥（只 root 可读），网关用**另一个**只含自己派生材料的文件（`nftweb` 可读）。两者彻底分离。**架构级改动，但它是本条的根。** |

### P0-4　安全状态字段混在通用配置里（安全模型 · 面板侧） · **实测坐实** · ✅ 已修复（v0.8.7）

| | |
|---|---|
| **位置** | `backend/app.py:2303`（`new_cfg.update(incoming)`） |
| **问题** | `auth_token_epoch`、`trusted_ip4`、`panel_allowed_nets` 这些是**安全状态**，却和普通设置一样走通用读写路径，靠注释和告警维持语义。结果：`auth_token_epoch` 能被通用 `/api/config` **改回旧值**，撤销掉「改密码作废全部会话」的保证。 |
| **佐证（代码）** | `backend/app.py:6535-6578` 的 `GATEWAY_OWNED / RP_OWNED / READONLY` 名单里 **`auth_token_epoch` 三者皆无**。 |
| **实测证据（写权限）** | 管理员会话 `POST /api/config {"auth_token_epoch": 999}` → **HTTP 200「配置已保存」**，落盘 `auth_token_epoch = 999`；响应里 `ignored_gateway_fields: []` / `ignored_readonly_fields: []` / `ignored_rp_fields: []` —— **三个剔除名单一个都没拦它**。 |
| **实测证据（危害）** | 改成 999 的**同一秒**，面板自己的会话立刻返回 `{"code":"AUTH_EXPIRED","message":"密码已修改，请重新登录"}` —— **epoch 机制本身是有效的，问题在于谁能写它**。 |
| **两种危害** | ① 调**大** → 立刻作废所有会话（DoS）；② 调**小 / 调回旧值** → **撤销「改密码作废全部会话」的保证**，被作废的令牌可以复活。 |
| **附带发现** | 代码注释写「没带 `config_rev` 的调用**不拦**（第三方脚本、curl、旧版前端）」—— 实测不带 `config_rev` 直接写成功，**版本闸对这条完全无效**。 |
| **修法** | ① `auth_token_epoch` 加进 `READONLY_CONFIG_KEYS`（或 `GATEWAY_OWNED_CONFIG_KEYS`）；② **不带 `config_rev` 的请求一律拒收**；③ 长期：把安全状态字段拆到**独立文件 + 独立写路径**（像 `nftables-web-auth-ratelimit.json` 那样）。 |
| **测试后恢复确认** | `auth_token_epoch` 已改回 **0**，`config_rev` 回到 `c2288113ed02e7ec`（与测试前一致）。 |

| | |
|---|---|
| **位置** | `backend/auth_gateway.py:675`（`_mutate_ratelimit`）、`:1125`（`remaining` 计算） |
