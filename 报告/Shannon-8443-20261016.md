On 2026-10-15, a static-analysis assessment of the nftables-web authentication gateway and management panel at https://192.168.100.224:8443 identified seventeen vulnerabilities spanning authentication, authorization, and session-handling code paths, most rated medium or higher in assessed severity. Injection, XSS, and SSRF classes were assessed in scope and produced no findings. Severity ratings and impacts are assessed from the vulnerability class and described exposure only; no live exploitation was performed against the target, and no finding is presented as measured or demonstrated.

# Authentication Findings

## Identified Vulnerabilities

### AUTH-03: /api/auth/login accepts PBKDF2 hashes below gateway's 100k iteration floor

**Summary:**
- **Severity:** High
- **Confidence:** Medium
- **OWASP:** A04:2025 — Cryptographic Failures
- **Vulnerable location:** POST /api/auth/login (backend/app.py:73 — `hashlib.pbkdf2_hmac(...)` invoked with `int(iters)` parsed from the stored hash, no minimum enforced)

**Overview:**
The panel's `_verify_password` derives the PBKDF2 iteration count directly from the stored hash and forwards it to `hashlib.pbkdf2_hmac` without enforcing a minimum. The gateway front-line rejects stored hashes below the `PBKDF2_ITERATIONS_MIN` floor of 100,000, but the panel shares the same `AUTH_PASSWORD_FILE` and does not. As a result, the shared on-disk format is interpreted more strictly by the front-line than by the management endpoint it is meant to protect.

**Impact:**
If a low-iteration hash (for example 1, 1,000, or 10,000 iterations) is placed into the shared `AUTH_PASSWORD_FILE` — whether by a future legacy-import path, a restore-from-backup flow that does not re-derive hashes, a privileged insider, or another file-write vulnerability — the gateway rejects the hash and the account appears locked, but the panel accepts it. Successful panel login grants the most critical write capability in the deployment (firewall/nftables rules, reverse-proxy rules, certificates, DDNS). Once such a hash is on disk, offline brute-force of the low-iteration hash is trivially fast, and the recovered plaintext authenticates to the panel directly even though the intended defence-in-depth front door appears to be holding.

**Remediation:**
Enforce the same `PBKDF2_ITERATIONS_MIN` floor in the panel-side `_verify_password` before calling `pbkdf2_hmac`, rejecting any stored hash below the floor as an authentication failure. Reject attempts to write such hashes via any future import, downgrade, or restore-from-backup path so the on-disk invariant is preserved end-to-end.

### AUTH-05: Token replay on /auth/verify — `dev` claim unenforced, `Authorization: Bearer` fallback accepted

**Summary:**
- **Severity:** High
- **Confidence:** Medium
- **OWASP:** A07:2025 — Authentication Failures
- **Vulnerable location:** POST /auth/login (token issue) -> GET /auth/verify (token replay) -> GET /auth/portal (token replay). Code: backend/auth_gateway.py:219 (issue_token writes `dev` claim); backend/auth_gateway.py:700-770 (_verify_or_deny never compares `dev`); backend/auth_gateway.py:797-803 (_authenticated never compares `dev`); backend/auth_gateway.py:711-714 (Bearer fallback on /auth/verify)

**Overview:**
The token's `dev` claim is set at issue and echoed in the `X-Auth-Device` response header, but neither `_verify_or_deny` (lines 700-770) nor `_authenticated` (lines 797-803) ever compares `payload["dev"]` against `device_id_from_request()` or any other client-supplied device identifier. The token therefore carries no enforced device binding. In addition, `/auth/verify` accepts `Authorization: Bearer <token>` as a fallback when the cookie is absent (lines 711-714), and nginx's internal `_auth` location forwards the original request's `Authorization` header to the auth_request subrequest (`proxy_set_header Authorization $http_authorization`). Combined, these mean that once a `gw_token` value escapes the cookie jar — through a proxy log, browser memory dump, post-exploit tool, log inclusion, or exfiltration by XSS in another service — it is replayable from any client, on any IP, in any browser, with either the cookie or a `Bearer` header.

**Impact:**
If the `gw_token` value is exfiltrated by any means, an attacker can replay it via the cookie path (`curl --cookie "gw_token=<stolen>"` against `/auth/portal` returns 200 plus the service list) or via the Bearer path against any nginx-fronted protected service (because nginx forwards `Authorization` to `/auth/verify`, which accepts it as a Bearer fallback). The stolen token continues to be accepted on every subsequent verify from any client until either the absolute TTL elapses or the legitimate user calls `/auth/logout`, which revokes the `jti`. The HTTP-only / Secure / SameSite=Lax cookie flags protect against browser-resident JavaScript exfiltration, but they do not protect against non-browser attackers who obtained the raw token value via any other means. Because the gateway's per-IP rate limit is keyed on `/auth/login` and not on `/auth/verify`, a replayed stolen token can be exercised at unlimited requests per second. The single hardcoded `kirito` principal means a stolen token grants full administrative access.

**Remediation:**
Enforce device binding by comparing `payload["dev"]` against `device_id_from_request()` in both `_verify_or_deny` and `_authenticated`, and reject tokens whose device claim does not match the presenting client. Remove the `Authorization: Bearer` fallback on `/auth/verify` (or restrict it to internal-only callers) so cookie-based protections are not bypassed by a non-browser attacker. Add a rate-limit gate to `/auth/verify` independent of `/auth/login` to limit replay throughput of stolen tokens.

### AUTH-01: Observable timing on `bool(stored)` short-circuit in `auth_login`

**Summary:**
- **Severity:** Medium
- **Confidence:** Medium
- **OWASP:** A07:2025 — Authentication Failures
- **Vulnerable location:** POST /auth/login (backend/auth_gateway.py:656 — `bool(stored)` short-circuit skips PBKDF2 derivation when the password file is missing or corrupt)

**Overview:**
The `auth_login` handler evaluates `bool(stored)` before invoking PBKDF2, so the full 200,000-iteration HMAC-SHA256 derivation is skipped on the no-hash-stored branch while it is performed in full on the wrong-password branch. The response body (`AUTH_FAILED`), status code (401), and message ("密码错误") are equalised across both paths, but wall-clock latency differs by tens of milliseconds because the PBKDF2 work is conditionally executed. The result is a remote, unauthenticated timing oracle that distinguishes deployments where the panel password has never been initialised (or where `/etc/nftables/nftables-web-password` has been deleted or corrupted) from properly configured deployments.

**Impact:**
An external attacker can fingerprint, per target, whether the shared password hash file is absent or corrupt versus populated with a valid hash, by issuing repeated POSTs to `/auth/login` and measuring end-to-end response time. Fresh or misconfigured panels can be prioritised for follow-up activity, since they are likelier to host weak or default credentials. The defect is informational rather than exploitable on its own: no authentication is bypassed, and the body of the response is held constant.

**Remediation:**
Always execute the full PBKDF2 derivation on the no-hash-stored branch (treat the missing file as a normal password failure), or perform a dummy PBKDF2 against a constant salt to make the wall-clock cost of the two paths indistinguishable. Pair the constant-time path with an explicit `auth_failure` audit event so missing-file conditions remain visible in the JSONL log.

### AUTH-04: Per-IP rate limit on /auth/login bypassable via distributed IPs

**Summary:**
- **Severity:** Medium
- **Confidence:** Medium
- **OWASP:** A07:2025 — Authentication Failures
- **Vulnerable location:** POST /auth/login (backend/auth_gateway.py:610-680 auth_login) plus backend/auth_gateway.py:310-358 _mutate_ratelimit and backend/auth_gateway.py:813-827 _is_locked

**Overview:**
The auth endpoint enforces rate limiting exclusively per source IP (5 failures per 300s window, escalating to a 900s lockout). The lockout is keyed on the `X-Real-IP` header that nginx properly overrides with `$remote_addr`, so client-side `X-Forwarded-For`/`X-Real-IP` spoofing does not defeat the limit, but no per-account, no CAPTCHA, no proof-of-work, and no distributed-attack dimension is layered on top. There is also no server-side password-strength policy on the login path.

**Impact:**
An external attacker with a residential-proxy network, VPN rotation pool, or botnet can attempt up to four passwords per source IP per five-minute window indefinitely, with total throughput scaling linearly with the number of attacker IPs. Although each PBKDF2 guess at 100k iterations costs roughly 100ms, a 100-IP botnet sustains on the order of 100 attempts per minute. Against an operator-set admin password of weak or moderate strength, a sustained distributed brute-force can compromise the single hardcoded `kirito` account within days to weeks. Header spoofing cannot bypass the lockout, but IP diversity alone can.

**Remediation:**
Layer per-account throttling and CAPTCHA or proof-of-work on top of the per-IP lockout so IP diversity does not translate directly into credential throughput. Enforce a server-side minimum password strength (length, complexity, breach-list match) at the point of password creation or rotation. Consider an absolute daily/global attempt budget that is independent of source IP diversity.

### AUTH-02: `remaining` field in /auth/login 401 body discloses live lockout counter

**Summary:**
- **Severity:** Low
- **Confidence:** High
- **OWASP:** A07:2025 — Authentication Failures
- **Vulnerable location:** POST /auth/login (backend/auth_gateway.py:482-484 — auth_login 401 failure response body)

**Overview:**
The 401 response returned by `auth_login` includes a `remaining` integer field that reports the live count-down of failed attempts left before the per-IP lockout fires. Although the response message and status code are designed to be constant between the wrong-password and missing-password-file paths, the auxiliary counter is exposed in the unauthenticated response body and undermines the generic-error-body anti-enumeration goal.

**Impact:**
Unauthenticated attackers can pace brute-force attempts with high precision by reading `remaining` from each 401 response, stopping just before the bucket locks and detecting the lockout state without observing the 429 transition. Combined with distributed IP rotation, this allows an external attacker to schedule per-proxy attempts so each bucket is drained to its last allowed try before being rotated out, sustaining continuous guessing against the single hardcoded account.

**Remediation:**
Remove the `remaining` field from the failure response body and return only `{success: false, code: "AUTH_FAILED", message: "密码错误"}`. If lockout-progress introspection is required, gate it behind an authenticated endpoint rather than returning it in the unauthenticated failure response.

## Identified Vulnerabilities

### AUTHZ-01: Wildcard LAN subnet (0.0.0.0/0 or ::/0) in lan_subnet4/lan_subnet6 collapses trust boundary in `is_lan_source` and generated nginx config

**Summary:**
- **Severity:** High
- **Confidence:** High
- **OWASP:** A01:2025 — Broken Access Control
- **Vulnerable location:** POST /api/config (post_config) -> backend/app.py:1119, plus backend/app.py:732 (_safe_cidr), backend/app.py:488 (validate_config), backend/app.py:1232 (_detect_risks), backend/auth_gateway.py:510 (is_lan_source's `any(addr in n for n in subnets)` accepts any address when subnet is 0.0.0.0/0 or ::/0), and backend/app.py:4349 (generated nginx `allow 0.0.0.0/0;` precedes `deny all;`)

**Overview:**
`_safe_cidr` does not reject the wildcard `0.0.0.0/0` or `::/0`, `validate_config` does not inspect `lan_subnet4`/`lan_subnet6`, and `_detect_risks` does not flag wildcards. `post_config` merges the incoming body verbatim into the persisted config. With `auth_lan_bypass=True` (the panel default), `is_lan_source()` matches the wildcard subnet and treats every client IP as LAN; for `public_access=false` services, the generated nginx config contains `allow 0.0.0.0/0; deny all;` where the `allow` matches first.

**Impact:**
A single misconfiguration by any authenticated panel user — entering `0.0.0.0/0` as the LAN subnet — silently grants anonymous WAN clients the same access as authenticated LAN users on every `public_access=true` service, and exposes every `public_access=false` LAN-only service to the entire IPv4 internet via the generated `allow` directive. The defect is silent because no validator or risk detector rejects or warns about wildcard subnets, and it persists in the on-disk config across reboots until corrected.

**Remediation:**
Reject `0.0.0.0/0` and `::/0` (and any prefix length smaller than the configured local subnet minimum) in `_safe_cidr` with an explicit error, inspect `lan_subnet4`/`lan_subnet6` in `validate_config`, and add a hard warning in `_detect_risks` whenever a wildcard subnet is present. Permit `auth_lan_bypass=True` only when the configured subnet list excludes all-wildcard entries.

### AUTHZ-02: Mass assignment in /api/config — `new_cfg.update(incoming)` accepts arbitrary top-level keys

**Summary:**
- **Severity:** Medium
- **Confidence:** High
- **OWASP:** A01:2025 — Broken Access Control
- **Vulnerable location:** POST /api/config (post_config) — backend/app.py:1119 `new_cfg.update(incoming)` (no field allow-list, only the literal key `confirm` is popped), backend/app.py:1122 `validate_config(new_cfg)` (never strips unknown keys), backend/app.py:1144 `save_config(new_cfg)` (persists the unverified dict)

**Overview:**
`post_config` performs `new_cfg.update(incoming)` on the JSON request body (only stripping the literal key `confirm`), then runs `validate_config` which inspects only schema-known fields and never rejects unknown keys. The merged dict is persisted verbatim to `/etc/nftables/nftables-web-config.json` and re-loaded with `DEFAULT_CONFIG` merged on top. No field-level allow-list exists.

**Impact:**
An authenticated client can persist arbitrary top-level keys — privileged flags, forged `list_history` or `ip_presets` entries, attacker-controlled blobs — into the on-disk configuration. On every subsequent `load_config()` the unknown keys survive the `DEFAULT_CONFIG` merge and are propagated to every consumer of `load_config()`, supplying attacker-controlled values to any current or future template, render, or shell-interpolation path that iterates the config dict. The direct observable effect today is largely cosmetic UI pollution and config-file bloat, but the persistence layer has no schema gate, so the persistence primitive is unsuppressed.

**Remediation:**
Introduce an explicit per-field allow-list in `post_config` and reject unknown keys with a 400 response. Have `validate_config` strip or refuse any key not in the schema before the dict is persisted. Re-emit a normalized view on every `load_config()` so unknown legacy keys cannot survive a round-trip across versions.

### AUTHZ-03: Aliyun AccessKeySecret briefly world-readable — chmod applied after file write in `_save_aliyun_ddns_config`

**Summary:**
- **Severity:** Medium
- **Confidence:** Medium
- **OWASP:** A02:2025 — Security Misconfiguration
- **Vulnerable location:** POST /api/aliyun_ddns/setup (aliyun_ddns_setup) and POST /api/aliyun_ddns/save (aliyun_ddns_save) — both call _save_aliyun_ddns_config at backend/app.py:2638 / :2964 (backend/app.py:2638 `with open(ALIYUN_DDNS_CONFIG_PATH, 'w') as f:` followed by `json.dump(config, f, ...)` and only then `os.chmod(ALIYUN_DDNS_CONFIG_PATH, 0o600)` at line 2641)

**Overview:**
The DDNS credential writer creates the destination file via `open(path, 'w')` under the process umask (typically `0o022`, yielding world-readable `0o644`) and tightens the mode to `0o600` only after the `with` block closes. No `os.umask(0o077)` is set before the `open`, and the file is not written with `os.open(O_CREAT|O_WRONLY|O_TRUNC, 0o600)` or via a temp-file-then-rename pattern. The eventual mode is `0o600`, but the file passes through a brief window at the default umask.

**Impact:**
Any local process or shell user on the router — root daemons, cron jobs, init scripts, or an unprivileged user running a tight-loop reader or `inotify` watcher — can capture the plaintext `AccessKeySecret` from the filesystem during the gap between file creation and the post-write chmod. A leaked `AccessKeySecret` enables full RAM-authorized API calls against the victim's Aliyun account (DNS hijack plus any other action the RAM role permits).

**Remediation:**
Write the file with `os.open(ALIYUN_DDNS_CONFIG_PATH, os.O_CREAT | os.O_WRONLY | os.O_TRUNC, 0o600)` followed by `os.fdopen` and `json.dump`, or set `os.umask(0o077)` for the duration of the write. Apply the chmod atomically with creation (`os.fchmod` on the open descriptor) rather than after `close`. For defense in depth, write to a sibling temp file and `os.rename` into place once the chmod has been applied, so the final destination never appears in a non-`0o600` mode.

### AUTHZ-06: /auth/login CSRF check fails open when both Origin and Referer headers are missing

**Summary:**
- **Severity:** Medium
- **Confidence:** High
- **OWASP:** A01:2025 — Broken Access Control
- **Vulnerable location:** POST /auth/login (backend/auth_gateway.py:627-643 — CSRF gate in auth_login)

**Overview:**
The CSRF check has three reject branches (Origin `null`, Origin host mismatch, Referer host mismatch when Origin is empty) but no reject branch for the case where both Origin and Referer are absent. In that case the function falls through to the rate-limit + password-verify path. The `_origin_host_mismatch` helper additionally returns `False` (treated as same-origin) when `urlparse` produces an empty netloc, which applies to `data:`, `file:`, `javascript:`, and `about:` URLs, and the host comparison strips the port on both sides so different ports on the same hostname pass.

**Impact:**
An external attacker can submit login attempts without triggering the CSRF block, including from non-browser clients (curl, scripts) and from cross-origin contexts that issue requests without `Origin` or `Referer` (server-side requests, `fetch` with `mode: no-cors`). The per-IP rate-limit (5 failures per 5-minute window, escalating to a 15-minute lockout) remains the only friction, and because nginx's `$remote_addr` override of `X-Real-IP` correctly keys the bucket on the real client, distributed brute force at up to 4 attempts per IP per 5 minutes is achievable with a residential-proxy or VPN-rotation botnet against the single hardcoded `kirito` account.

**Remediation:**
Add an explicit reject branch for the case where both `Origin` and `Referer` are missing on `/auth/login`, returning 403. Treat an empty `urlparse` netloc as a mismatch in `_origin_host_mismatch` (do not collapse it to same-origin), and include the port in the host comparison instead of stripping it on both sides. Layer the CSRF gate with per-account and global throttling so IP diversity does not translate into brute-force throughput.

### AUTHZ-04: POST /auth/logout has no authentication, no CSRF check, no rate limit

**Summary:**
- **Severity:** Low
- **Confidence:** High
- **OWASP:** A01:2025 — Broken Access Control
- **Vulnerable location:** POST /auth/logout (backend/auth_gateway.py:682-690 handler)

**Overview:**
The `/auth/logout` handler is reachable without authentication, accepts cross-site requests because there is no Origin/Referer CSRF check, and never calls `_is_locked` or `_mutate_ratelimit`. The same `gw_token` cookie is read only to extract a `jti` for revocation when a valid cookie is supplied; the same `_SYSLOG_EVENTS` allowlist routes the audit line through `/usr/bin/logger` to local syslog, which is then forwarded to remote syslog by syslogd.

**Impact:**
When a valid `gw_token` is presented, the server-side `jti` is added to the revocation list (persistent on disk under `fcntl.flock`). Every call writes one JSONL line to `/var/log/nftables-web-auth.log` and spawns `/usr/bin/logger` to forward to local syslog (which is forwarded remotely by syslogd). Because the audit log file mode is not enforced by the auth-gateway process (only the writer in `app.py` enforces `0o600`), the JSONL log typically sits world-readable, so the per-call audit line is observable on the box. The combination gives external attackers an unbounded observability and audit-log flooding surface against the gateway process and the log forwarding infrastructure.

**Remediation:**
Require a valid `gw_token` (or a synchronous CSRF token + Origin/Referer host check) on `/auth/logout`, and gate the handler behind `_is_locked` plus `_mutate_ratelimit` so the per-IP lockout applies. Set `os.umask(0o077)` (or explicitly `chmod 0o600`) on `/var/log/nftables-web-auth.log` at writer startup so the audit log is not world-readable between writes. Remove the `/auth/logout` event from the syslog-forwarding allowlist or sample it.

# Miscellaneous Findings

## Identified Vulnerabilities

### MISC-01: /api/auth/change-password does not revoke outstanding gateway JWTs

**Summary:**
- **Severity:** High
- **Confidence:** High
- **OWASP:** A07:2025 — Authentication Failures
- **Vulnerable location:** POST /api/auth/change-password (panel) combined with gateway-issued gw_token cookie on all protected services. Code: backend/app.py:5739-5782 (auth_change_password), backend/auth_gateway.py:600/745/265/296 (JWT verification, revocation list)

**Overview:**
`auth_change_password` updates the on-disk password hash and clears the panel-side Flask session, but the gateway process owns a separate revocation list that the panel cannot reach. There is no shared file write, IPC, or secret rotation by which the panel signals the gateway to revoke outstanding JWTs at password-change time; the gateway revocation list is populated only by `/auth/logout` and by the sliding-window refresh path. New `gw_token` cookies are bound to `TOKEN_TTL_DEFAULT` (up to 86,400 seconds) and are accepted for the full TTL.

**Impact:**
An attacker who has obtained a `gw_token` (via phishing, malware post-exploit, leaked browser profile, or proxy log) and is now feared compromised continues to access every reverse-proxy-protected service for up to 24 hours after the legitimate user rotates the password, defeating the primary purpose of credential rotation. Because the gateway and the panel are separate processes with no revocation handshake, password rotation gives the operator a false sense that prior sessions are dead while they remain valid for the full token TTL.

**Remediation:**
On password change, populate the gateway revocation list with the `jti` of every currently outstanding `gw_token` (write a shared `/etc/nftables/nftables-web-auth-revoke-on-rotate.json` that the gateway polls, or call a loopback HTTP endpoint exposed by the gateway that accepts a list of `jti`s to revoke). Reduce `TOKEN_TTL_DEFAULT` to a value that limits the residual risk window, and emit an audit event tying the rotation to its revocation batch.

### MISC-02: Revocation table fail-open in `load_revoked` — read/parse error returns `{}`, no shared lock with `revoke_jti` (TOCTOU window)

**Summary:**
- **Severity:** High
- **Confidence:** High
- **OWASP:** A07:2025 — Authentication Failures
- **Vulnerable location:** GET /auth/verify, /auth/status, /auth/portal (and every nginx auth_request-gated service). Code: backend/auth_gateway.py:256-262 (load_revoked fail-open), 296-301 (is_revoked), 600/718/802 (call sites)

**Overview:**
`load_revoked` catches `OSError` and `json.JSONDecodeError` and returns `{}`, which causes `is_revoked` to return `False` for every `jti` at the three security-critical call sites: `/auth/verify` (line 718), `/auth/status` (line 600), and `/auth/portal` via `_authenticated` (line 802). `load_revoked` also does not acquire the `fcntl` lock that `revoke_jti` holds, producing a TOCTOU window between the seek/truncate and `json.dump` inside `revoke_jti`.

**Impact:**
An attacker who has previously obtained a `gw_token` and watched the victim revoke it via `/auth/logout`, sliding refresh, or admin action can re-enable the revoked token by inducing any state where the revocation file is unreadable, mid-write, or partial — for example by deleting the file, removing read permission, filling the disk, racing `revoke_jti`'s truncate, or delivering a write that produces half-written JSON. In that state every `jti` lookup returns `False`, the revoked token is treated as fresh, and the attacker reaches the upstream service. This is the worst case for revocation, because the explicit security control is silently disabled by an induced file-system condition.

**Remediation:**
Fail closed inside `load_revoked`: on `OSError` or `json.JSONDecodeError`, deny by returning a sentinel that makes `is_revoked` accept any `jti` (or raise up so `_verify_or_deny` returns 401). Have `load_revoked` acquire the same `fcntl.LOCK_SH` (or `LOCK_EX`) that `revoke_jti` holds for write so the read cannot interleave with the truncate-and-dump window. Replace the open-seek-truncate-dump pattern with a write-temp-then-rename so the file is always either the old complete contents or the new complete contents, never a partial JSON document.

### MISC-04: GET /api/reverse-proxy/certificates/<id>/download has no re-authentication — single GET exfiltrates every managed TLS private key

**Summary:**
- **Severity:** High
- **Confidence:** Medium
- **OWASP:** A01:2025 — Broken Access Control
- **Vulnerable location:** GET /api/reverse-proxy/certificates/<id>/download (backend/app.py:5329 rp_download_cert, auth gate at backend/app.py:194)

**Overview:**
The certificate download handler serves the fullchain plus the private key from a single GET request, gated only by the `nftables_web_session` cookie check at `before_request` (line 194). There is no re-authentication step (password, TOTP, WebAuthn, or signed per-action token), no per-action confirmation, and the access log line is indistinguishable from ordinary authenticated GETs.

**Impact:**
An attacker who obtains or replays any valid `nftables_web_session` cookie — for example via XSS in the SPA, malware on a previously-authenticated device, or a leaked browser profile — can issue one GET per certificate to exfiltrate every TLS private key the panel manages. Once the keys are exported, the attacker can MITM every future TLS connection to the configured domains using the legitimate certificates. There is no audit signal that distinguishes the export action from ordinary reads.

**Remediation:**
Require a per-action confirmation step before serving the private key (re-entry of the panel password, a TOTP/WebAuthn assertion, or a signed per-action token). Add a dedicated audit-log entry that records the export, the requesting identity, the certificate id, the source IP, and a hash of the key payload. Apply per-IP and per-account throttling on the download endpoint so a single compromised cookie cannot be replayed at high throughput.

### MISC-03: PUT /api/reverse-proxy/rules/<id> skips `validate_config` and `_is_port`/protocol-whitelist checks on `listen_port` and `target_protocol`

**Summary:**
- **Severity:** Medium
- **Confidence:** Medium
- **OWASP:** A06:2025 — Insecure Design
- **Vulnerable location:** PUT /api/reverse-proxy/rules/<id> (backend/app.py:5083 rp_update_rule, update field list at 5097, nginx generation at 4115/4148, deploy at 5127)

**Overview:**
The PUT handler does not invoke `validate_config` on the resulting rule and does not enforce the `_is_port` numeric range or the `target_protocol` whitelist on `listen_port` and `target_protocol`. Only the create-route path (`rp_create_rule`) carries these checks. The update path can therefore persist a rule whose values are non-numeric or otherwise out of range.

**Impact:**
An authenticated admin can persist reverse-proxy rules with non-numeric `listen_port` values or arbitrary `target_protocol` strings that flow raw into nginx config generation. Because the resulting rule fails nginx `-t` validation, the deploy pipeline halts, leaving the panel in a deploy-blocked state that prevents new rules from being applied until the bad rule is repaired. The bad value also persists on disk across reboots, accumulating malformed configuration in the nginx conf directory.

**Remediation:**
Run `validate_config` on the merged rule (or call `_is_port` and the `target_protocol` whitelist) inside `rp_update_rule` before persistence, and reject (with a 400 response) any rule whose `listen_port` is not an integer in the valid range or whose `target_protocol` is not in the whitelist. Centralize the validation in a single helper shared between `rp_create_rule` and `rp_update_rule` so the create/update parity cannot drift again.

### MISC-05: _deploy_gateway_nginx._undo and _deploy_all_rules._rollback rmtree the backup directory before it is consumed by the copytree that restores it

**Summary:**
- **Severity:** Medium
- **Confidence:** Medium
- **OWASP:** A10:2025 — Mishandling of Exceptional Conditions
- **Vulnerable location:** POST /api/gateway/config, POST/PUT/DELETE /api/reverse-proxy/rules, POST /api/reverse-proxy/certificates/upload, PUT /api/reverse-proxy/settings, POST /api/reverse-proxy/certificates/{id}/set-default. Code: backend/app.py:4555-4571 (_deploy_gateway_nginx._undo), backend/app.py:4789-4796 (_deploy_all_rules._rollback)

**Overview:**
Both rollback closures contain the same ordering bug: `shutil.rmtree(backup_dir, ignore_errors=True)` runs unconditionally before the `if not have_backup:` check and before `shutil.copytree(backup_dir, NGINX_CONF_DIR)`. The backup snapshot taken at line 4555 is destroyed before it can be used for restore. The docstring advertises atomic rollback to the previous working state, but the implementation removes the source of the restore.

**Impact:**
When an authenticated admin triggers any change that `nginx -t` rejects (a typo, a port collision with a forgotten site, a `client_max_body_size` outside nginx's accepted range, or a planted bad `.conf` file in `NGINX_CONF_DIR`), the rollback path runs, removes `NGINX_CONF_DIR`, removes `backup_dir`, and then returns a "rollback also failed" error with `conf.d` empty. The actual safety net advertised by the code is non-functional, and the failure mode is a full denial of service on the nginx front door with no working recovery path.

**Remediation:**
Reorder the rollback so the `copytree` from `backup_dir` to `NGINX_CONF_DIR` completes before the backup directory is removed, or guard the `rmtree` call behind the `if not have_backup` check. Verify on deploy that the rollback actually restores the prior `conf.d` contents (e.g., a smoke test that re-runs `nginx -t` after the rollback returns success) so the non-functional safety net is caught in CI rather than at runtime.

### MISC-06: _aliyun_api does not inspect Aliyun error `Code` field — DDNS setup/test report success on invalid credentials

**Summary:**
- **Severity:** Low
- **Confidence:** Low
- **OWASP:** A10:2025 — Mishandling of Exceptional Conditions
- **Vulnerable location:** POST /api/aliyun-ddns/setup and POST /api/aliyun-ddns/test. Code: backend/app.py:2777-2792 (_aliyun_api), backend/app.py:2864-2882 (aliyun_ddns_setup), backend/app.py:2795 (_aliyun_ddns_update)

**Overview:**
`_aliyun_api` parses the JSON body and returns it without inspecting the Aliyun error `Code` field (e.g., `InvalidParameter`, `Forbidden.RAM`, `Throttling.User`). `aliyun_ddns_setup` calls `_aliyun_api("DescribeDomains")` inside a broad `try/except Exception` and treats any non-exception return as success. The Aliyun RPC API returns HTTP 200 with body `{"Code": "<error>", ...}` for credential or permission failures; that body is returned but not raised, and the bad AK/SK is silently persisted by `_save_aliyun_ddns_config`.

**Impact:**
An attacker with panel admin access who misconfigures (or deliberately submits broken) Aliyun credentials obtains a success confirmation while DNS updates silently never run. In a rotation scenario, working credentials can be silently overwritten with broken ones, breaking DDNS for the operator with no recorded signal. No direct security boundary is crossed — the defect is operational — but silent failure of the only DNS-update path on the host is a security-relevant reliability problem because defensive DNS-based controls can be silently disabled.

**Remediation:**
Inspect the parsed JSON body for a non-empty `Code` field (or non-`OK` value) inside `_aliyun_api` and raise a typed exception when Aliyun signals an error. Have `aliyun_ddns_setup`, `_aliyun_ddns_update`, and `/api/aliyun-ddns/test` propagate that exception to the caller (with a 4xx response) rather than persisting the configuration or returning success. Add a recorded audit event when a credential validation fails so the operator can see the rotation did not take effect.

### MISC-07: set_logd_config missing `returncode` check on `uci commit system` subprocess

**Summary:**
- **Severity:** Low
- **Confidence:** Low
- **OWASP:** A09:2025 — Security Logging and Alerting Failures
- **Vulnerable location:** POST /api/system/logd (or whichever endpoint invokes set_logd_config). Code: backend/app.py:3307 (set_logd_config), backend/app.py:3393 (subprocess.run call), backend/app.py:3395 (restart), backend/app.py:3397 (return)

**Overview:**
`set_logd_config` calls `subprocess.run(["uci", "commit", "system"], timeout=10, check=False)` without inspecting the returned `returncode`, then conditionally runs `/etc/init.d/log restart` whenever `fwd_changed` or `size_changed`, and returns `{"success": true}` to the operator regardless of the commit outcome. Compare `save_ddns_config`, which does capture the returncode.

**Impact:**
An operator or attacker who can induce a `uci commit` failure (via disk-fill, lock contention, or filesystem permission change) causes the on-disk UCI state to retain its previous values while the in-memory logd process is restarted against the new state and the UI reports success. The security-relevant consequence is audit/forensic drift on the log forwarding destination and size: a SOC that relies on the configured forwarding target for detection sees continued flow to the old destination (or no flow at all) without any operator-visible signal of the drift, masking compromise activity.

**Remediation:**
Capture the `CompletedProcess.returncode` from `subprocess.run(["uci", "commit", "system"], ...)` and treat a non-zero status as a failure: do not restart `/etc/init.d/log`, return an explicit error response, and emit an audit event. Apply the same fix to any sibling `subprocess.run` invocations that use `check=False` without inspecting the returncode, and centralize the pattern in a helper that enforces returncode inspection.
