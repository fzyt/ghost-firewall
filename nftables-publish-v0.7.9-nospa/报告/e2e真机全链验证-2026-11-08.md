## 二、环境事实（跑之前先摸清的）

### 2.1 `.232` 的网络与防火墙

- 网卡只有 `lo` 与 `br-lan`（192.168.100.232/24），**没有 WAN 网卡**
- 但 `table inet fw4` 里满屏 `iifname "pppoe-wan"` —— **全是死规则**，
  这套规则集是从有 PPPoE 的机器搬过来的
- `chain input { policy drop; }`，LAN 侧靠 `chain input_lan` 里最后一条
  `meta nfproto ipv4 accept` 放行 ⇒ SSH 22 通**不是**因为 `@tcp_services` 集合
  （那三个集合 `tcp_services` / `allowed4` / `allowed6` 当前全是空的）
- **重要**：Ghost Firewall 自己管的表就是 `table inet fw4`，而
  `build_rules` 生成的规则集**以 `flush ruleset` 开头、完全接管规则表**
  ⇒ 「应用防火墙规则」会整表替换 fw4

### 2.2 风险评估（点 destructive 之前做的）

| 风险 | 结论 |
|---|---|
| `applyRules()` flush 掉 fw4 导致 SSH 断 | 生成的规则含 `iifname $LAN_IF tcp dport { 22, 5443 } accept`（`lan_allowed_ports=[22,5443]`）；且回滚链完整：`99-custom-rules.nft.lastgood` 与主文件 md5 一致（`7ebe493c…`）→ 再失败退 `_apply_basic_lockdown()`（注释明写「不放行的话兜底规则一执行就没法远程自救」）→ 再失败 init 看门狗自愈 |
| 删掉 `.232` 的真实反代规则 | 配置已定点备份到 `/root/nft-cfg-20261108-013252/` |
| 名单被清空 | `.232` 上名单文件压根不存在，无物可清 |
| DDNS 服务被删 | `.232` 没配 DDNS 服务（`.224` 才有） |

备份内容：`nftables-web-config.json`、nginx conf、init 脚本、`ruleset.before.txt`（258 行）。

## 四、挖出来的问题

### A1（产品 · 安全）`/api/config/restore` 回退 `auth_token_epoch`

**现象（`.232` 真机实测）**

1. 面板点「恢复配置」
2. 落盘配置里 `auth_token_epoch` 从 **1** 变成 **0**
3. 紧接着 `GET /api/config` 返回 **401**
4. 面板上所有操作按钮变成 **disabled**（用户被硬踢下线，而 `restoreConfig()` 只弹一句「配置已恢复」）
5. 更严重的一侧：世代号调小 = **撤销「改密码作废全部会话」的保证** ——
   改密码之前签发的旧令牌会重新生效

**根因**

`restore_config` 原来是 `shutil.copy(backup, tmp)` + `os.replace` **整份覆盖**，
绕过了 app.py 里 READONLY 名单对 `auth_token_epoch` 的保护。那个名单的注释
写得很清楚（「它**只能**由改密码路径写」），但 restore 路径根本不走字段白名单。

**修复**

恢复时**继承当前配置的世代号**，只恢复其余字段：

```python
current_epoch = _current_token_epoch()
restored = json.load(open(backup_path))
if not isinstance(restored, dict):
    raise ValueError('备份文件内容不是配置对象')
restored['auth_token_epoch'] = current_epoch
```

「恢复配置」恢复的是防火墙配置，不是安全状态 —— 世代号只该由改密码路径递增。

### B1（测试器 · 安全）两条分档正则漏了 11 个动作

`tests/e2e_buttons.js` 的 `NETWORK_PAT` / `DESTRUCTIVE_PAT` 原来
**中文标签 + 少量英文动作名**混着写，凡是英文动作名和中文标签对不上就漏网。
两条正则合计补了 **11 个动作**：`DESTRUCTIVE_PAT` 补 8 个、`NETWORK_PAT` 补 3 个。

**实测真执行了的 4 个**（设备日志逐条对上，发生在**非破坏性**的 click 档）：

| 动作 | 运行时标签 | 实际请求 | 本该归 |
|---|---|---|---|
| `saveNetworkConfig()` | 保存网络配置 | `POST /api/network/config` 400 | 网络级 |
| `installIpv6Cron()` | 安装定时更新 | `POST /api/network/install-ipv6-cron` 200 | 网络级 |
| `restartDdns()` | 重启服务 | `POST /api/ddns/restart` 200 | 破坏性级 |
| `reloadNginx()` | 重载 Nginx | `POST /api/reverse-proxy/nginx/reload` 200 | 破坏性级 |

⇒ **两档防线各漏了两个**：网络级漏 2 个、破坏性级漏 2 个。

**静态核对又挖出 7 个**（运行时不可见，但按钮所在 tab 一激活就会漏）：

| 动作 | 运行时标签 | 说明 |
|---|---|---|
| `uploadRpCert()` | 上传证书 | 弹文件选择器 ⇒ 浏览器里会卡住脚本 |
| `pickRpReupload()` | 重新上传 | 弹文件选择器，和 `uploadRpCert` 一个毛病 |
| `requestRpCert()` | 申请证书 | 要打 ACME 外网 |
| `renewRpCert()` | 续期证书 | 同上 |
| `confirmSaveConfig()` | 确认保存 | 真正落盘配置并应用防火墙规则（见 B2） |
| `applyPreset()` | 应用预设 | 按预设改名单/规则 |
| `updateChinaIps()` | 立即刷新中国IP | 和 `installChinaIps()` 是两个不同动作，原来只护了后者 |

**根因：注释与代码不一致。** 脚本自己的注释写着 2026-10-06 那次把 `.224`
搞到整机失联的事故元凶是「`togglePppoe()` / `saveNetworkConfig()` / `restartNetwork()`」
三，**但保护里只有两个** —— `saveNetworkConfig` 从来没进过 `NETWORK_PAT`。
（在 `.232` 上因为没有 PPPoE 账号，后端按设计 400 拒了保存，没造成后果；
但 `.224` 那样的真机上，这一发就是真的把网络配置写下去。）

**修复**：动作名 + 中文标签都写全；并加两条自动断言：

- **注释与代码必须一致** —— 注释里提到、且在 `index.html` 里真实存在的动作，
  必须被某条正则覆盖（口径限定在真实动作上，`nth()`/`confirm()` 这类不算）
- **`EXPECT` 表不能漏项** —— 界面每加一个按钮，都必须被审视一次

### B2（测试器 · 盲区）保存配置的完整链路从未被测过

设备日志：`POST /api/config` 计数 = **0**（click 档点了 7 次「保存配置」）。

**原因**：`saveConfig()` 走的是**两步流程** —— 先 `POST /api/rules/preview-changes`
（日志里 7 次）弹差异确认，用户点「确认保存」才真正落盘。而测试器的
`dismissModals()` 每次点击后都会把 `diffModal` 关掉 ⇒ 预览弹窗从未被确认。

**而且是结构性盲区**：真正落盘的那颗按钮 `confirmSaveConfig()` 属于静态清单里的
`default` 页，而 e2e 的 14 页 `NAV_ITEMS` **压根不含 default 页**。
运行时核对：`confirmSaveConfig` / `applyPreset` / `savePreset` / `cancelSaveConfig`
在 14 页里**都不可见**。

⇒ **「保存配置 → 落盘 → 应用防火墙规则」这条最关键的链路，e2e 从来没测过。**

### B3（测试器 · 归因）「按设计拒绝」的归因窗口过宽

click 档有 6 个 `reject-by-design`，其中 4 个是 DDNS 页的
`[service.enabled = !service.enabled; saveDdns()]` —— 它们被算成
「后端按设计拒绝（wan-ipv6 404）」，但那个 404 是**页面级**请求，
落在该按钮的 700ms 归因窗口里，不是这个按钮引起的。

### B4（工具 · 覆盖）静态按钮清单漏了 `intro` 页

`tests/button_audit.py` 抽出 206 个元素、13 个页面；运行时是 351 个元素、14 个页面。
差在两头：

- 静态**漏**了 `intro` 页（运行时 18 个元素）
- 静态**多**算了 `reverse-proxy`（57 vs 40）—— 把未渲染的隐藏表单也算进去了

⇒ 两个口径不可直接对账；「静态 ∩ 运行时」才算测全这句话，在这套工具下不成立。

### B5（测试器 · 盲区）变异锚点与源码脱节 ⇒ 变异被静默跳过，却照样计入总数

修 A1 时顺手改了 `restore_config` 的实现（`shutil.copy` → 读 JSON / 改世代号 / 写 tmp），
`tests/mutation_check_secret_perms.py` 的 **M10** 锚点钉的还是旧实现的
「`_ensure_file_mode` 紧跟 `shutil.copy(backup_path, tmp_path)`」两行 ⇒ **锚点失配**。

后果：那条变异**根本没跑**，但脚本的自报数里它仍然占一个名额。
只看「捕获 N / N」会把一个覆盖漏洞误读成「全捕获」。

⇒ 这次是靠**全仓扫描器把「锚点未命中」单独列成一列并当失败处理**才抓出来的，
不是靠退出码（退出码当时仍是 0）。这条纪律已经写进 AGENTS.md：**还原提示 ≠ 跳过**、
**锚点未命中必须当失败**。

修法：把 M10 锚点挪到 restore 路径独有的 `restored['auth_token_epoch'] = current_epoch`
那一处（与 `save_config` 的同形代码区分开），并把它改成「去掉 `_ensure_file_mode`
⇒ `open(tmp_path,'w')` 按 umask 建出 0644」—— 这个退化在 A1 修完之后**依然真实存在**
（`os.chmod` 是事后补的，落盘那一刻确实有可读窗口），所以这条变异保留了价值。

### B6（自己的修复里）改实现没改注释 ⇒ 注释与代码漂移

修 A1 时把 `restore_config` 的实现从 `shutil.copy` 换成「读 JSON → 改世代号 → 写 tmp」，
但**周围的注释还在描述 `shutil.copy`**：

- 「先写临时文件再 replace：shutil.copy 是『边读边写』直接落到 CONFIG_PATH」—— 代码里早没有 shutil.copy 了
- 「shutil.copy 会先按 umask 建文件（默认 0644）拷完才 copystat ⇒ 有窗口」—— 同上

⇒ **这正是 B1 那一类病根（注释与代码不一致）在我自己的修复里复现**。

还有一个约束要注意：M10 变异锚点正好覆盖 `_ensure_file_mode` 上面那三行注释
（见 B5），**一改锚点就失配、变异被静默跳过** ⇒ 修注释前得先确认没有变异锚点钉在上面。

⇒ 两条教训：① 改实现和改注释要**同一批**做；② 改注释前先确认没有变异锚点钉在它上面。

### 9.1 先回答「跑下去会不会失联」

`.232` 没有 WAN 网卡、没有串口/IPMI，**唯一的连接方式就是 LAN 这根网线**。
而 `applyRules` 生成的规则集以 `flush ruleset` 开头、完全接管规则表 ——
如果生成的规则没放行 LAN 侧的 SSH 22 和面板 5443，flush 之后就再也连不上了。

所以先做了一个**纯本地**的预检（不碰设备）：用项目自己的 `build_rules()`
按 `.232` 那份配置生成规则集（592 行，`deploy_mode=openwrt` 接管整机），然后逐条查：

| 检查项 | 结果 |
|---|---|
| `input` 链跳到 LAN 链 | `iifname $LAN_IF jump input_lan` ✓ |
| LAN 链放行管理端口 | `iifname $LAN_IF tcp dport { 22, 5443 } accept` ✓ |
| 放行排在丢弃规则之前 | 在 `meta nfproto ipv4 drop` 之前 ✓ |
| `define LAN_IF` 与设备网卡名一致 | `br-lan` = `.232` 的网卡名 ✓ |

⇒ **destructive 档跑在 `.232` 上不会切断 SSH 与面板**。安全前提已验证，不是「应该没问题」。

这个预检固化成了项目里的工具（不是一次性脚本）：

- `tests/precheck_generated_rules.py` —— 安全闸，退出码 0 = 可以跑破坏性档，1 = 不要跑，2 = 出错

### 10.3 唯一没修好的一条：#60 IPv6 scope-id

子代理最初判成「nft 命令注入」，**我复核后推翻了**：

- **注入不成立**：nft 1.1.7 隔离 netns 实测，`elements = { fe80::1%eth0 }` 报
  `syntax error, unexpected junk`（指针在 `%` 后）—— 连**合法**的 scope-id nft 都不认；
  试图用 `;` 断链的构造同样报语法错误。
- **文件加载路径也测了**（面板生成的是规则集文件，用 `nft -f` 加载，不是命令行）：
  `elements = { fd00::1%; flush ruleset; # }` 加载失败（返回码非 0），
  **表未被删除、内容未被改** ⇒ `flush ruleset` 没有被执行 ⇒ **不构成注入**。

  ⚠️ 这条实测我第一版写错了：建表时用了 `elements = { }`（空集合），
  那是**非法语法**，表压根没建起来，于是「查表还在不在」必然查不到，
  误判成「flush ruleset 被执行了 ⇒ 构成注入」。改成合法的非空集合、
  并在注入测试**之前**先确认基线表存在，才得到上面的结论。
  ⇒ **「注入测试的基线本身」也是需要先验证的东西**。

- **真实风险低一档**：三处校验（`_valid_ip` / `_format_list_elements` / `_inject_list_elements`）
  都用宽松的 `ipaddress.ip_address()`，Python 3.9+ 的它**接受** scope-id
  （实测 `fe80::1%eth0`、`fe80::1%;drop` 都放行，且 `str()` 原样保留）
  ⇒ scope-id 会被原样写进规则集文件的 `elements = {...}` 行
  ⇒ nft -f 语法错误 ⇒ **apply 或开机加载失败**。
- **正常 API 路径进不去**：`list_add` 先调 `_detect_ip_version(ip)`（app.py:7057）
  校验，走的是同一套宽松 `ipaddress` ⇒ **放行**；但下一步
  `_nft_set_write(['add','element',...])` 会先被内核拒（returncode≠0 ⇒ 不落盘）。
  也就是说**能写进 `lists.json` 但进不了内核** ⇒ 危险的是「配置文件被写脏」，
  而真正生效的仍是内核里的旧集合。
  要真的让脏数据进规则集文件，需 root 直接改 `lists.json`。

⇒ 这是「配置被写坏导致 apply 失败」，不是「攻击者能执行任意命令」。

### 10.5 C1：P0-10 的同型漏网，已修

**这是 53 条对账挖出来的唯一真实缺陷。**

P0-10（2026-10-29）修了 crontab 读失败 fail-closed，但只修了三处 crontab 写点里的**两处**
（`_upsert_cron_for()` 与 `install_china_ips()`），**漏了 `_manage_ddns_cron()`**。

漏修的原因有个很实用的线索：**三处里只有它用双引号写 `["crontab", "-l"]`**，
另外两处是单引号 `['crontab', '-l']` 且带 returncode 检查 —— 引号风格的差异正好标出了它。

原代码：

```python
result = subprocess.run(["crontab", "-l"], ...)
current_crontab = result.stdout if result.returncode == 0 else ""
```

读失败被当成「crontab 本来就是空的」，于是后面的 `crontab -` 拿「只有 DDNS 那一条」
覆盖整个 root crontab —— `/etc/init.d/acme renew` 与 `/opt/nftables-web/renew-certs.sh`
双双被抹，而接口照样返回「配置已保存」。

触发条件是**运维故障**（spool 被删/损坏、磁盘异常、crontab 被 shadow），
不需要攻击者参与，也不会有任何人察觉。

**修复**：改成与既有两处完全一致的 fail-closed —— 读失败直接返回 `(False, msg)`、
**不写 crontab**，并提示「若本机确实一条 cron 都没有，请先手工 `crontab -` 建一条」。

**配套测试**（新增 `tests/test_crontab_fail_closed.py`，**30 项**）：

- **第 1 组（源码不变式）**：先扫源码找出所有读 crontab 的函数，
  对**每一个**断言「读点与写点之间有 returncode 闸门」「闸门真的 return 中止」
  「闸门在写回点之前」。⇒ 将来加第四个 crontab 写入口、忘了带闸门，本文件直接红。
- **第 2 组（行为级）**：读失败有**三种形态**（返回码非 0 / 抛 FileNotFoundError /
  抛 TimeoutExpired），每种都要「明确的失败返回」且**绝不执行 `crontab -`**；
  外加「写回失败必须报错，不能报『已更新』」。
- **第 3 组（正常路径）**：正常读取时保留 `renew-certs.sh` / `acme renew`，
  DDNS 条目只有一条不重复。

**配套变异**（新增 `tests/mutation_check_crontab_fail_closed.py`，**9 条全捕获**）：
摘掉三处闸门各一条、读失败当成空表两条、闸门挪到写回之后、写回失败不上报、
闸门只 return 不带失败语义、闸门缩到只拦一种异常。

### 10.6 写测试时，测试自己露了两个缺陷

跟安全闸那次一样 —— **是靠造坏输入逼出来的，不是靠读代码**：

1. **行为级只测了「返回码非 0」，没测「抛异常」**。
   而本次修复新增的 `except` 闸门正是管抛异常的 ⇒ 那条分支原本**完全没有行为级覆盖**。
   补上三种失败形态后，M3/M8/M9 三条变异才抓得住。
2. **静态断言用「有没有 return」当判据太松**。
   `except` 分支那句 `return False` 一直都在，
   于是「把 returncode 闸门挪到写回之后」这种退化照样能过。
   改成找 **`result.returncode != 0` 这个条件的位置**、要求它落在写回点之前，
   才把 M6 抓住。

⇒ 首版变异脚本 M6 **漏网**（我自己写的变异写错了：闸门插在 `new_crontab` 之前，
仍在写回之前，等价于 M1）。改成真正「先覆盖再检查」后才捕获。

⇒ 每条变异都被**对应层级的断言**抓住（逐条核对过捕获来源，没有靠巧合蒙对）。
