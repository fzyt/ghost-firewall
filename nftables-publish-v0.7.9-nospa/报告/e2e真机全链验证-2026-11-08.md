## 二、环境事实（跑之前先摸清的）

### 2.1 `.232` 的网络与防火墙

- 网卡只有 `lo` 与 `br-lan`（192.168.100.232/24），**没有 WAN 网卡**
- 但 `table inet fw4` 里满屏 `iifname "pppoe-wan"` —— **全是死规则**，
  这套规则集是从有 PPPoE 的机器搬过来的
- `chain input { policy drop; }`，LAN 侧靠 `chain input_lan` 里最后一条
  `meta nfproto ipv4 accept` 放行 ⇒ SSH 22 通**不是**因为 `@tcp_services` 集合
  （那三个集合 `tcp_services` / `allowed4` / `allowed6` 当前全是空的）
- **重要**：Ghost Firewall 自己管的表就是 `table inet fw4`，而
  `build_rules` 生成的规则集**以 `flush ruleset` 开头、完全接管规则表**
  ⇒ 「应用防火墙规则」会整表替换 fw4

### 2.2 风险评估（点 destructive 之前做的）

| 风险 | 结论 |
|---|---|
| `applyRules()` flush 掉 fw4 导致 SSH 断 | 生成的规则含 `iifname $LAN_IF tcp dport { 22, 5443 } accept`（`lan_allowed_ports=[22,5443]`）；且回滚链完整：`99-custom-rules.nft.lastgood` 与主文件 md5 一致（`7ebe493c…`）→ 再失败退 `_apply_basic_lockdown()`（注释明写「不放行的话兜底规则一执行就没法远程自救」）→ 再失败 init 看门狗自愈 |
| 删掉 `.232` 的真实反代规则 | 配置已定点备份到 `/root/nft-cfg-20261108-013252/` |
| 名单被清空 | `.232` 上名单文件压根不存在，无物可清 |
| DDNS 服务被删 | `.232` 没配 DDNS 服务（`.224` 才有） |

备份内容：`nftables-web-config.json`、nginx conf、init 脚本、`ruleset.before.txt`（258 行）。

## 四、挖出来的问题

### A1（产品 · 安全）`/api/config/restore` 回退 `auth_token_epoch`

**现象（`.232` 真机实测）**

1. 面板点「恢复配置」
2. 落盘配置里 `auth_token_epoch` 从 **1** 变成 **0**
3. 紧接着 `GET /api/config` 返回 **401**
4. 面板上所有操作按钮变成 **disabled**（用户被硬踢下线，而 `restoreConfig()` 只弹一句「配置已恢复」）
5. 更严重的一侧：世代号调小 = **撤销「改密码作废全部会话」的保证** ——
   改密码之前签发的旧令牌会重新生效

**根因**

`restore_config` 原来是 `shutil.copy(backup, tmp)` + `os.replace` **整份覆盖**，
绕过了 app.py 里 READONLY 名单对 `auth_token_epoch` 的保护。那个名单的注释
写得很清楚（「它**只能**由改密码路径写」），但 restore 路径根本不走字段白名单。

**修复**

恢复时**继承当前配置的世代号**，只恢复其余字段：

```python
current_epoch = _current_token_epoch()
restored = json.load(open(backup_path))
if not isinstance(restored, dict):
    raise ValueError('备份文件内容不是配置对象')
restored['auth_token_epoch'] = current_epoch
```

「恢复配置」恢复的是防火墙配置，不是安全状态 —— 世代号只该由改密码路径递增。

### B1（测试器 · 安全）两条分档正则漏了 11 个动作

|---|---|---|

### B2（测试器 · 盲区）保存配置的完整链路从未被测过

设备日志：`POST /api/config` 计数 = **0**（click 档点了 7 次「保存配置」）。

**原因**：`saveConfig()` 走的是**两步流程** —— 先 `POST /api/rules/preview-changes`
（日志里 7 次）弹差异确认，用户点「确认保存」才真正落盘。而测试器的
`dismissModals()` 每次点击后都会把 `diffModal` 关掉 ⇒ 预览弹窗从未被确认。

**而且是结构性盲区**：真正落盘的那颗按钮 `confirmSaveConfig()` 属于静态清单里的
`default` 页，而 e2e 的 14 页 `NAV_ITEMS` **压根不含 default 页**。
运行时核对：`confirmSaveConfig` / `applyPreset` / `savePreset` / `cancelSaveConfig`
在 14 页里**都不可见**。

⇒ **「保存配置 → 落盘 → 应用防火墙规则」这条最关键的链路，e2e 从来没测过。**

### B3（测试器 · 归因）「按设计拒绝」的归因窗口过宽

click 档有 6 个 `reject-by-design`，其中 4 个是 DDNS 页的
`[service.enabled = !service.enabled; saveDdns()]` —— 它们被算成
「后端按设计拒绝（wan-ipv6 404）」，但那个 404 是**页面级**请求，
落在该按钮的 700ms 归因窗口里，不是这个按钮引起的。

### B4（工具 · 覆盖）静态按钮清单漏了 `intro` 页

`tests/button_audit.py` 抽出 206 个元素、13 个页面；运行时是 351 个元素、14 个页面。
差在两头：

- 静态**漏**了 `intro` 页（运行时 18 个元素）
- 静态**多**算了 `reverse-proxy`（57 vs 40）—— 把未渲染的隐藏表单也算进去了

⇒ 两个口径不可直接对账；「静态 ∩ 运行时」才算测全这句话，在这套工具下不成立。

### B5（测试器 · 盲区）变异锚点与源码脱节 ⇒ 变异被静默跳过，却照样计入总数

修 A1 时顺手改了 `restore_config` 的实现（`shutil.copy` → 读 JSON / 改世代号 / 写 tmp），
`tests/mutation_check_secret_perms.py` 的 **M10** 锚点钉的还是旧实现的
「`_ensure_file_mode` 紧跟 `shutil.copy(backup_path, tmp_path)`」两行 ⇒ **锚点失配**。

后果：那条变异**根本没跑**，但脚本的自报数里它仍然占一个名额。
只看「捕获 N / N」会把一个覆盖漏洞误读成「全捕获」。

⇒ 这次是靠**全仓扫描器把「锚点未命中」单独列成一列并当失败处理**才抓出来的，
不是靠退出码（退出码当时仍是 0）。这条纪律已经写进 AGENTS.md：**还原提示 ≠ 跳过**、
**锚点未命中必须当失败**。

修法：把 M10 锚点挪到 restore 路径独有的 `restored['auth_token_epoch'] = current_epoch`
那一处（与 `save_config` 的同形代码区分开），并把它改成「去掉 `_ensure_file_mode`
⇒ `open(tmp_path,'w')` 按 umask 建出 0644」—— 这个退化在 A1 修完之后**依然真实存在**
（`os.chmod` 是事后补的，落盘那一刻确实有可读窗口），所以这条变异保留了价值。

### B6（自己的修复里）改实现没改注释 ⇒ 注释与代码漂移

修 A1 时把 `restore_config` 的实现从 `shutil.copy` 换成「读 JSON → 改世代号 → 写 tmp」，
但**周围的注释还在描述 `shutil.copy`**：

- 「先写临时文件再 replace：shutil.copy 是『边读边写』直接落到 CONFIG_PATH」—— 代码里早没有 shutil.copy 了
- 「shutil.copy 会先按 umask 建文件（默认 0644）拷完才 copystat ⇒ 有窗口」—— 同上

⇒ **这正是 B1 那一类病根（注释与代码不一致）在我自己的修复里复现**。

还有一个约束要注意：M10 变异锚点正好覆盖 `_ensure_file_mode` 上面那三行注释
（见 B5），**一改锚点就失配、变异被静默跳过** ⇒ 修注释前得先确认没有变异锚点钉在上面。

⇒ 两条教训：① 改实现和改注释要**同一批**做；② 改注释前先确认没有变异锚点钉在它上面。

### 10.5 C1：P0-10 的同型漏网，已修

**这是 53 条对账挖出来的唯一真实缺陷。**

P0-10（2026-10-29）修了 crontab 读失败 fail-closed，但只修了三处 crontab 写点里的**两处**
（`_upsert_cron_for()` 与 `install_china_ips()`），**漏了 `_manage_ddns_cron()`**。

漏修的原因有个很实用的线索：**三处里只有它用双引号写 `["crontab", "-l"]`**，
另外两处是单引号 `['crontab', '-l']` 且带 returncode 检查 —— 引号风格的差异正好标出了它。

原代码：

```python
result = subprocess.run(["crontab", "-l"], ...)
current_crontab = result.stdout if result.returncode == 0 else ""
```

读失败被当成「crontab 本来就是空的」，于是后面的 `crontab -` 拿「只有 DDNS 那一条」
覆盖整个 root crontab —— `/etc/init.d/acme renew` 与 `/opt/nftables-web/renew-certs.sh`
双双被抹，而接口照样返回「配置已保存」。

触发条件是**运维故障**（spool 被删/损坏、磁盘异常、crontab 被 shadow），
不需要攻击者参与，也不会有任何人察觉。

**修复**：改成与既有两处完全一致的 fail-closed —— 读失败直接返回 `(False, msg)`、
**不写 crontab**，并提示「若本机确实一条 cron 都没有，请先手工 `crontab -` 建一条」。

**配套测试**（新增 `tests/test_crontab_fail_closed.py`，**30 项**）：

- **第 1 组（源码不变式）**：先扫源码找出所有读 crontab 的函数，
  对**每一个**断言「读点与写点之间有 returncode 闸门」「闸门真的 return 中止」
  「闸门在写回点之前」。⇒ 将来加第四个 crontab 写入口、忘了带闸门，本文件直接红。
- **第 2 组（行为级）**：读失败有**三种形态**（返回码非 0 / 抛 FileNotFoundError /
  抛 TimeoutExpired），每种都要「明确的失败返回」且**绝不执行 `crontab -`**；
  外加「写回失败必须报错，不能报『已更新』」。
- **第 3 组（正常路径）**：正常读取时保留 `renew-certs.sh` / `acme renew`，
  DDNS 条目只有一条不重复。

**配套变异**（新增 `tests/mutation_check_crontab_fail_closed.py`，**9 条全捕获**）：
摘掉三处闸门各一条、读失败当成空表两条、闸门挪到写回之后、写回失败不上报、
闸门只 return 不带失败语义、闸门缩到只拦一种异常。

### 10.6 写测试时，测试自己露了两个缺陷

跟安全闸那次一样 —— **是靠造坏输入逼出来的，不是靠读代码**：

1. **行为级只测了「返回码非 0」，没测「抛异常」**。
   而本次修复新增的 `except` 闸门正是管抛异常的 ⇒ 那条分支原本**完全没有行为级覆盖**。
   补上三种失败形态后，M3/M8/M9 三条变异才抓得住。
2. **静态断言用「有没有 return」当判据太松**。
   `except` 分支那句 `return False` 一直都在，
   于是「把 returncode 闸门挪到写回之后」这种退化照样能过。
   改成找 **`result.returncode != 0` 这个条件的位置**、要求它落在写回点之前，
   才把 M6 抓住。

⇒ 首版变异脚本 M6 **漏网**（我自己写的变异写错了：闸门插在 `new_crontab` 之前，
仍在写回之前，等价于 M1）。改成真正「先覆盖再检查」后才捕获。

⇒ 每条变异都被**对应层级的断言**抓住（逐条核对过捕获来源，没有靠巧合蒙对）。

### 10.7 M9 锚点脱节：破口从哪来、怎么发现的

这是本轮**第二个工程级发现**（第一个是指标失真，见原型说明「附三」）。

**现象**：全仓变异扫描报 `BAD`：

```
  [BAD] mutation_check_default_tab.py    8 捕获 / 1 漏网 / 1 锚点未命中
        ⚠️ 锚点未命中 [M9  防火墙状态被挪回原来的第 11 位（导航第一项不再是它）]: 旧串出现 0 次
```

**根因**：M9 的锚点是导航里**相邻的两行**：

```
      { id: 'firewall-status', label: '防火墙状态', icon: '🛡️' },
      { id: 'network', label: '网络接口' },
```

而 2026-11-08 加「系统信息」页时，在这两行**中间插了一行**
`{ id: 'system-info', ... }` ⇒ 两行不再相邻 ⇒ **旧串出现 0 次**
⇒ 这条变异**根本没跑**，却仍占着「捕获 N/N」里的一个名额。

**性质**：与 B5（锚点与源码脱节 ⇒ 变异被静默跳过，却照样计入总数）
**同型复发** —— 但这次发生在**自己刚加的功能**上：
加功能时改了被变异脚本锚住的那段源码，却没同步改锚点。

**流程失误在哪**：加「系统信息」的那两批（`f6d8416` / `579a6c4`）
**只跑了行为级回归、没跑全仓变异扫描** ⇒ 破口连续溜过两批提交，
直到这一轮跑全仓扫描才暴露。

⇒ **这正是「每批必须过三层验证」这条规矩要防的事**：
少跑一层，破口就能潜伏两批。

**修法**：锚点从「两项相邻」改成「整块结构」——

```
      { id: 'firewall-status', ... },
      // 「系统信息」紧跟在「防火墙状态」后面 ——
      // ……
      { id: 'system-info', label: '系统信息', icon: 'ℹ️' },
```

并在变异脚本里写明**为什么**要这么写（免得下次又有人改成"两项相邻"）。
修完单跑该脚本：**9/9 全捕获，锚点未命中 0**。

**防线是有效的**：扫描器把「锚点未命中」**单列一列**并当失败（不是"跳过"），
这正是 B5 那轮的成果 —— 它这次主动报了警。
⇒ 教训不是「防线不行」，而是**没跑那道防线**。

⚠️ 还有一个附带发现：**扫描器的计数口径本身有污染**。

第一次扫描报的是「捕获 8 / 漏网 1 / 锚点未命中 1」= 10，
但这个脚本**自报只有 9 条变异**（M1–M9）。多出来的那一条是假的。

查扫描器 `classify()` 的分类规则才看明白（不是猜，是读代码 + 拿原始输出复算）：

```python
if s.startswith('❌') and ('漏网' in s or '漏过' in s):
    missed += 1
```

脚本在有破口时会打**一行脚本级失败汇总**：

```
❌ 有漏网或锚点未命中的变异 —— 这些缺陷从此没人守
```

这行**以 `❌` 开头且含「漏网」二字** ⇒ 被扫描器当成「一条漏网的变异」计数。
⇒ **「漏网 1」根本不存在**，那正是这条汇总行冒充的。

而同一个脚本正常收尾时打的 `✅ 全部捕获` 也含「捕获」二字
⇒ 会被计进「捕获」列 ⇒ **捕获数也虚高**（实测 `static_whitelist` 扫描报 10、自报 9）。

⇒ 这个污染**方向最坏**：
「锚点未命中」是覆盖漏洞（这条变异根本没跑），
「漏网」是断言没抓住（跑了但没被抓住）——
两者严重程度完全不同，却被汇总行混成同一个数字，
看的人会以为**真有一条变异漏网**，白花一轮去查不存在的漏网。

**修法**：扫描器 `classify()` 增加「脚本级汇总行不计入四列」的过滤
（`_is_summary_line()` + 汇总短语黑名单，同时用明细特征片段兜底，
保证变异明细本身不会被误排除）。
改完用 M9 脱节那轮的**原始输出**复算过：`(捕获1, 漏网0, 锚点未命中1, 跳过0)`，与期望一致。

⚠️ 这条修的是**本机工具**（`~/main/tmp/apkval/mutation_isolated2.py`，不在仓库里），
所以它**不产生提交**。但它改变了「捕获」的官方口径 ——
数字会变小（去掉的是汇总行，不是真变异）。见 8.3。

⇒ 三条发现其实是同一件事：
**指标必须只统计它声称统计的东西。**
- 回归的「断言合计」漏统计了 14 项（输出格式不合规）
- 变异的「捕获数」多统计了汇总行
- 变异的「漏网数」被汇总行冒充出一条

#### 10.9.1 C2：IPv6 scope-id 判**非法**（不是「清洗」）

**先补一条 nft 1.1.7 实测**（隔离 netns，脚本与原始输出已归档在
`报告/nft-scopeid实测-20261108/`）：

| 用例 | `nft -c -f` 结果 |
|---|---|
| `elements = { fe80::1%eth0 }` | `syntax error, unexpected junk`（指针在 `%` 后） |
| `ip6 saddr fe80::1%eth0 accept` | `syntax error, unexpected junk`（指针在 `%` 后） |
| 基线：`ip6 saddr fe80::1 accept` | 通过 |

⇒ 两条结论：**集合元素**与**地址字面量**两种写法 nft 都拒；
连**合法**的 scope-id 也不认 ⇒ 任何带 scope-id 的地址都会让**整份**规则集加载失败。

**为什么判非法而不是剥掉 scope-id**：scope-id 是**链路本地地址**的接口标识，
不是地址本身；名单、白名单、信任 IP 全都是**按地址匹配**的，带它毫无意义。
而把 `fe80::1%br-lan` 悄悄改成 `fe80::1` 等于**替用户改了他填的值**。

**四个入口全部收紧**（第三、第四个是动手前逐个 grep 才发现的）：

| # | 位置 | 覆盖的路径 |
|---|---|---|
| 1 | `app.py` `_valid_ip` | 配置路径：trusted_ip6 / router_ip6 / 转发目标 |
| 2 | `app.py` `_detect_ip_version` | 名单添加路径（`POST /api/lists/add`） |
| 3 | `app.py` `_format_list_elements` | 名单 → **已落盘**规则集文件的同步 |
| 4 | `template_engine.py` `_inject_list_elements` | 名单 → **生成的**规则集文件（「点应用规则」） |

第 1 个是总入口（`_safe_ip` → `_valid_ip`），一处收紧覆盖多个下游；
第 4 个在**独立文件**里 —— 模板引擎不 import app.py，拿不到 `_valid_ip`，
所以它的闸门是就地实现的（`if '%' in s: dropped += 1; continue`）。

#### 10.9.2 C3：恢复配置前必须校验，且「缺失」与「非法」分开处理

`restore_config` 里补 `errs = validate_config(restored)`，
`if errs:` ⇒ 拒绝恢复 —— 校验放在 **落盘（`os.replace`）之前**。

`validate_config` 是**纯配置校验**（区间内零 subprocess、不查设备状态）⇒ 恢复时调用安全。

⚠️ 但直接 `validate_config(restored)` 会把「备份里**缺** `router_ip4`/`trusted_ip4`」
也判为非法 ⇒ **老版本备份连回退都做不了**（既有测试 `test_restore_epoch_guard.py`
与 `test_secret_file_perms.py` 直接挂 8 个）。最终语义分两类：

- **缺失** ⇒ 用**当前生效值**补上，再校验
- **非法 / 过宽**（`panel_allowed_nets` 含 `0.0.0.0/0`、`access_mode=knock`、
  `trusted_ip4='not-an-ip'`）⇒ 拒绝恢复

⇒ **缺失 ≠ 放宽边界，过宽才是**。

⚠️⚠️「当前生效值」的定义，两版做错过 —— 值得记下来：

**第一版**：只读**原始文件**（`open(CONFIG_PATH)+json.load`），
理由是「不能拿 `load_config()` 的返回值 —— 它会把 `DEFAULT_CONFIG` 合并进来，
而 `DEFAULT_CONFIG` 里写死的是 `trusted_ip4=192.168.100.2`（app.py:939），
那不是用户自己的地址」。

⇒ 这条理由**只对了一半**：`load_config()` 的合并顺序是
`result = dict(DEFAULT_CONFIG); result.update(config)` ⇒ **文件值优先**，
所以文件里写了值时它返回的就是**用户自己写的**那个值 ✔。
真正不能直接调 `load_config()` 的原因是另一个：
**它在配置损坏时会把那个文件移走**（`os.replace` 成 `.broken.<ts>`）——
恢复流程里不该有这种副作用。

**第二版（最终）**：自己算生效值 = `DEFAULT_CONFIG` + 原始文件（**文件优先**），
只读文件、不碰磁盘：

```python
_effective_cfg = dict(DEFAULT_CONFIG)
_effective_cfg.update(_current_cfg)     # _current_cfg = 原始文件的内容
```

- 文件里写了 ⇒ 继承用户**自己写的**值 ✔
- 文件里没写 ⇒ 继承 `DEFAULT_CONFIG` 的值 ——
  而那**正是当前生效的值**（`load_config()` 就是这么合并的）
  ⇒ 补它等于**保持现状**，不是放宽边界 ✔

⚠️ 这个语义是**被既有测试逼出来的**：第一版只读原始文件时，
`test_restore_epoch_guard.py` 直接挂 3 条 ——
它的夹具里「当前配置」**也**缺这两个字段 ⇒ 无值可继承 ⇒ 恢复被 500 拒掉。
⇒ 也就是说：**只堵住「备份缺字段」还不够**，
「当前配置也缺字段」同样要有一条明确的语义，
否则老版本备份在这台机器上根本回退不了。

⇒ 顺带把「只继承这两个字段」说清楚：`validate_config` 只把
`router_ip4` / `trusted_ip4` 列为**必填**，IPv6 那两个（`router_ip6` /
`trusted_ip6`）是**可选**。所以：

- **必填**字段缺失 ⇒ 必须填 ⇒ 填「当前生效值」（唯一不改变现状的填法）
- **可选**字段缺失 ⇒ 恢复后的文件里**也不写**它 ⇒ 生效值仍由
  `DEFAULT_CONFIG` 兜底 ⇒ **同样是保持现状**，
  不必（也不该）把默认值**钉进**用户的配置文件。

#### 10.9.3 C4：规则集完整备份必须 0600

`_apply_ruleset_locked` 里备份完整 ruleset 时改成**先 chmod 再让 nft 写**：

```
open(_rules_backup, 'w') → os.chmod(_rules_backup, 0o600) → nft list ruleset > 备份
```

- 为什么不是「写完再 chmod」：那是**有窗口**的 —— 写完到 chmod 之间，
  文件内容已经完整且权限还松着。现在是刚创建（还是空文件）就 chmod，之后 nft 才开始写。
- chmod 失败 ⇒ **丢弃该备份**（`_unlink_quiet`）+ 警告 + raise ——
  留一个「内容完整但对本地用户可读」的文件，比没有这个备份更糟。
- 权限位依据：规则集本体 0600（`_ensure_file_mode(tmp_path, 0o600)`）、
  `.lastgood` 也是 0600 ⇒ `.backup` 应为 0600。
- **顺手修了一处硬编码不一致**：备份路径从写死的
  `/etc/nftables.d/99-custom-rules.nft.backup` 改为 `RULES_PATH + '.backup'` ——
  原写法与 `_config_corrupted()` 检查的**不是同一个文件**（`RULES_PATH` 可被环境变量改），
  而且写死路径没法在测试里隔离。默认部署下拼出来的路径**完全一样**，行为不变。

#### 10.9.5 工程发现（一）：**401 冒充了测试结果**

写完 C3 的测试，头一次跑有 3 条失败。逐条定位后发现：
其中 **3 条是假通过** —— 它们拿到的不是被测逻辑的拒绝，而是 **401**。

机理：测试自己重写配置时把 `auth_token_epoch` 从「缺省回落 0」改成了显式的 `1`
⇒ `_session_epoch_ok()` 比对不上 ⇒ `before_request` 清会话 ⇒ 之后**所有**接口返回 401
⇒ 而「应当被拒」的断言写的是 `status >= 400` ⇒ **401 也算通过**。

⇒ 被测逻辑到底有没有生效，那三条断言**根本没测到**。

修法三步：
1. 夹具里**显式写死** `auth_token_epoch`（并补上 `trusted_ip4`/`router_ip4`，
   否则「缺失字段继承当前配置」无值可继承，测的就不是继承）；
2. 加 `session_alive()` 探针 + `is_auth_error()` 判定 ——
   凡「应当被拒」的用例都必须**排除 401**，并要求消息里出现被测特征（如「校验」）；
3. 测试**故意**改 epoch 时（用例 2.6）必须重签会话，否则那条断言
   会「因为文件里本来就是 7」而通过 —— 又是假通过。

⇒ 通用经验：**判据里凡是「状态码 ≥ 某个值」这种宽判定，
都要额外排除「认证失效」这一类假阳性** ——
它满足所有宽判定，却什么都没测。

#### 10.9.6 工程发现（二）：「以为只有两处」

C2 的原始描述只点了「名单条目写 `nft add element` 时未严格解析」，
⇒ 动手前我先按这个描述去找入口（`_valid_ip` + `_detect_ip_version`），
**自认为找齐了**。真正逐个 grep `ipaddress.ip_address(` 的调用点时才发现：
名单进规则集还有**两条**路径，各自有一道自己的闸 ——
`_format_list_elements`（同步进已落盘文件）和
`template_engine._inject_list_elements`（生成新规则集文件），
而这两道闸**既不走** `_valid_ip` **也不走** `_detect_ip_version`，
自己直接调宽松的 `ipaddress.ip_address()`。

⇒ 若只堵住「描述里提到的那两处」，脏值照样能进规则集文件
⇒ **apply 永久失败**（`nft -c -f` 预检挂，预检在 `os.replace` 之前，
所以已生效的规则不变，但面板失去控制能力）。

⇒ 通用经验：**修一处漏洞时，要找的是「这类数据能流过的所有闸」，
不是「描述里点名的那几处」**。描述是线索，不是清单。

#### 10.9.7 工程发现（三）：我的改动把**别人脚本的锚点**打散了

全仓变异扫描（41 个脚本，各跑独立副本）把 `mutation_check_secret_perms.py`
标成了 `[BAD]` —— 捕获 10 / 11。

原因：C3 在 `restore_config` 里往两行之间**插了一段**（缺失字段继承当前生效值），
而那条脚本的 M10 锚点恰好是「epoch 赋值 → 注释 → `_ensure_file_mode`」这一整块
⇒ 锚点失配 ⇒ 变异**被静默跳过** ⇒ 那条防线**根本没跑**。

⚠️ 这跟 10.7 记的 M9 锚点脱节是**同一个病**，只是这次发生在**别的脚本**上。
⇒ 所以「全仓扫描」不只是查漏网，也是查**锚点漂移**的手段：
   任何改动只要动了别人脚本的锚点附近，那次扫描就会把它暴露出来。

**这次是脚本自己发现的** —— 它的锚点失配会打印警告并以非 0 退出，
扫描器据此把这一份标成 `[BAD]` ⇒ 机制是有效的，不是靠人眼发现。

修法：把锚点从「A 恰好挨着 B」换成「这段代码独有的语义」——
用**纯代码**三行（`json.dump(restored, ...)` 只有 `restore_config` 有），
不含任何注释 ⇒ 改注释、插代码都不会再把它打散。

⇒ 顺带查清了扫描表里另外两处「数字看着对不上」：
`mutation_check_auth_bounds.py`（自报 16 变异 / 捕获 15）与
`mutation_check_auth_hardening.py`（17 / 15）——
那两处是脚本自己归类的**等价变异**（改掉之后可观测行为完全不变），
并写明了理由（POSIX `rename(2)` 对已存在的目标本身就是原子替换，
与 `replace` 语义一致）⇒ **不是漏网**。
⇒ 扫描器已加「等价」一列（见 10.9.8）⇒ 数字现在直接对得上。

#### 10.9.8 工程发现（四）：扫描里的一次**偶发**失败，暴露了脚本「红了却不说哪条红」

全仓扫描（41 个脚本，6 路并发）里，`mutation_check_p0_fixes.py` 出现过 **2 次**
`[BAD]`：捕获 25 / 漏网 0 / 锚点未命中 0，但**退出码非 0**。

⇒ 四列数字全对（25 条变异**全部被抓住**，检测结论不受影响），
只有退出码不对 ⇒ 说明它走的是另一条非零退出路径。

定位过程（逐条排除，不是猜的）：

1. 单独跑该脚本：**rc=0，25/25 全捕获** ⇒ 不是脚本自身的确定性缺陷；
2. **6 份并发**跑同一个脚本：**全绿** ⇒ 不是脚本内部互相踩；
3. **8 份并发**跑它依赖的 `test_p0_security_fixes.py`：**全绿**（56/0）
   ⇒ 那条 PBKDF2 计时断言（已用 `process_time` + 3 次取 min + 0.85 阈值加固过）
   在这个负载下不抖；
4. 输出里打印的三个 sha256 与仓库当前值**逐字节一致**
   ⇒ 源码**确实还原干净了** ⇒ 「没还原干净」这条路径被排除；
5. ⇒ 结论：还原后的那次测试跑**偶发变红**，只在满负载（41 脚本混跑）下出现。

⇒ 但真正的问题不在「偶发」本身，而在**它不可诊断**：
脚本只印一句「还原后测试仍不绿，源码可能没还原干净」——
既不说是哪个文件、哪条断言红了，也没把 sha256 与基线**比对**（只印出来给人看）。

**修法**（`tests/mutation_check_p0_fixes.py`）：

- 基线指纹在开跑前记下，还原后**逐个比对** ⇒ 一眼分清
  「源码没还原干净」与「源码没问题、是测试假红」；
- 假红时把**失败的断言行**打出来（原来完全无从下手）。

⇒ 配套把扫描器（**本机工具**，不在仓库里）也改了三处：

| 改动 | 为什么 |
|---|---|
| 认「等价变异」这一列 | 免得每次都要人看一眼「自报 16 变异 / 捕获 15」是不是出问题了 |
| 把「崩了」计入**漏网** | 那种「捕获」是假的 —— 变异把代码改到连跑都跑不起来时，断言根本没机会红 |
| 每份脚本的输出**落盘** | 下次再出现 `[BAD]`，直接看文件复盘，不用重跑那一轮 |

⇒ 这条也印证了 10.7 的结论：**扫描器不只是查漏网的工具，
也是查「工具自己漂移/失灵」的工具** —— 这次的 `[BAD]` 就是它自己报的。
