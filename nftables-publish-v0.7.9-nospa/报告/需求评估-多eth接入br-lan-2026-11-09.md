# 需求评估：多 eth 接入 br-lan（多 LAN 口）

- **提出**：用户 kirito，2026-11-09（原话：「多eth接入br-lan。这个功能应该简单，就是多lan口。」）
- **状态**：**待排期**（用户说「未来还要加」，本轮未实现）
- **本文档作用**：把「看起来简单」的地方和「其实不简单」的地方分开写清楚，
  免得下次接这个需求时重新摸一遍。

---

## 一、先说结论

| 层面 | 要不要改 | 说明 |
|---|---|---|
| **防火墙规则** | **不用改** | 规则全部用 `iifname $LAN_IF`（`$LAN_IF = br-lan`）。桥成员口的 L3 输入挂在**桥**上，iifname 就是 `br-lan` ⇒ 一条规则覆盖全部成员口 |
| **兜底 lockdown 规则** | **不用改** | 同上，`iifname "{lan_if}"` |
| **setup.sh 的接口探测** | **不用改** | 已经同时兼容 DSA（`option device 'br-lan'` + `list ports`）和 swconfig（`option ifname`） |
| **面板监听地址** | **不用改** | 面板绑 router IP / 0.0.0.0，与口数无关 |
| **WAN 口自动检测** | **要改（两处）** | 见第三节 |
| **系统信息页展示** | **建议改（可选）** | 见第四节 |
| **「在面板里把某个口加进 br-lan」** | **要做的话就不是小活** | 见第五节 |

⇒ **「设备已经是多口桥接、面板跑在上面」⇒ 面板不用改任何东西就能正常工作。**
真正的工作量在「让面板去改桥成员」这件事上。

---

## 二、为什么防火墙侧不用改（这是「简单」的那部分）

模板里 LAN 侧只有一处关键定义：

```
define LAN_IF = "br-lan"
...
chain input {
    ...
    iifname $LAN_IF jump input_lan
}
```

OpenWrt 把 `eth0`/`eth1`/`eth2` 都 `add` 进 `br-lan` 之后，
这些口进来的三层报文在桥上交给 `br-lan` 处理 ⇒ `iifname` 看到的是 `br-lan`。

⇒ **加口 = 在 UCI 里多一行 `list ports`**，防火墙规则一个字都不用动。
面板配置里的 `lan_if` 也保持 `br-lan` 不变。

实测佐证（`.232`，2026-11-09）：`eth0` 的 master 就是 `br-lan`，
`ip addr` 里地址只挂在 `br-lan` 上，`eth0` 自己没有 inet 地址。

---

## 三、要改的地方：WAN 口自动检测（`update_uci_wan_config`）

面板在「保存网络配置 / PPPoE 拨号」时，会自己找一个**没被 LAN 桥占用**的物理口当 WAN：

```python
# 读 /etc/config/network 里所有 `list ports` 行 → lan_ports
# 再从 /sys/class/net 里挑第一个 eth*/ens*/enp* 且不在 lan_ports 的
```

多口都进 br-lan 时，这个逻辑**仍然成立**（lan_ports = {eth0, eth1} ⇒ WAN 候选 = eth2），
但有两处要改：

| # | 问题 | 后果 | 改法 |
|---|---|---|---|
| W1 | `list ports` 的解析**只认带引号的**：`p = line.strip().split("'")[-2] if "'" in line else ''` | 手写成 `list ports eth1`（UCI 允许无引号）时这个口**解析不到** ⇒ 被当成 WAN 候选 ⇒ **WAN 抢走 LAN 的桥成员 ⇒ 整机失联** | 改成 `shlex`/正则容错解析；同时把「解析到的端口」与 `/sys/class/net/<if>/master` 交叉验证（**桥成员的 master 一定是 br-lan**，这是比文本解析更硬的证据） |
| W2 | 检测不到独立 WAN 口时，错误文案写死「本机只有一张物理网卡」 | 多口机上这句是错的（真实原因应是「所有物理口都已划给 LAN 桥」） | 文案按实际口数生成 |

⚠️ W1 这条正是 2026-10-06 那次失联事故（`ARP FAILED`、Proxmox 没开带外口）的同一类问题，
只是当时是「单网卡兜底猜 eth0」，现在是「多口时解析漏了一个桥成员」。
**同一个坑，值得单独加一条回归。**

## 四、可选：系统信息页的展示

多口桥接后，系统信息页上会这样显示：

| 接口 | state | ipv4 | ipv6 |
|---|---|---|---|
| `br-lan` | up | 192.168.100.232 | fe80::… |
| `eth0` | up | （空） | （空） |
| `eth1` | up | （空） | （空） |

**这是正确的**（桥成员口自己不持有 IP，地址在桥上），
但用户看到「eth1 的 IP 是空的」很容易以为这个口坏了。
⇒ 可选改进：在接口表里标出「属于 br-lan 桥，地址在桥上」。

⚠️ 顺带：桥成员口在 `/proc/net/if_inet6` 里**没有**自己的 IPv6，
IPv6 只在 `br-lan` 上 ⇒ 所以这个展示口径不会因为多口而重复。

## 五、如果要做到「在面板里把某几个口加进 br-lan」

那就不是小活了。现状：`/api/network/config` 的 GET/POST **只处理 WAN 相关字段**
和 LAN IP 同步，**完全不读写 `list ports`**。

要做的话，最少要补：

1. **读**：解析 `config interface 'lan'` 段的 `option device` + 所有 `list ports`
2. **写**：增删 `list ports`（要保证**至少保留一个**成员口，且不能动 WAN 口）
3. **失联保护**（最关键）：改桥成员 = 改网络 = **改错就是整机失联**。
   必须有：改前备份 `/etc/config/network`（含拨号口令，权限 600）、
   校验（WAN 口不得被划进 LAN 桥）、写后原子替换、失败回滚、
   以及**明确提示「改完要重启网络，期间会断」**。
4. **和第三节的 WAN 检测联动**：两个功能改的是同一份文件，必须共用一套
   「哪些口归 LAN / 哪些口归 WAN」的真值来源（建议以 `/sys/class/net/*/master` 为准，
   UCI 文本只作为写入目标）。

⇒ 建议的推进顺序：**先做「面板能正确跑在多口机器上」（= 不改代码）**，
确认用户真的需要面板来改桥成员之后，再做第五节那套带失联保护的写入功能。

---

## 六、需要用户拍板的一件事

「多 eth 接入 br-lan」这句需求有两种读法，工作量差一个数量级：

- **读法 A**：设备侧把几个口加进 br-lan（手工改 UCI），面板照常跑
  ⇒ **面板不用改**，只需保证 W1/W2 两处修好 + 补回归
- **读法 B**：在面板界面上选择哪些口进 br-lan
  ⇒ 要做第五节整套（读/写/失联保护/联动），是新功能

⇒ **默认按读法 A 推进**（先把 A 做扎实、测过），B 等明确要做时再开。
