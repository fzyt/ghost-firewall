# 路由器「系统信息」页（原型）

> 2026-11-08 第一版原型。数据来源是**设备本身**（`/proc`、`/sys`、`/etc`），
> 不是面板配置文件。

## 这页解决什么问题

面板此前只展示两样东西：**配置**（你能改什么）和**状态**（防火墙还活着吗）。
从不展示「**这台设备本身是什么样**」。

而排查问题的第一句话往往就是这些：

- 你这什么设备、什么型号？
- 固件什么版本？（固件版本 ≠ 内核版本，两者差着好几代）
- 多少内存、多少磁盘、还剩多少？
- 开了多久了？
- 哪些接口、各配了什么地址、收发了多少流量？

这些信息以前只能 ssh 进去自己敲命令看。现在面板上直接有。

## 数据从哪来

| 展示项 | 数据源 | 备注 |
|---|---|---|
| 设备型号 | `/tmp/sysinfo/model` | OpenWrt 专有，没有就显示「未知」 |
| 固件版本 | `/etc/openwrt_release` | `DISTRIB_ID` + `DISTRIB_RELEASE` + `DISTRIB_REVISION` |
| 通用发行版 | `/etc/os-release` | 非 OpenWrt 部署模式（linux_gateway）走这条 |
| 内核版本 | `os.uname()` | **与固件版本不是一回事**，分开显示 |
| 运行时间 | `/proc/uptime` | |
| CPU 型号 / 核数 / 主频 | `/proc/cpuinfo` + `/sys/devices/system/cpu` | |
| 内存 | `/proc/meminfo` | `MemAvailable` 没有时用 `MemFree + Cached + SReclaimable - Shmem` 估算 |
| 磁盘 | `os.statvfs('/')` | 真实占用，不解析 `df` 输出 |
| 接口清单 / 流量 | `/proc/net/dev` | |
| 接口状态 | `/sys/class/net/*/operstate` | |
| 接口 IPv4 | `/proc/net/route` + `/proc/net/fib_trie` | 读不到时退到 `getifaddrs` |
| 接口 IPv6 | `/proc/net/if_inet6` | 临时地址（隐私地址）不显示 |

## 三条硬约束

### 1. 只读

采集器**只读文件**，不写任何东西、不执行任何会改状态的命令。
不调 `ip`、不跑 `ifconfig`、不用 netlink（实测本机 netlink 的 `recv` 会阻塞，
一个展示型页面不该有把请求挂住的风险）。

### 2. 不依赖 ubus / rpcd

OpenWrt 的 ubus 走本地 socket，`POST /ubus` 会被 rpcd 的 ACL 挡住
（`/usr/share/rpcd/acl.d/` 下默认没有任何规则授权 `system.*`）。
面板跑在 nginx 后面、权限也被降过 ⇒ 走 ubus 既不可靠也不安全。
能用 `/proc`、`/sys`、`/etc` 读到的，一律直接读文件。

### 3. 读不到就是「未知」，不猜

宁可页面上显示「未知」，也不要显示一个编出来的数字。
**内存 0 KB** 会被误读成「设备没有内存」—— 而真实情况是「这一项没采到」。

这一条在测试里有对应的断言：`fmtKb(null)` 必须返回 `'未知'`，不能返回 `'0 KB'`。

## OpenWrt 上的环境差异（真机要重点验的）

采集器是为 OpenWrt / BusyBox 写的，开发机是 Debian，两者有几处不一致：

| 差异 | 影响 | 兜底 |
|---|---|---|
| `/proc/net/fib_trie` 依赖 `CONFIG_FIB_TRIES` | OpenWrt 上不一定开 ⇒ IPv4 采不到 | 退到 `getifaddrs`（libc 标准函数，musl 也有） |
| `/sys/class/net/*/ipv4` 在 5.15+ 内核已移除 | 拿不到接口 IPv4 | 不用它，走 route+fib_trie / getifaddrs |
| `/proc/net/if_inet6` IPv6 关掉时不存在 | IPv6 采不到 | 空列表，不是错误 |
| 无 `ubus` ACL 授权 | 走 ubus 会被拒 | 完全不用 ubus |

**所有路径在读不到时都返回 None / 空列表，不抛异常** ——
「这台设备上没这个文件」是常态，不是故障。

## 写这个采集器时踩的四个坑

全部记在 `backend/device_info.py` 的注释里，也各有对应的回归用例：

1. **`/proc/net/route` 的地址是小端字节序**
   （`0064A8C0` = 192.168.100.0）。按大端解析 ⇒ 网段变成 `0.100.168.192/24`
   ⇒ IPv4 一个都匹配不上。
2. **掩码不能当二进制串去 `int(..., 2)`**
   —— 掩码已经是点分十进制（255.255.255.0），那样会拿到 `'2552552550'` 报错。
3. **`/proc/net/fib_trie` 里地址行与 `/32 host LOCAL` 是两行**，地址在上面那行。
   把「以 host LOCAL 结尾的行」当地址行去 split ⇒ body 是空串。
4. **`Main:` 是 `/proc/net/fib_trie` 的第一行**，不是中间的分节。
   按「先找 Main: 再往下读」写 ⇒ 永远进不去 Main 表。

另外，**掩码的连续性检查要看整体**：255.0.255.0 的每一组都合法，
但整体不连续（前缀长度算出来是 16，而这个掩码不是任何合法前缀）。

## 附：这一轮被既有防线抓住的三个真实回归

新代码不是「加了就能过」——全量回归跑出 **3 个真实失败**，
全是项目里**既有**的防线抓住了我新写的东西。这三条防线各自在防什么，
值得记下来（也说明它们确实在干活）：

### 1. `test_e2e_button_guards.py`：新动作必须登记进 EXPECT 表

`index.html` 里每个应用动作都必须在 EXPECT 表里登记（否则 e2e 跑的时候
不知道该怎么处理它）。我加了 `loadDeviceInfo` 没登记 ⇒ 直接被抓。

⇒ 这条防线的价值：新增页面动作时，**必须同时更新 e2e 的预期表**，
不能只写页面。

### 2. `test_frontend_default_tab.js`：导航次序断言写得太死

原断言是「**网络接口**紧随防火墙状态之后」，也就是「`navIds[1]` 必须是 network」。
我把「系统信息」插在两者之间，它就红了。

⇒ 但这条断言的**意图**（「配置项之间的次序没被打乱」）其实没被破坏 ——
被打乱的是「状态页和配置项的相对位置」，配置项内部次序原封不动。

⇒ 修法不是把断言改松，而是**把判据改准**：断言「网络接口是**第一个配置项**」
（把状态页 id 排除掉再比），而不是「排在第二项」。
⇒ 顺带暴露了一个更普适的问题：**断言里写死了序号，就等于把「同类项的个数」也写死了**。

### 3. `test_frontend_xfor_keys.js`：`:key` 不能用内容本身

我给接口列表写了 `:key="iface.name"`。这条防线的白名单是
`id` / `key` / `ip` 三种字段 + 索引变量 —— **不许用「内容」当 key**，
因为内容可能重复（重复的 key 会让 Alpine 的 diff 出错）。

⇒ 改成 `:key="idx"`（并把 x-for 写成 `(iface, idx) in ...`）。

⇒ 三条都在**没跑真机**的情况下被抓住 —— 说明这层防线比真机验证更早、也更省事。

## 附二：截图抓到的布局问题（纯代码测试抓不到）

上面三条是「代码层面的错」。但还有一类错，**静态测试全绿、真机没跑、页面上看着也不报错** ——
只是**难看**、或者**信息读不出来**。

本轮用 Playwright 截了一次图，抓到：

**接口表的地址列用了 `break-all`。**

`break-all` 的语义是「在**任意字符**处断行」。实测效果：

```
192.168.100.24
9                    ← 被从中间劈开了
```

IPv6 更糟 —— 两条地址（各 39 字符）用逗号连在一起，
既断在半路、又分不清哪条到哪条结束。

⇒ 这类问题**代码测试一条都抓不到**：
字段名对、表达式对、值对、无异常、标签配平 —— 全绿，
但用户看到的是一堆断成两半的 IP。

⇒ 修法：
- `break-all` → `break-words`（按词断，IPv4 的点号是断点）
- 多条地址**每条一行**（内层 `x-for`），不用逗号连
- 地址列给 `min-w-[9rem]` / `min-w-[12rem]`，让长 IPv6 换行而不是挤扁别的列
- 接口名/状态/流量列加 `whitespace-nowrap`

⇒ 结论：**前端改动，静态测试过了不算完** —— 至少要渲染一次看一眼。
这也正是项目里 e2e 用 Playwright 的价值所在。

### 本地渲染验证怎么做的

不需要真设备：

1. 起一个本地面板实例，用**测试配置**（`127.0.0.0/8` 白名单 + 预设会话）

## 附三：14 项断言被静默漏计 —— 指标自己骗自己

这一节是本轮**最该被记住**的一条，不是功能记录，是工程记录。

### 发生了什么

采集器测试 `tests/test_device_info.py` 写的是 **unittest**，
默认输出长这样：

```
test_route_address_is_little_endian (__main__.TestHexConversion.test_route_address_is_little_endian) ... ok
```

**不带任何标记**。

而全量回归的计数规则只认「行首是 `✅` 或 `[PASS]`」——
于是这个文件的 **14 项断言一条都没进硬指标**，
回归日志里显示成：

```
  ✅ test_device_info.py                        ✅0 ❌0
```

`rc=0`、失败数 `0`、整行是绿的 ⇒ **看着完全正常**。
实际上这 14 项从来没被计入过。

### 为什么危险

这跟「测试写错了」不一样 —— 测试**是对的**，14 项全过。
危险的是**指标**：如果这个文件里有一条断言挂了，`rc` 仍然非 0，
回归会红，所以**失败还是拦得住**。

但硬指标「断言合计 N」会**长期偏低**，而这个数字是判断
「覆盖有没有在长」的依据。偏低不报警 ⇒ 指标失效 ⇒
「回归全绿」这句话的含金量在悄悄下降。

**这是本项目第三次踩同一类坑**：

| 次序 | 文件 | 漏计 | 当时的修法 |
|---|---|---|---|
| 1 | `test_portal_frontend.py` | 282 项 | 在 `run_all.sh` 加「两种标记一起数」 |
| 2 | `test_pixelfield_trae.js` | 20 项 | 同上 |
| 3 | `test_device_info.py`（本轮） | 14 项 | 改测试文件输出 + 回归脚本加兜底 |

⇒ 前两次都是「**在计数端打补丁**」，治的是症状。
第三次换了个思路：**两头堵**。

### 这次怎么修的

**头：测试文件侧输出合规标记**

`test_device_info.py` 换成自定义的 `unittest.TestResult`，
每个用例打一行 `  [PASS] 方法名`，失败打 `  [FAIL] 方法名` + traceback，
跳过打 `  [SKIP]`（跳过既不算通过也不算失败，与回归脚本的既有约定一致）。

⚠️ 有一个坑：`unittest.TestResult.addSubTest` **不会**回调
`addSuccess` / `addFailure` ⇒ 用了 `subTest` 的用例会一条标记都不打。
所以额外覆盖了 `addSubTest`，否则又是一次静默漏计。

**尾：回归脚本侧加兜底**

`tests/run_all.sh` 的两个循环（Python / 前端）都加了：

```bash
elif [ "$p" -eq 0 ] && [ "$fl" -eq 0 ]; then
  FAILED="$FAILED $(basename "$f")(0 断言未计入)"
  printf '  ❌ %-42s 断言数 0 —— 输出格式不被计数规则识别\n' "$(basename "$f")"
```

**只要出现 0 断言就判失败** —— 逼作者把输出格式改合规，
而不是让指标悄悄少算。

### 怎么验的（不是"看代码觉得对"）

1. **失败路径单独验**：造 2 个故意失败的用例 + 1 个跳过的用例，
   确认 `[FAIL]` 行真的打出来（计数规则数得到）、`[SKIP]` 不计入、
   退出码为 1。
   —— 因为「只在成功路径打标记」的写法会让**失败数漏计**，
   那是往「看起来全绿」的方向失真，比漏计成功数更坏。
2. **兜底逻辑单独验**：在 `/tmp` 副本里放一个「输出无标记、rc=0」的假测试文件，
   确认回归脚本真的报「断言数 0」并以退出码 1 结束。
3. **数字自证**：修完全量回归从 3744 变成 **3758**，
   正好 +14 = 补计入的项数。分解自洽：
   `3624 + 32（端点）+ 56（契约）+ 31（渲染）+ 1（EXPECT 表）+ 14（补计入）= 3758`。

### 结论

⇒ **「测试全过」不等于「测试被算进去了」。**
一个数字如果只统计自己认识的那几种格式，那它统计的是**格式**，
不是**测试**。

⇒ 加新测试文件时，除了「跑一遍看到 ok」，还要确认
**它的输出能被回归脚本数到** —— 现在有兜底会直接拦，不用再靠人记。

⇒ 同类问题本轮还挖出两起，都在变异那侧：
**M9 变异锚点脱节**（加「系统信息」页时把锚点顶开了，那条变异根本没跑）
与**扫描器把脚本级汇总行当成变异明细行**（捕获数虚高）。
⇒ 详见 `报告/e2e真机全链验证-2026-11-08.md` 的 10.7。

⇒ 三起其实是同一件事：**指标必须只统计它声称统计的东西。**
