# 路由器「系统信息」页（原型）

> 2026-11-08 第一版原型。数据来源是**设备本身**（`/proc`、`/sys`、`/etc`），
> 不是面板配置文件。

## 这页解决什么问题

面板此前只展示两样东西：**配置**（你能改什么）和**状态**（防火墙还活着吗）。
从不展示「**这台设备本身是什么样**」。

而排查问题的第一句话往往就是这些：

- 你这什么设备、什么型号？
- 固件什么版本？（固件版本 ≠ 内核版本，两者差着好几代）
- 多少内存、多少磁盘、还剩多少？
- 开了多久了？
- 哪些接口、各配了什么地址、收发了多少流量？

这些信息以前只能 ssh 进去自己敲命令看。现在面板上直接有。

## 数据从哪来

| 展示项 | 数据源 | 备注 |
|---|---|---|
| 设备型号 | `/tmp/sysinfo/model` | OpenWrt 专有，没有就显示「未知」 |
| 固件版本 | `/etc/openwrt_release` | `DISTRIB_ID` + `DISTRIB_RELEASE` + `DISTRIB_REVISION` |
| 通用发行版 | `/etc/os-release` | 非 OpenWrt 部署模式（linux_gateway）走这条 |
| 内核版本 | `os.uname()` | **与固件版本不是一回事**，分开显示 |
| 运行时间 | `/proc/uptime` | |
| CPU 型号 / 核数 / 主频 | `/proc/cpuinfo` + `/sys/devices/system/cpu` | |
| 内存 | `/proc/meminfo` | `MemAvailable` 没有时用 `MemFree + Cached + SReclaimable - Shmem` 估算 |
| 磁盘 | `os.statvfs('/')` | 真实占用，不解析 `df` 输出 |
| 接口清单 / 流量 | `/proc/net/dev` | |
| 接口状态 | `/sys/class/net/*/operstate` | |
| 接口 IPv4 | `/proc/net/route` + `/proc/net/fib_trie` | 读不到时退到 `getifaddrs` |
| 接口 IPv6 | `/proc/net/if_inet6` | 临时地址（隐私地址）不显示 |

## 三条硬约束

### 1. 只读

采集器**只读文件**，不写任何东西、不执行任何会改状态的命令。
不调 `ip`、不跑 `ifconfig`、不用 netlink（实测本机 netlink 的 `recv` 会阻塞，
一个展示型页面不该有把请求挂住的风险）。

### 2. 不依赖 ubus / rpcd

OpenWrt 的 ubus 走本地 socket，`POST /ubus` 会被 rpcd 的 ACL 挡住
（`/usr/share/rpcd/acl.d/` 下默认没有任何规则授权 `system.*`）。
面板跑在 nginx 后面、权限也被降过 ⇒ 走 ubus 既不可靠也不安全。
能用 `/proc`、`/sys`、`/etc` 读到的，一律直接读文件。

### 3. 读不到就是「未知」，不猜

宁可页面上显示「未知」，也不要显示一个编出来的数字。
**内存 0 KB** 会被误读成「设备没有内存」—— 而真实情况是「这一项没采到」。

这一条在测试里有对应的断言：`fmtKb(null)` 必须返回 `'未知'`，不能返回 `'0 KB'`。

## OpenWrt 上的环境差异（真机要重点验的）

采集器是为 OpenWrt / BusyBox 写的，开发机是 Debian，两者有几处不一致：

| 差异 | 影响 | 兜底 |
|---|---|---|
| `/proc/net/fib_trie` 依赖 `CONFIG_FIB_TRIES` | OpenWrt 上不一定开 ⇒ IPv4 采不到 | 退到 `getifaddrs`（libc 标准函数，musl 也有） |
| `/sys/class/net/*/ipv4` 在 5.15+ 内核已移除 | 拿不到接口 IPv4 | 不用它，走 route+fib_trie / getifaddrs |
| `/proc/net/if_inet6` IPv6 关掉时不存在 | IPv6 采不到 | 空列表，不是错误 |
| 无 `ubus` ACL 授权 | 走 ubus 会被拒 | 完全不用 ubus |

**所有路径在读不到时都返回 None / 空列表，不抛异常** ——
「这台设备上没这个文件」是常态，不是故障。

## 写这个采集器时踩的四个坑

全部记在 `backend/device_info.py` 的注释里，也各有对应的回归用例：

1. **`/proc/net/route` 的地址是小端字节序**
   （`0064A8C0` = 192.168.100.0）。按大端解析 ⇒ 网段变成 `0.100.168.192/24`
   ⇒ IPv4 一个都匹配不上。
2. **掩码不能当二进制串去 `int(..., 2)`**
   —— 掩码已经是点分十进制（255.255.255.0），那样会拿到 `'2552552550'` 报错。
3. **`/proc/net/fib_trie` 里地址行与 `/32 host LOCAL` 是两行**，地址在上面那行。
   把「以 host LOCAL 结尾的行」当地址行去 split ⇒ body 是空串。
4. **`Main:` 是 `/proc/net/fib_trie` 的第一行**，不是中间的分节。
   按「先找 Main: 再往下读」写 ⇒ 永远进不去 Main 表。

另外，**掩码的连续性检查要看整体**：255.0.255.0 的每一组都合法，
但整体不连续（前缀长度算出来是 16，而这个掩码不是任何合法前缀）。

## 真机验证清单（设备上线后逐条核对）

- [ ] 型号、固件版本、内核版本三个字段都对（与 `cat /etc/openwrt_release` 对照）
- [ ] 内存总量与 `free -m` 对得上
- [ ] 磁盘总量与 `df -h /` 对得上
- [ ] 运行时间与 `uptime` 对得上
- [ ] 接口清单与 `ip addr` 对得上（**IPv4 尤其要验** —— fib_trie 在 OpenWrt 上可能不存在，
      走的是 getifaddrs 兜底路径）
- [ ] 接口状态与 `ip link` 对得上
- [ ] 收/发流量在刷新后确实在涨
- [ ] 未登录时接口返回 401

## 附：这一轮被既有防线抓住的三个真实回归

新代码不是「加了就能过」——全量回归跑出 **3 个真实失败**，
全是项目里**既有**的防线抓住了我新写的东西。这三条防线各自在防什么，
值得记下来（也说明它们确实在干活）：

### 1. `test_e2e_button_guards.py`：新动作必须登记进 EXPECT 表

`index.html` 里每个应用动作都必须在 EXPECT 表里登记（否则 e2e 跑的时候
不知道该怎么处理它）。我加了 `loadDeviceInfo` 没登记 ⇒ 直接被抓。

⇒ 这条防线的价值：新增页面动作时，**必须同时更新 e2e 的预期表**，
不能只写页面。

### 2. `test_frontend_default_tab.js`：导航次序断言写得太死

原断言是「**网络接口**紧随防火墙状态之后」，也就是「`navIds[1]` 必须是 network」。
我把「系统信息」插在两者之间，它就红了。

⇒ 但这条断言的**意图**（「配置项之间的次序没被打乱」）其实没被破坏 ——
被打乱的是「状态页和配置项的相对位置」，配置项内部次序原封不动。

⇒ 修法不是把断言改松，而是**把判据改准**：断言「网络接口是**第一个配置项**」
（把状态页 id 排除掉再比），而不是「排在第二项」。
⇒ 顺带暴露了一个更普适的问题：**断言里写死了序号，就等于把「同类项的个数」也写死了**。

### 3. `test_frontend_xfor_keys.js`：`:key` 不能用内容本身

我给接口列表写了 `:key="iface.name"`。这条防线的白名单是
`id` / `key` / `ip` 三种字段 + 索引变量 —— **不许用「内容」当 key**，
因为内容可能重复（重复的 key 会让 Alpine 的 diff 出错）。

⇒ 改成 `:key="idx"`（并把 x-for 写成 `(iface, idx) in ...`）。

⇒ 三条都在**没跑真机**的情况下被抓住 —— 说明这层防线比真机验证更早、也更省事。
