### 0.1 面板主进程是 root，只有认证网关降权到 nftweb `[实证]`

任务简报写「面板进程跑在降权账号下（nftweb），不是 root」。**这条与项目代码不符**：

| 进程 | init 脚本 | 实际身份 | 证据 |
|---|---|---|---|
| 面板本体 `app.py` | `backend/nftables-web.init:293` → `python3 app.py &` | **root**（脚本无 `procd_set_param user`，整体以 root 跑） | `backend/nftables-web.init:292-295` |
| 认证网关 `auth_gateway.py` | `backend/nftables-web-auth.init:356-358` → `AUTH_DROP_UID=$NFTWEB_UID … python3 auth_gateway.py` | **nftweb**（uid 1000 段；init 里降权后还要复核一次身份） | `backend/nftables-web-auth.init:344-363` |

代码里反复确认这个分工：`app.py:30`「`nftables-web-session-secret` 0600 root:root ← **只有面板(root)能读**」；
`app.py:63-66`「认证网关（**降权到 nftweb**）是独立进程」。

**这条对结论的意义**：下文凡是写「降权面板拿不到」的结论，**对面板本体（root）不成立**。
面板本体以 root 运行时，直连本地 ubus socket 在**权限上**是可行的 —— 但「可行」≠「该做」，
理由见 B.4。真正受降权限制的只有网关。

⇒ 报告里所有权限标注按 **「面板本体(root)」** 与 **「网关(nftweb)」** 两栏区分，不要笼统写「降权面板」。

## 一、A 类：UCI 配置面

### A.1 `/etc/config/` 默认有哪些文件 `[文档]`

OpenWrt 官方 UCI 文档给出的基础清单：

| 文件 | 内容 | 面板价值 |
|---|---|---|
| `/etc/config/system` | hostname、timezone、log_size、ttylogin、urandom_seed、`config timeserver` 段 | **高**（主机名 / 时区 / 日志水位） |
| `/etc/config/network` | switch、interface、route | **高**（已有部分解析） |
| `/etc/config/dhcp` | dnsmasq / odhcpd：DNS、DHCP、DHCPv6 | 中 |
| `/etc/config/firewall` | NAT、包过滤、端口转发 | 中（面板已有自己的规则表） |
| `/etc/config/wireless` | 无线设备与网络定义 | 中（**`.232` 无无线硬件 ⇒ 实际价值 0**）`[实证]` |
| `/etc/config/dropbear` | SSH 服务端选项 | 中（安全体检用） |
| `/etc/config/timeserver` | rdate 时间服务器列表 | 低（21.02+ 已被 `timesync` 取代，见下） |

其它可选段：`ahcpd`/`aiccu`/`dhcp6c`/`dhcp6s`/`gw6c`/`radvd`/`fstab`/`hd-idle`/`etherwake` 等。

**[注意] 「默认存在」的准确含义** `[文档]`：
`base-files` 的 `conffiles` 清单里**只有 `/etc/config/network` 与 `/etc/config/system`**
（见 `package/base-files/Makefile` 的 `Package/base-files/conffiles`）。
`dhcp`/`firewall`/`wireless`/`dropbear` 这些来自**各自的包**（dnsmasq / firewall4 / wpad / dropbear），
**没装对应包就没有那个文件** ⇒ 面板必须「文件不存在 = 跳过」，不能当异常。

**版本差异（必须处理）** `[文档]`+`[推断]`：
- 官方 UCI 文档列的是 `/etc/config/timeserver`（rdate 时代）；**21.02 起 OpenWrt 改用
  `timesync` 包（chrony）**，配置文件名变为 `/etc/config/timesync`。
  25.12 分支的 `uci-defaults` 里存在 `15_migrate-time-zonename`（时区迁移脚本），印证这条演进。
  ⇒ 面板**不要写死**段名，按「存在哪个读哪个」处理。
- 25.12 已全面切到 **apk**（`CONFIG_USE_APK`），opkg 是 24.10 及更早。
  源码佐证：`include/image.mk` 的 `Image/Manifest` 按 `$(CONFIG_USE_APK)` 分叉成
  `apk list --quiet --manifest` 或 `opkg list-installed`；
  `base-files/Makefile` 里 `CONFIG_USE_APK` 分支建 `/etc/apk/keys`、删 `13_fix-group-user`，
  否则建 `/etc/opkg`。

### A.2 UCI 的只读查询方式：哪种在降权下可行 `[文档]`+`[推断]`

| 方式 | 机制 | 降权可行性 | 评价 |
|---|---|---|---|
| `uci show <pkg>` | 调 `/sbin/uci` | 不需要 root（只读文件） | 可行，但每次 fork 子进程；输出需解析 |
| `uci get <pkg>.<sec>.<opt>` | 同上 | 不需要 root | 同上，且**一个字段一次 fork** |
| **直接读 `/etc/config/<pkg>` 解析** | `open()` | 不需要 root（只要文件权限允许） | **推荐**：零 fork、可控、与现有 `parse_uci_config` 同构 |

**`uci` 二进制在 OpenWrt 上默认存在吗？** `[文档]` **是。**
官方 UCI Technical Reference 明确：`uci` 与 `libuci` 是两个包，`uci` 安装 `/sbin/uci`（可执行）
+ `/lib/config/uci.sh`（兼容 wrapper），是 OpenWrt 基础组件（LuCI 依赖 libuci，
netifd / firewall4 / dnsmasq 等系统服务都依赖 uci 配置）。
**本项目已实证依赖它**：`setup/setup.sh` 多处直接 `uci set … && uci commit …`
（如 `setup.sh:2383` 改 uhttpd、`setup.sh:2459` 改 nginx）。

**[注意] 权限陷阱** `[推断]`：
`/etc/config/network` 里存着 **PPPoE 拨号口令**。UCI 落盘时先 `mkstemp` 建临时文件
（默认 0600）再 `rename`，而 `uci_file_commit` 末段是
`chmod(filename, statbuf.st_mode)` + `rename()` —— **沿用原文件权限**
（`project/uci` 的 `file.c`）。所以：
- 出厂 `/etc/config/network` 的权限位取决于镜像构建，**具体位需真机验证**；
- 一旦是 0600 root:root，**网关（nftweb）读不到** ⇒ 面板若把 network 配置放进
  公网可达的网关侧页面，就是凭据泄露面；
- ⇒ **结论：任何要显示的 UCI 字段，必须做「敏感字段白名单/黑名单」，绝不能整段 dump。**

### A.3 项目现有 `parse_uci_config` 的坑 `[实证]`

`backend/app.py:3462-3511` 的 `parse_uci_config(path)` 是**针对 network 段定制**的：

1. **只认三个 section 名**：`config interface 'lan'` / `'wan'` / `'wan6'`；
   其它任何 `config xxx` 行都走 `elif line.startswith("config "): current_section = None` 把状态清掉。
   ⇒ 通用化时**不能**沿用这种「只认固定名字」的白名单。
2. **匿名分段完全不支持**：`config system`（无引号名）不会被任何分支命中 ⇒ 值全丢。
   而 `/etc/config/system` 恰好就是匿名段（`config system` + `option hostname 'OpenWrt'`）。
3. **list 值不支持**：`list server '0.openwrt.pool.ntp.org'` 这类多值项会被整条跳过。
   `timeserver`/`timesync` 的 NTP 服务器列表就是 list。
4. **类型 vs 名字混为一谈**：UCI 语法里 `config foo 'bar'` 的 `foo` 是**类型**、`bar` 是**名字**；
   匿名段（`config foo`）在 UCI 里用 `@foo[0]` 索引。现有代码没区分。
5. **引号形式多样**：`option x 'v'`、`option x "v"`、`option x v`（无引号）都合法。
   UCI 源码 `project/uci` 的 `file.c` 里 `parse_str` 明确处理了单引号 / 双引号 / 无引号三种，
   并支持 `\` 转义 ⇒ 通用解析器应对齐这个行为。
6. **`include` 指令**：`/etc/config/<pkg>` 支持 `include` 引用其它文件
   （uci 的 `uci_import` 会处理 `package` 切换）。直接读文件**不会**跟随 include
   ⇒ 要么不支持并在 UI 上说明，要么自己实现。
7. **注释**：`#` 整行注释 + **行尾注释**（UCI 的 `parse_str` 里 `#` 会终止该行）。
   现有解析器未处理行尾注释 ⇒ 注释里出现的 `option` 字样会被误当配置。

> ⇒ 若要做通用 UCI 读取，**建议不要扩展 `parse_uci_config`**，而是新写独立模块
> （如 `uci_parser.py`），返回 `{package: {sections: {type: [{name, options:{}, lists:{}}]}}}`，
> 并单独维护敏感键黑名单（password / secret / key / token / passwd / psk）。

### B.1 内置对象与 `system` 对象能拿到什么 `[文档]`

### B.2 `ubus call system board` 需要什么权限？降权能直连本地 socket 吗？ `[文档]`+`[推断]`

**ubusd 自己有一套 ACL**（`project/ubus` 的 `ubusd_acl.c`）：
- ACL 目录是 **`/usr/share/acl.d`**（`const char *ubusd_acl_dir = "/usr/share/acl.d";`），
  每次加载 `*.json`，格式 `{"<group>": {"access": {"<object>": ["<method>"]}}}`。
- 判定函数 `ubusd_acl_check()` 的**第一行**：
  ```c
  if (!cl || !cl->uid || !obj) return 0;   /* uid 0 直接放行 */
  ```
  ⇒ **uid 0（root）调用任何 ubus 对象都不受 ubusd ACL 限制。**
- 非 root 则必须在 `/usr/share/acl.d/*.json` 里有对应条目才放行；加载时还检查文件
  属主必须是 root、权限不得 group/other 可写。

**⇒ 对面板本体（root）：本地 socket 直连 `ubus call system board` 在权限上可行。** `[推断]`
（依据是上面 uid 0 豁免代码；**socket 路径与连接方式仍需真机验证**）。

**对网关（nftweb，非 root）：需要 `/usr/share/acl.d/` 里有授权条目，否则被拒。**
而这正是任务要求里「不写系统文件」的死结：不改 ACL 文件 ⇒ 网关拿不到 `system.*`。

### B.3 `POST /ubus` 为什么会被 ACL 挡？机制是什么？ `[文档]`

这里有**两套完全不同的 ACL**，必须分清（项目现有注释只提了一套，容易误导）：

| # | ACL 目录 | 由谁加载 | 管什么 |
|---|---|---|---|
| 1 | **`/usr/share/acl.d`** | **ubusd**（`ubusd_acl.c` 的 `ubusd_acl_load()`） | **谁能连 ubus socket 调哪个对象的哪个方法**（按 uid/gid） |
| 2 | **`/usr/share/rpcd/acl.d`** | **rpcd**（`project/rpcd` 的 `session.c`，`rpc_login_setup_acls()` 遍历 `RPC_SESSION_ACL_DIR "/*.json"`） | **登录后某个 session 能调哪些 ubus 方法**（按 access group） |

`RPC_SESSION_ACL_DIR` 的定义（`project/rpcd` 的 `include/rpcd/session.h`）：
```c
#define RPC_SESSION_ACL_DIR  INSTALL_PREFIX "/share/rpcd/acl.d"
```
⇒ 即 **`/usr/share/rpcd/acl.d`**（与项目现有注释一致 `[实证]` + `[文档]`）。

`POST /ubus` 的路径：uhttpd → rpcd → 先 `session login`（拿 session id）→ 再带 session id
调目标对象 → rpcd 用该 session 的 ACL 校验。**默认没有任何 access group 授权 `system.*`
给面板用的用户** ⇒ 被拒。这就是项目注释「`/usr/share/rpcd/acl.d/` 里默认没有任何规则
授权 `system.*`」的准确含义。

`session login` 本身需要**设备 root 口令**：`rpc_login_test_login()` 从 `/etc/config/rpcd`
的 `config login` 段取 username/password 哈希，`rpc_login_test_password()` 走 `crypt()` 比对。

**[注意] 一个必须知道的新变化（2026-10-28 上游合入）** `[文档]`：
rpcd master 刚合入 commit `469d785`「session: enforce session ACLs for non-root ubus callers」。
提交说明写得很直白：

> Reaching rpcd over ubus is treated as authorisation: `rpc_file_access()` and its three
> `uci.c` siblings return true outright when a request carries no `ubus_rpc_session` …
> Check every incoming call from the libubus pre-invoke callback: a caller ubusd reports
> as non-root must satisfy the session ACL … with the default session when the request
> carries no id.

代码（`project/rpcd` 的 `session.c`，`rpc_session_pre_invoke`）：
```c
if (!req->acl.user || !strcmp(req->acl.user, "root") ||
    (method->tags & RPC_SESSION_TAG_OPEN))
        return 0;                       /* root 与 session 自身的 auth 方法不受限 */
...
if (!rpc_session_access(sid, "ubus", obj->name, method->name))
        return UBUS_STATUS_PERMISSION_DENIED;
```
该提交**依赖 openwrt/ubus#27 的 `pre_invoke`**，目前只在 rpcd master，
**25.12 分支大概率没有** ⇒ 版本差异必须标注 `[推断]`。

**⇒ 趋势判断** `[推断]`：上游正在把「本地 ubus socket 直连」逐步收紧到「必须持合法 session」。
即使今天 root 能直连，**依赖它做功能是有风险的**，且对网关（nftweb）现在就不通。

### B.4 「有没有办法在不写系统文件的前提下让面板读到 `system.*`？」

| 路径 | 面板本体(root) | 网关(nftweb) | 要写系统文件吗 |
|---|---|---|---|
| **A. 直读 `/proc`、`/sys`、`/etc`（现有 device_info.py 路线）** | 可 | 可 | 否 |
| **B. `ubus` CLI 直连本地 socket** | 权限上可行 `[推断]` | **不可**（需 `/usr/share/acl.d` 授权） | 否（但引入 fork + 阻塞风险） |
| **C. `POST /ubus` 走 HTTP** | 需 root 口令 `session login` | 同左 | 否（但要持设备 root 口令 = 扩大凭据面） |
| **D. `rpc-sys packagelist`（ubus 方式）** | 同 B/C | 不可 | 否 |
| **E. 直接读包数据库文件**（见 D.3） | 可 | 可 | 否 |
| **F. 读 procd 状态文件 + `/proc`**（见 D.2） | 可 | 可 | 否 |

⇒ **答案：能，但只能走只读文件路线。** ubus/rpcd 两条路要么被 ACL 挡，要么必须持有
设备 root 口令（`session login` 要 `/etc/shadow` 的密码哈希，`rpc_login_test_password`
走 `crypt()`）——**后者与项目已确立的「凭据分离 / 最小暴露面」原则直接冲突**
（`app.py:12-33`、`app.py:8580-8588`）。**结论：不建议面板依赖 ubus。**

### B.5 一个不写系统文件也能拿到的只读替代：`/usr/lib/os-release` `[文档]`

`procd` 的 `system board` 读的 release 信息来自 **`/usr/lib/os-release`**
（不是 `/etc/openwrt_release`）。而 `base-files` 里 **`/etc/os-release` 是指向
`/usr/lib/os-release` 的软链**（`package/base-files/files/etc/os-release` → `../usr/lib/os-release`，
cgit 目录树里可见该符号链接条目）。

`/usr/lib/os-release` 的字段（由 procd 的 `system.c` 解析逻辑直接印证字段名）：
`NAME`→distribution、`VERSION`→version、`BUILD_ID`→revision、`VERSION_CODENAME`→codename、
`OPENWRT_BOARD`→target、`OPENWRT_RELEASE`→description、`OPENWRT_BUILD_DATE`→builddate、
`FIRMWARE_URL`→firmware_url、`OPENWRT_DEVICE_MANUFACTURER`→manufacturer。

⇒ **`/usr/lib/os-release` 是「固件身份」的权威单一来源**，比 `/tmp/sysinfo/model` 强：
同时含**版本、目标平台、编译日期、固件下载 URL、设备厂商**。
⇒ **建议**：`device_info.py` 现在读 `/etc/openwrt_release`（DISTRIB_* 格式），
**应补读 `/usr/lib/os-release`** —— 两者字段不同、互不覆盖（DISTRIB_TARGET 与 OPENWRT_BOARD
语义接近但不完全等价）。

## 三、C 类：设备身份信息

### C.1 `/tmp/sysinfo/*` 有哪些文件？哪些稳定、哪些运行时生成？ `[文档]`+`[推断]`

**`base-files/Makefile` 的 install 段有一行硬证据**：

```make
$(LN) /tmp/sysinfo/board.json $(1)/etc/board.json
```

⇒ **`/etc/board.json` 是指向 `/tmp/sysinfo/board.json` 的软链**。
这同时说明：**`/tmp/sysinfo/` 是运行时生成目录**，`board.json` 与其它 sysinfo 文件**同源**。

`procd` 的 `system.c` 里明确出现的 sysinfo 文件（硬证据）：

| 文件 | 被谁读 | 内容 | 稳定性 |
|---|---|---|---|
| `/tmp/sysinfo/model` | procd `system board` | 真实硬件型号（如 `GL-MT6000`） | **运行时生成**（tmpfs，重启后由 target 的 board 脚本重写）`[推断]` |
| `/tmp/sysinfo/board_name` | procd `system board` | board 标识（如 `tl-wr1043nd-v4`） | 同上 |
| `/tmp/sysinfo/image_type` | procd `system board` | 镜像类型（sysupgrade/factory 等） | 同上，**可选**（procd 注释原文：「Strictly optional, don't try to guess if it is not explicit.」） |
| `/tmp/sysinfo/board.json` | `/etc/board.json` 软链指向它 | 设备元信息 JSON（含 `system` 对象） | 同上 |

**生成方式** `[文档]`：`base-files` 的 `ImageConfigOptions` 里，开了
`CONFIG_TARGET_DEFAULT_LAN_IP_FROM_PREINIT` 时会生成 `/etc/board.d/99-lan-ip`，
脚本里用 `json_select network` / `json_add_string ipaddr` / `board_config_flush`
往 board.json 里写 LAN IP ⇒ **board.json 是运行时被 board.d 脚本改写的 JSON**，
不是编译期常量。

⇒ **稳定性判断** `[推断]`：
- 这些文件在**运行时**存在，重启后重新生成 ⇒ 内容稳定但**生命周期是 tmpfs**；
- 面板读不到时应当显示「未知」，**不能据此断言「设备无型号」**；
- `/etc/board.json` 虽在 `/etc` 下（看起来像持久文件），**但它只是 `/tmp` 的软链**，
  同样是运行时产物 —— 这一点**很容易被误判**。

**`.232`（x86_64）上 `/tmp/sysinfo/model` 是否存在？** —— **未验证**（设备下线）。
x86 target 是否提供这些文件取决于该 target 的 base-files 实现 `[推断]`，需真机确认。
现有 `device_info.py` 已做「model → board_name → None」降级链，这是对的 `[实证]`。

### C.2 `/etc/board.json`：比 `/tmp/sysinfo/model` 强在哪？ `[文档]`+`[推断]`

**格式（有源码硬证据）**：`base-files` 的 `package/base-files/files/lib/functions/system.sh`
里 `get_mac_label_json()` 直接解析它：

```sh
get_mac_label_json() {
        local cfg="/etc/board.json"
        ...
        json_load "$(cat $cfg)"
        if json_is_a system object; then
                json_select system
                json_get_var macaddr label_macaddr
```

⇒ **结构事实**：顶层含一个 **`system` 对象**，其下有 **`label_macaddr`** 字段（设备标签 MAC）。
（`get_mac_label()` 的优先级是：先试 device-tree 的 `/proc/device-tree/aliases/label-mac-device`，
再退到 board.json ⇒ **x86 无 device-tree，只能靠 board.json** `[推断]`。）

**比 `/tmp/sysinfo/model` 强在哪** `[推断]`：
1. **一个文件里装下多类元信息**（JSON 结构化），而 sysinfo 是散落的纯文本；
2. **含设备标签 MAC**（`system.label_macaddr`）—— 这是身份信息里最有用的字段之一；
3. **JSON 可整体解析**，不必为每个字段猜一个路径。

**比 `/tmp/sysinfo/model` 弱在哪 / 不能替代什么** `[推断]`：
- **生命周期相同**（都是 `/tmp` 产物），没有「更持久」的优势；
- **不含**版本 / 内核 / 编译日期 —— 那些在 `/usr/lib/os-release`；
⇒ **正确用法是三者互补**：`/usr/lib/os-release`（版本与目标）+ `/tmp/sysinfo/model`+`board_name`（硬件型号）+ `/etc/board.json`（JSON 元信息与标签 MAC）。

**[注意] 未验证**：`/etc/board.json` 的**完整字段集合**（除 `system.label_macaddr` 外还有什么）
本轮未从源码找到权威清单（openwrt.org 的 wiki 页本轮被反爬拦截，未能直读）。
⇒ **实施前必须先在设备上 `cat /etc/board.json` 看真实结构。**

### C.3 `/etc/openwrt_release` vs `/etc/os-release` vs `/etc/banner` `[文档]`

| 文件 | 内容 | 来源 | 稳定性 |
|---|---|---|---|
| `/etc/openwrt_release` | `DISTRIB_ID='OpenWrt'`、`DISTRIB_RELEASE='25.12.5'`、`DISTRIB_REVISION='r1'`、`DISTRIB_TARGET='x86/64'` | `base-files/files/etc/openwrt_release`（构建期生成 + `VERSION_SED_SCRIPT` 替换） | 编译期常量 |
| `/etc/os-release` | **指向 `/usr/lib/os-release` 的软链** | 同目录树 | 编译期常量 |
| `/usr/lib/os-release` | 标准 os-release 字段 + `OPENWRT_*` 扩展（见 B.6） | 构建期生成 | 编译期常量，**字段最丰富** |
| `/etc/banner` | 登录时的 ASCII 艺术字（`base-files/files/etc/banner`，372 字节） | 同上 | 编译期常量，**无结构化信息** |

⇒ **`/etc/banner` 不值得采集**（纯装饰文本，无机器可读字段）。
`/etc/openwrt_release` 与 `/usr/lib/os-release` **互补而非重复**，两者都读成本极低。

顺带记录几个同源的运行时软链（做「文件系统体检」时可能有用）`[文档]`：
`/etc/mtab` → `/proc/mounts`；`/etc/resolv.conf`、`/etc/TZ`、`/etc/localtime` → `/tmp/*`；
`/var` → `/tmp`（除非 `CONFIG_TARGET_ROOTFS_PERSIST_VAR=y`，那时 `/var/run` → `/tmp/run`）。

## 四、D 类：系统运行面

### D.1 进程列表：降权能列出所有进程吗？ `[推断]`

**能列出 PID 和 `stat`，但看不全别人的 cmdline**：

| 数据 | 可见性 |
|---|---|
| `/proc/<pid>/stat`、`/proc/<pid>/status` | **任何用户可读**（字段级：Name/State/PPid/Uid）`[推断]` |
| `/proc/<pid>/cmdline` | **属主可读**；默认 mount 下他人进程的 cmdline 也可读，但若内核以 `hidepid=2` 挂载 `/proc` 则不可读 `[推断]`。**OpenWrt 默认不启用 hidepid** `[推断]` ⇒ 大概率可读，**需真机验证** |
| `/proc/<pid>/environ` | **仅属主可读** ⇒ 面板(root) 可读、网关(nftweb) 不可读。**绝不要采集**：里面全是环境变量，可能含 token |

**⇒ 推荐做法**：只采集 `/proc/<pid>/stat` 的 `pid / ppid / comm / state / utime+stime`
+ **可选** cmdline（读不到就显示「未知」），**不采集 environ**。
在 `/proc` 下遍历 PID 目录优于 `ps`：不 fork，且 BusyBox `ps` 输出格式各版本不一致
（与 `device_info.py` 里不解析 `df` 输出、不用 `ip`/netlink 的理由一致 `[实证]`）。

### D.2 服务状态：`/etc/init.d/<name> status` 还是 `ubus call service list`？ `[文档]`

| 方式 | 机制 | 权限 | 评价 |
|---|---|---|---|
| `ubus call service list` | procd 的 `service` 对象 | root 直连可行；非 root 需 ACL | 数据最全（pid、command、respawn 次数、triggers、validators） |
| `/etc/init.d/<name> status` | `rc.common` → procd | 需要能问 procd | **每个服务一次 fork**，输出格式不稳定 |
| **`/etc/init.d/` + pid 文件 + `/proc`（纯文件）** | 遍历目录 | 任何人 | 无 fork；拿不到 respawn 计数 |

**不依赖 ubus 的等价替代** `[推断]`：
- 遍历 `/etc/init.d/*` ⇒ 哪些服务存在；
- 读各服务的 `/var/run/<name>.pid`（procd 的 `service_running` 就是靠 pid 文件判的）
  ⇒ 是否在跑；
- 交叉 `/proc/<pid>` 拿 cmdline 与状态；
- `ls -l /etc/rc.d/S*`（符号链接指向 init.d 脚本）⇒ 是否开机自启。

⇒ **落地建议**：做「服务清单 + 运行状态」时**优先纯文件路线**
（`/etc/init.d/` + pid 文件 + `/proc`），把 `ubus call service list` 作为**可选增强**。

### D.3 已安装软件包列表：apk vs opkg `[文档]`

**这是本轮最有价值的一条新发现** —— rpcd 的 `rpc-sys` 插件（`project/rpcd` 的 `sys.c`）
在实现 `packagelist` 时，**源码注释直接写明了两个包数据库的路径与字段对应关系**：

```
 * Status file fields, /usr/lib/opkg/status vs /lib/apk/db/installed
 *                        opkg              apk
 * PACKAGE_ABIVERSION     "ABIVersion"      "g:openwrt:abiversion="
 * PACKAGE_AUTOINSTALLED  "Auto-Installed"  package listed in 'world', not a db field
 * PACKAGE_NAME           "Package"         "P"
 * PACKAGE_STATUS         "Status"          package listed in db, not a status value
 * PACKAGE_VERSION        "Version"         "V"
```

⇒ **权威路径** `[文档]`：

| 包管理器 | 已安装包数据库 | world 文件（用户显式安装的） |
|---|---|---|
| **apk**（`.232` 用的是这个） | **`/lib/apk/db/installed`** | **`/etc/apk/world`** |
| **opkg**（24.10 及更早） | **`/usr/lib/opkg/status`** | `/etc/opkg/world` `[推断]` |

（`base-files/Makefile` 佐证 apk 时代建 `/etc/apk/keys`、否则建 `/etc/opkg` `[文档]`。）

**⇒ 面板该怎么读** `[推断]`：
- **不要用 `apk list --installed` / `opkg list-installed`**：CLI 行为随版本变化
  （项目已有 apk 3.0.5 的多条踩坑记录 `[实证]`），且要 fork。**直接读数据库文件更稳。**
- **全量还是只读 world？** rpcd 的 `packagelist` 默认只返回 world 里的（`all=true` 才全量）。
  对面板而言：**「全部已安装包」做体检输入，「world 里的」标成「用户手动装的」** —— 两者都给，用不同字段区分。
- apk 的 `/lib/apk/db/installed` 是 **ADB 格式**（不是 opkg 的扁平块），
  解析要注意 `P:` / `V:` / `g:openwrt:abiversion=` 前缀 + **空行分隔记录**
  （rpcd 的解析器正是按空行切记录 `[文档]`）。
- **文件权限**：通常 world-readable `[推断]` ⇒ 网关也能读。

**⇒ 额外价值**：包列表能直接支撑「版本对比 / 装了哪些 luci-app / 与本项目相关包的版本」等体检功能。

### D.4 磁盘与挂载点：除了 `/` 还有哪些？ `[文档]`+`[推断]`

**procd 自己的 `system info` 只报两个**：`/`（root）与 `/tmp`（tmp）
（`system.c` 的 `fslist[] = { "/", "root", "/tmp", "tmp" }`）`[文档]`。

**OpenWrt 上实际关心、且现有采集器没覆盖的挂载点** `[推断]`：

| 挂载点 | 类型 | 为什么要看 |
|---|---|---|
| **`/overlay`** | ext4/ubifs（可写层） | **最重要** —— 固件升级、包安装、配置改动全写这里。**满了就装不了东西**（LuCI 升级固件会失败） |
| `/rom` | squashfs/jffs2（只读固件） | 固件本体占用 |
| `/tmp` | tmpfs | 内存盘。`.232` 的 `/var -> /tmp` ⇒ **审计日志吃的是内存** `[实证]` |
| `/dev` | devtmpfs | 一般不用 |
| `/sys` `/proc` | sysfs / proc | 只读 |
| **`/dev/mtd*` / `/proc/mtd`** | flash 分区表 | 固件分区布局（**仅 flash 设备有，x86 无**） |

**⇒ 强烈建议加 `/overlay` 占用** —— 这是 OpenWrt 上最常出问题、最该被看见的数字，
而现在面板的 `collect_storage()` 只看了 `/` `[实证]`。
注意：**`/` 的 statvfs 与 `/overlay` 在 squashfs+overlay 组合下含义不同**，
必须**单独 statvfs `/overlay`** 才准 `[推断]`。

### D.5 温度 / 风扇 `[推断]`

| 路径 | 内容 | x86 设备上有没有 |
|---|---|---|
| `/sys/class/thermal/thermal_zone*/temp` | 温度（毫摄氏度） | **可能没有**。x86 上由 `coretemp`/`k10temp` 等驱动提供，OpenWrt x86 target 默认内核**通常不含**这些模块 `[推断]` |
| `/sys/class/hwmon/hwmon*/temp*_input` | 同上 | 同上，依赖 `hwmon` 驱动 |
| `/sys/class/hwmon/hwmon*/fan*_input` | 风扇转速 | **x86 台式机 / 虚机没有风扇** `[推断]` |

**⇒ 结论**：在 `.232`（x86_64）上**温度/风扇大概率采不到** `[推断]`。
**实现方式**：遍历目录、读不到就显示「不支持 / 未知」—— **不要因为读不到就报错**，
这与 `device_info.py`「读不到就返回 None」的既有原则一致 `[实证]`。
**价值定位**：这是**面向真实实体路由器的可选项**，对当前测试机价值低。

### D.6 日志：`logread` 与 `/dev/kmsg` `[文档]`+`[实证]`

| 来源 | 机制 | 权限 | 备注 |
|---|---|---|---|
| **`logread`** | 连 `/dev/log`（unix socket）读 logd 的环形缓冲 | 需能连 `/dev/log`；**本项目已实证面板能读到**（`.224` 实测 1582 行）`[实证]` | `/etc/config/system` 的 `log_size` 控制缓冲大小（默认 128KB）`[文档]` |
| **`/dev/kmsg`** | 内核环形缓冲，**读会消费**（内核推进 read 位置） | 通常 root | **[注意] 读取有副作用** ⇒ 违反本项目只读原则 `[实证]`（`device_info.py` 明确「不执行任何会改状态的命令」） |
| `dmesg` | 读 `/dev/kmsg` | 通常 root | 同上，**有副作用** ⇒ 不用 |

**⇒ 结论**：只用 `logread`（已实证可用），**不要碰 `/dev/kmsg` 和 `dmesg`**。
`logread` 的能力已由现有 `/api/system/logs` 覆盖 `[实证]`，本轮**不需要重复建设**。

## 五、E 类：LuCI 做不到的跨域编排机会

### E.1 前提澄清：LuCI 的边界 `[文档]`

LuCI 是 OpenWrt 自带的 Web 管理界面（25.x 由 **uhttpd** 提供，80/443 `[实证]`），
是一个**独立的 Web 服务**，通过 rpcd 的 JSON-RPC 调 ubus。
其 System/Status 是**给人看的、分散的页面**。

**⇒ 面板的定位（按任务要求）：不重复实现 LuCI，只做 LuCI 做不到的事。**

### E.2 A~D 里哪些是 LuCI 上根本没有、或没有聚合在一处的？ `[文档]`+`[推断]`

| 信息 | LuCI 有吗 | 聚合在一处吗 | 判断 |
|---|---|---|---|
| `/etc/config/*` 全量配置视图 | **没有**。LuCI 按功能拆页（Network/Wireless/Firewall/DHCP…），每页只显示自己那几项 | 否 | **面板可做「配置全景」** |
| 已安装包列表 + 版本 | 有（Software 页），但只列 luci-app 视角 | 弱 | 面板可做**全量 + 与本项目相关包的聚合** |
| procd 服务实例 / respawn 次数 | **没有**（LuCI 的 Processes 页只有进程表，无 respawn 语义） | 否 | **面板可做** |
| `/overlay` 占用 | 有（Overview 里的 Flash Usage），但**不区分 overlay / rom** | 否 | 面板可做更细的 |
| 面板自身 + 反代 + 证书 + DDNS + 名单的**一致性** | **完全看不到** | — | **LuCI 做不到** |
| 内核 / 固件 / 型号的聚合 | 部分（Overview） | 部分 | 边缘 |

（LuCI 的 Status 相关 ACL 文件名与描述可佐证其页面构成：
`luci-mod-status.json` 里含「Grant access to system logs」「Grant access to the system route status」
「Grant access to wireless status display」等条目 `[文档]`。）

### E.3 哪些信息「只有面板这个位置能拿到」？理由是什么？ `[推断]`

面板同时管：**防火墙（nftables 规则集）+ 反向代理（nginx 配置）+ 证书（acme.sh）+ DDNS + 名单（白/黑名单）+ 认证网关**。
这些是**同一台设备上的不同配置域**，而 **LuCI 看不到反代、看不到证书、看不到本项目的名单、看不到面板自己的配置**。

⇒ 因此只有面板能做的检查，是**跨域一致性检查** —— 这不是「LuCI 少一个页面」，
而是「LuCI 架构上不可能有」（LuCI 是通用 OpenWrt 管理界面，不理解 Ghost Firewall 的配置结构）。

### E.4 五个具体可落地的功能点（每个都说明「为什么 LuCI 做不到」）

#### 功能点 1：设备体检总览（跨域一致性检查）

**做什么**：一次性跑一批只读检查，给出「通过 / 失败 / 待确认」清单 + 每项原始证据。

**具体检查项**（每项都有 A~D 的来源支撑）：
1. 固件/内核/型号身份是否自洽（`/usr/lib/os-release` 的 `OPENWRT_BOARD` vs `/tmp/sysinfo/model` vs `/etc/board.json` 的 `system` 对象）
2. **`/overlay` 剩余空间**是否够升级固件（D.4）
3. **防火墙规则里的死引用**：规则集引用的接口（`pppoe-wan`）在本机是否存在 ⇒ **`.232` 就是活例子：规则满屏 `pppoe-wan` 但机器没有 WAN 网卡** `[实证]`
4. **WAN 网卡缺失但配置里有 WAN 段**（`lan_if`/`wan_if` 与实际接口对不上）
5. **面板自身配置与设备实际是否一致**（面板配置里的 `lan_if` 指向的接口是否存在）
6. **降权网关读不到必需文件**（网关以 nftweb 运行，检查其依赖文件是否组可读 —— 这正是项目历史上真实踩过的坑 `[实证]`：`setup.sh:2143-2162`、`auth_gateway.py:761-769`）
7. **时间是否同步**（`/etc/config/timesync` 或 `timeserver` 是否配了、时钟是否合理）

**为什么 LuCI 做不到** `[推断]`：
- 第 3/4/5 项要读**本项目自己的**规则集与配置（`/opt/nftables-web-v2/`、`/etc/nftables/`），LuCI 不认识这些文件；
- 第 6 项要读**认证网关的运行身份与文件权限位**，那是本项目的部署结构；
- 第 1/2/7 项单独看 LuCI 都有，但**聚成「一个健康结论 + 修复动作」**是本项目的能力 ——
  LuCI 是「按页面组织」，不是「按结论组织」。

#### 功能点 2：跨域配置一致性检查（防火墙 ↔ 反代 ↔ 端口）

**做什么**：面板管了防火墙放行规则、反向代理的监听端口、面板自己的 5443/8443 端口。
检查它们**是否互相矛盾** —— 例如：反代要暴露某端口但防火墙没放行；或防火墙放行了
一个没有任何服务监听的端口（僵尸规则）。

**为什么 LuCI 做不到** `[推断]`：
LuCI 的 Firewall 页只知道它自己的 UCI 规则集，**不知道 nginx 在监听什么**。
而面板同时持有 `/etc/nginx/*`（自己管的反代）、监听状态（netstat）和 nftables 规则集
⇒ **这个三方对账只有面板能做**。LuCI 能看到 nftables 规则和 LuCI 自己配的 uhttpd，
但它看不到本项目的反代配置。

#### 功能点 3：证书 / DDNS / 域名三者的联动状态

**做什么**：证书（acme.sh 续期时间、剩余天数、证书 SAN 与域名）、DDNS（当前解析到的 IP
是否等于设备当前出口 IP）、反代（上游指向的域名）三者放一起，显示「这条链路哪一环断了」。

**为什么 LuCI 做不到** `[推断]`：
LuCI 没有 acme.sh 的证书状态视图，也没有本项目的 DDNS 写回逻辑，
更没有「反代域名 ↔ 证书 SAN ↔ DDNS 记录」这条链的概念。
⇒ **只有面板知道这三个域的对应关系**（都在 `/etc/nftables/nftables-web-config.json` 里）。

#### 功能点 4：可解释的「设备身份档案」

**做什么**：把散落的身份信息聚成一张档案：型号、board_name、固件版本、内核版本、
目标平台、编译日期、设备厂商、固件下载 URL、根文件系统类型、overlay 占用、内存、CPU、
包管理器与包总数。

**为什么 LuCI 做不到（部分）** `[推断]`：
LuCI 的 Status→Overview 只显示其中一部分，且**不显示** `/usr/lib/os-release` 里的
`OPENWRT_BUILD_DATE` / `FIRMWARE_URL` / `OPENWRT_DEVICE_MANUFACTURER`
（procd 解析了但 LuCI 不展示），也**不区分 overlay 与 rom 的占用**。
面板的价值在于「一次给全 + 带证据路径」，而不是「多几个字段」。

#### 功能点 5：只读的「配置基线快照与变更留痕」

**做什么**：记录每次系统信息采集的结果，做基线快照，后续页面显示「自上次记录以来变了什么」
—— 固件版本变了、CPU 型号变了、网卡数量变了、`/overlay` 掉了一大截。

**为什么 LuCI 做不到** `[推断]`：
LuCI 是**无状态**展示界面，不保存历史快照，也就没有「变化」这个概念。
而面板已有 `/var/log/nftables-web-auth.log` 这样的落盘习惯（`auth_gateway.py:62`）
⇒ **基线快照的存储位置与轮转策略是现成的**（注意 `/var` 在 tmpfs 上，需考虑持久化位置）。
这是**增量价值**，不是替代 LuCI 的价值。

### 二、修正一处表述（6.1 第 2 项）

报告建议「**补读** `/usr/lib/os-release`」。复核后要改一处说法：
**不是"再读一个文件"，而是"当前实现读不到它"**。

`backend/device_info.py:119` 的通用发行版分支写的是：

```python
    # ── 通用发行版：/etc/os-release ──
    if not out['pretty_name']:
        txt = _read_text('/etc/os-release', 8192)
```

而 OpenWrt 上 `/etc/openwrt_release` **必定存在** ⇒ `out['pretty_name']` 必有值
⇒ **这个分支在 OpenWrt 上永远不执行** ⇒
`/usr/lib/os-release` 里的 `OPENWRT_BOARD` / `OPENWRT_BUILD_DATE` /
`FIRMWARE_URL` / `OPENWRT_DEVICE_MANUFACTURER` 四个字段**一条都读不到**。

⇒ 准确的说法：那段代码是「**互斥兜底**」，不是「**并列采集**」。
要拿 OpenWrt 扩展字段，必须把 `/usr/lib/os-release` 从互斥分支里拿出来，
与 `/etc/openwrt_release` **并列**采集（两者字段不重叠，互不覆盖）。

（顺带：OpenWrt 上 `/etc/os-release` 本身就是 `/usr/lib/os-release` 的软链，
所以不必单独再读 `/usr/lib/os-release`；但两个路径都试更稳妥。）

### 四、复核顺带确认的一件事（对本项目的影响）

报告 0.1 纠正了任务简报的前提 —— **面板本体是 root，不是降权账号**。

这条不只是措辞：它决定了**哪条采集路线可用**。
若面板确实是降权账号，`system.*`（ubus）这条路就彻底堵死；

且网关（nftweb）这条路本来就不通、而纯文件路线零 fork、零耦合。

⇒ **结论不变，但理由更准了**：不依赖 ubus 是**架构选择**，
不是被权限逼的无奈。写文档时别把「不能」写成「不必」的理由被推翻。
