## 0. 一句话

DDNS「不断删除重新上传」的**直接成因**是：更新记录用的是「**删除 + 新增**」，
每轮换一条记录（RecordId 必变），控制台看上去就是记录被删掉又重建。

现在改成阿里云官方的 `UpdateDomainRecord` **原地更新**：

| 情形 | 动作 |
|---|---|
| 值没变 | **一个写接口都不调** |
| 值变了 | 只调 `UpdateDomainRecord`，**RecordId 不变** |
| 记录不存在 | 才调 `AddDomainRecord` |
| 任何情况 | **永不调用 `DeleteDomainRecord`** |

⇒ 用户诉求「地址没变就跳过上传」现在是**天然满足**的，
而且控制台上那条记录从此**不再消失重建**。

## 1. 唯一自动入口与「测试按钮测不出问题」

`[源码]` 全仓只有两处会改 DNS 记录：

| 入口 | 位置 | 触发方式 |
|---|---|---|
| 设备 cron 脚本 | `app.py` 的 `_generate_ddns_update_script()` 生成物 | `*/10 * * * *` 自动 |
| 面板函数 `_aliyun_ddns_update()` | 只被 `/api/aliyun-ddns/test` 调用 | 人工点「测试」 |

前端只有 GET 列表 / POST 保存配置 / 手动测试按钮，**不会自动删加**。

⚠️ 顺带修掉一个**结构性的误导**：面板「测试」按钮原来给 A 记录传的是
**阿里云上现存的旧值**（`app.js` 里 `value: rec.Value || rec.value`），
后端拿它和阿里云的值一比必然相等 ⇒ **永远返回「IP 未变化，无需更新」**。
也就是说这个按钮**结构上不可能**测出自动更新到底通不通，点一百次也是绿的。

现在 A 记录也传空值，由后端自己取「当前」公网 IPv4 —— 与设备上的 cron 脚本
同一条取值路径，测的才是真正会跑的那条路。

## 2. 同批修掉的九件事

| 编号 | 问题 | 修法 |
|---|---|---|
| D1 | 「删除+新增」⇒ RecordId 每轮都变 | 改 `UpdateDomainRecord` 原地更新 |
| D2 | 只按 RR+Type 匹配 ⇒ **多线路记录被误改** | 匹配时带上 `Line` 判定，**只动 default 线路** |
| D3 | 删成功、加失败 ⇒ 域名直接解析不到 | 永不调用 Delete ⇒ 这类风险消失 |
| D3b | 一条记录抛异常 ⇒ 整轮剩下的都不处理 | 每条记录独立 try |
| D4 | 正常路径零日志 ⇒ 「一直删加」在设备上不留痕迹 | 每轮写一行摘要到 `/var/log/nftables-web-ddns.log` |
| D5 | 取不到公网 IP 时**拿旧值去覆盖**阿里云上正确的地址 | 取不到就**跳过本轮** |
| D6 | 查询默认 PageSize=20 ⇒ 目标记录可能落在首屏之外 | 显式 `PageSize=500` |
| D7 | cron 脚本的配置路径写死 / 中转目录用错环境变量名 | 统一读 `NFTABLES_WEB_ALIYUN_CONFIG` 与 `NFTABLES_WEB_DDNS_RELAY_DIR` |
| D8 | 配置里的 `rr`/`type` 只认小写键 ⇒ 存量配置永远匹配不上 | 大小写两种键都认 |
| D9 | 改的是**生成模板**，设备上那份脚本不会自动更新 | 部署后必须点一次「保存配置并生成脚本」 |

### D2 是这一批里最危险的一条

阿里云允许**同一 RR+Type 按线路（电信/联通/移动…）存在多条合法记录**。
旧代码只按 RR+Type 匹配，拿到第一条就改 —— **如果那条是电信线路，
用户配的电信解析就被改成了 default 的值**。
这不是「多了一条记录」的问题，是**改错了别人的配置**。

阿里云返回记录的顺序**不保证**，`matched[0]` 落到哪条是随机的。

### 另加两处（真机跑脚本时暴露的）

- **配置文件不存在时**原来抛 `FileNotFoundError`，日志里写的是
  「整体失败：FileNotFoundError ...」—— 用户看不出是「还没配置」还是「配置坏了」。
  现在先判断文件在不在：不在就写一行说明并**安静退出（rc=0）**。
- `datetime.utcnow()` 在 Python 3.13 已弃用，cron 每跑一次都往 stderr 打
  一条 `DeprecationWarning`。改成 timezone-aware 的 `now(timezone.utc)`，
  取值完全等价（阿里云要的就是 UTC 时间戳）。

## 3. 判据怎么设计的

### 3.1 判据落在「设备上真正会跑的那条路径」上

`[实证]` 测试不是读源码断言「应该出现某段文字」，而是：

1. 用 **AST** 从 `backend/app.py` 里提取 `script_content`（生成出来的脚本原文）
   —— 不用正则切，正则差一个字符不会报错，只是内容变了；
2. 起一个**本地假阿里云服务端**（HTTP），记录每一次 API 调用；
3. 把脚本的端点 / 配置路径 / 日志路径 / IP 源全部指向本地（脚本支持注入）；
4. **子进程真跑脚本**，断言它**发出的 API 调用序列**。

⇒ 判据问的是「它到底调了哪些阿里云接口」，而不是「代码里写没写某个函数名」。

### 3.2 假服务端不校验签名，但断言签名参数在

签名逻辑没改，本轮不重复测。

### 3.3 IP 源做成可注入，是因为「测试不能真出网」

若测试真去访问 `ipv4.icanhazip.com`：结果会随时间变、网络不通就假失败，
那样的测试等于没有。所以脚本支持 `NFTW_IPV4_SOURCES` 指向本地假源。

⇒ 顺带把「取 IP 的源会返回 IPv6」这件事也钉住了：
**只有合法 IPv4 才算数**，IPv6 是另一个地址族、另一条出口。

### 3.4 本轮测试抓到的两个真 bug

| bug | 怎么发现的 | 性质 |
|---|---|---|
| 改写 cron 脚本时**把「从配置读 value」这一步弄丢了** ⇒ CNAME 等非 A 记录永远被跳过 | 「IPv6 同一地址的不同写法判为未变」那条断言跑出的调用序列是空的 | 静态看代码不容易发现；真跑脚本才暴露 |
| 取证脚本把 **IPv6 当成「多出口」** ⇒ 假结论 | 本机冒烟时 ident.me 返回 `240e:...` | A 记录只认 IPv4，IPv6 必须排除出比对 |
| 取证脚本用**去重后的列表**判稳定性 ⇒ 「采样 2 次同值」被误报成「漂移」 | 同上 | 判据必须拿**原始采样**判断 |

⇒ 这三条都说明：**判据本身也会出错，而且出错时代码看起来完全正常。**

### 3.5 变异验证暴露的判据缺陷

`[实证]` 第一轮变异有 **2 处漏网**，查下来**都是判据不够硬**，不是代码问题：

- **M3（多线路）**：测试里把电信那条排在 default **后面**，
  于是去掉 Line 判定后 `matched[0]` 恰好还是 default ⇒ 测不出来。
  ⇒ 真实风险恰恰是电信那条排在**前面**（返回顺序不保证）⇒ 改成排在前面。
- **M15（前端）**：变异只加了一行注释，**根本没改代码** ⇒ 当然测不出来。
  ⇒ 改成真的把 `value: ''` 改回 `rec.Value || rec.value`。

⇒ 「变异没被抓到」的第一反应应该是**怀疑判据**，而不是怀疑代码。

`[实证]` 部署 v0.19.11 后的核对：

| 项 | 结果 |
|---|---|
| 设备端 `VERSION` | `0.19.11` |
| 设备端 `backend/app.py` md5 | `0ec688e0cc81f705bd01d783f5d4bac4` ＝ 本地 |
| 设备端 `frontend/app.js` md5 | `a2f5c1dba32317dd99fcde42c00dbba9` ＝ 本地 |
| **设备端 cron 脚本模板 md5** | `876e63dc05b4a56437a6092737bebaad` ＝ 本地（AST 提取后比对） |
| 生成的脚本在设备上编译 | 通过 |
| 脚本在设备上真跑（无配置） | **rc=0**，日志「退出：配置文件不存在（...）—— 面板上还没保存过阿里云 DDNS 配置」 |
| 脚本在设备上真跑（带假配置） | 取值链路通、查询发出并收到响应、失败被**单条隔离**、rc=0 |
| 未启用的记录 | 被正确跳过（日志里不出现） |
| **stderr** | **0 字节**（弃用警告已消除） |
| 配置指纹 | `/etc/config/network`、`firewall`、`ddns`、`nftables-web-config.json` **部署前后完全一致** |

| 面板探活 | `https://192.168.100.232:5443/` HTTP 200 |

⚠️ 设备端脚本文件是用 **AST 提取模板后写入**的，不是 `import app` 后调
`_generate_ddns_update_script()` 生成的 —— 刻意不 import：
app.py 顶层可能起后台线程（watchdog 之类），**在真机上 import 有触发防火墙
规则切换的风险**。两者的写入内容完全等价（函数体就是 `write(script_content)`），
且设备端 app.py 与本地 md5 一致 ⇒ 面板点「保存配置并生成脚本」得到的必然是同一份。

### 部署注意（D9）

改的是 cron 脚本的**生成模板**，不是设备上那份脚本文件。
部署新版本后**必须在面板上点一次「保存配置并生成脚本」**，否则设备上跑的还是旧脚本。

## 6. 还没做的

1. **根因定论还差一次现场对照**：本次修复把「动作选错」这一类**确定存在**的问题
   全部修掉了，但「每轮都触发更新」的触发条件是「本次值 ≠ 现存值」——
   若是公网 IPv4 真的在变（多出口 / CGNAT），脚本仍会每轮更新一次
   （只是**不再删了重加**，RecordId 不变）。
   ⇒ 用户侧的控制台操作日志取证（路径 A）仍需回执，才能定性。
2. **批 B（防抖）** 未做：若确认为公网 IP 在漂移，可加「连续 N 轮值一致才更新」。
3. **DDNS 成功路径仍未在有公网 IPv6 的设备上验证过**（`.232` 没有阿里云配置）。
4. 未写 Hindsight 记忆库（按用户红线）。

## 7. 本轮踩过的坑

| 坑 | 教训 |
|---|---|
| 改写 cron 脚本时弄丢了「从配置读 value」 | 重写模板最容易丢的是**数据来源**，不是控制流 ⇒ 必须有真跑脚本的测试 |
| 取证脚本把 IPv6 当成「多出口」 | 判据要按**地址族**分开：A 记录只认 IPv4 |
| 取证脚本用去重后的列表判稳定性 | 判据要拿**原始样本**判断，不能拿加工过的 |
| 变异有 2 处漏网，查下来是判据不够硬 | 「没抓到」先怀疑判据；且样本顺序要覆盖**真实顺序不保证**的情况 |
| 既有断言卡住了旧写法（`value: isAaaa ? ''`） | 改行为要连带更新既有断言，但**要保留它的捕获点**（`ipv6_source: isAaaa`），否则别的变异脚本会失去捕获点 |
| 隔离扫描一度报 `[BAD]` | 查下来是负载导致的时序假红 ⇒ 扫描结果要能**追到原始输出**复盘 |
| 原地跑变异会留下残留 | 取消正在跑的变异任务后，必须 `git checkout` 还原并核对 sha256，再跑隔离扫描 |
