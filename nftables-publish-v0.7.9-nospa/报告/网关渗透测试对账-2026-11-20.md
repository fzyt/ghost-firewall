### 2.4 T0 专项：按「公网 + 无需凭据 + 无交互」口径单独筛一遍

「T0」按最严的口径取：**攻击者位置 = EXTERNAL（公网可达）且 privileges_required = NONE
（不需要任何凭据）且 user_interaction = NONE（不用受害者配合）**，后果是认证彻底失效
或拿到路由器 root。

基线 120 条里符合这个特征的共 **41 条**。逐条处理结果：

| 处置 | 条数 | 说明 |
|---|---|---|
| 已逐行核实、判为**已修** | 21 | 机制在当前代码上已不成立（其中 CRITICAL 13 / HIGH 4） |
| 辅助键配上了、但没逐行核 | 9 | 其中 3 CRITICAL + 1 HIGH 需人工判读 |
| 完全没碰 | 11 | **最高只到 MEDIUM**（MEDIUM 7 / LOW 4） |

**⇒ 在已核实的范围内，没有 T0 级漏洞。** 逐条核过的最可疑的几条：

| 候选 | 结论 |
|---|---|
| 滑动续期吊销旧 jti，但新令牌只经 Set-Cookie 下发、被 nginx 的 auth_request 丢弃（HIGH） | **已修**。前提不成立：续期发生在 `auth_status()`，那是**客户端直接访问**的端点（nginx `location = /auth/status`），不是 `auth_request` 子请求（子请求目标是 `/_auth`）。且续期本身已收口：吊销失败落审计 `refresh_old_token_not_revoked`，`_mark_superseded()` 让旧 jti 在本进程内立即失效，新令牌照常下发 |
| 客户端 Host 头被信任用于登录跳转 / 上游请求 / Location 改写（LOW） | **已修**。全部改用 nginx 规范化过的 `$host`，不用客户端可控的 `$http_host`（P2-19） |
| 面板 init 脚本在验证替换规则集**之前**就永久停用平台防火墙（HIGH） | **已修**。顺序倒过来了：`nft -f` 装载成功（且功能性复核通过）之后才 `firewall disable`；失败则一步不动 fw4 |

### 5.1 展开讲三条最要紧的

**（1）访客页日志解析注入 —— 监控盲区**

链条：面板生成 nginx `log_format`（app.py:12082-12086）把 `$host` / `$uri` /
`$http_user_agent` / `$http_referer` 四个**客户端可控**字段原样写进带引号的格式里，
nginx 的 log_format 没有转义机制；面板的解析器（app.py:8996-9002）用一条锚定的正则，
六个引号字段全部用 `[^"]*` 匹配；读的时候 app.py:9034-9037 是
`m = _GW_ACCESS_RE.match(line.strip())` 然后 `if not m: continue` ——
**匹配不上就静默丢弃，没有计数、没有告警、没有「未能解析」字段**。

用真实正则实跑验证过：构造 729 组、20000 条随机 UA，含引号的 15373 条
**0 条匹配、15373 条全部被丢弃**。

三个子结论要分清：
- 注入引号 ⇒ 自己的行被丢：**成立**（CONFIRMED）
- 注入引号 ⇒ 伪造出别人的行：**不成立**（IP 是 `$remote_addr`，在所有可控字段之前，
  且网关配置里没有 realip 指令）
- 注入引号 ⇒ 串到下一个字段（溢出到 `ref`）：**不成立**（`[^"]*` 跨不过引号，
  正则要求六个字面前缀严格定序，多一个 token 就整体失配 ⇒ 结果恒为「整行丢弃」）

**修法**：日志格式里对这几个字段做转义（至少把 `"` 与 `\` 换成安全字面量），
或者解析端改成不依赖引号定界（按固定顺序 + 贪婪匹配 + 尾部锚定）。
解析失败也要计数并在面板上提示，不能静默丢。

**（2）设备标识不可信 —— 直接决定第 8 批怎么做**

`device_id_from_request()`（auth_gateway.py:1518-1523）从 cookie 取值，
**只要 8-64 位、字符集 `[A-Za-z0-9_-]` 就原样采信**；取不到就每次生成一个新的
随机值（`secrets.token_urlsafe(16)`）⇒ 不带 cookie 的客户端每条审计记录都是不同的
设备 ID。`fingerprint()`（:1526-1529）同理，值来自前端 JS 送来的请求头。

这个值一路流到：审计记录（:1902）→ 令牌的 `dev` 声明（:516）→ 响应头 `X-Auth-Device`
（:2005）→ nginx 日志的 `auth_dev` 字段（app.py:12086）。

另外：`backend/static/fingerprint.js:9` 里宣传的「发现同一账号从多个未知设备登录」
的异常检测，**服务端根本没实现** —— 全仓找不到任何比较、计数或告警的代码。
这个指纹目前是装饰性的。

⇒ 第 8 批如果按原计划做「设备指纹页」，呈现出来的会是**看起来可信、实则可伪造**的
审计视图。

**（3）访客页的时间窗口口径不实**

`window` 参数被钳制在 1..10080 分钟（app.py:9083-9086）并回显给前端（:9116），
界面也提供「24 小时」选项；但读取端**只取日志最后 512KiB**
（`GATEWAY_LOG_TAIL_BYTES`，:9015，:9026-9030 应用），再按 cutoff 过滤。
访问日志在 tmpfs 上只追加不轮转，日志封顶脚本也刻意保留尾部 8MiB 正是为了这页。
⇒ 日志一旦超过 512KiB，请求 24 小时窗口拿到的其实是「最后 512KiB 里的内容」。

- `flock` 是 **OFD 语义**：同一 fd 重复加锁立即成功，**不同 fd 加同一把锁互相阻塞**
  ⇒ `update_config` 调 `save_config` 时，后者必须**复用同一个 fd**，
  否则就是自己把自己锁死。
- 锁状态用 `threading.local` 而不是普通全局变量 —— 面板是 `threaded=True` 的
  多线程 Flask，普通全局会跨线程串味。
- `mutator` 里不能 `return`（会把应答吞掉），所以「预期中的拒绝」用带
  `code`/`status`/`extra` 的异常传给调用方。

### 6.4 核实过程中新发现的一处真问题：`public_access=false` 分支的 `auth_request_set` 是死配置

**不在 120 条基线里**（基线是外部渗透测试报告的条目），是本轮核实第 8 批前置时
在 `.193` 真机上实测出来的 ⇒ 单独记在这里，**本轮没修**，理由见末尾。

**位置**：`backend/app.py:11990-12012`

```python
if rule.get("public_access"):
    L.append("        auth_request /_auth;")                        # ← 只有公网分支才有
    L.append("        auth_request_set $auth_user $upstream_http_x_auth_user;")
    L.append("        auth_request_set $auth_device $upstream_http_x_auth_device;")
else:
    # 仅内网 → 按来源地址拦截，不进认证
    L.append(f"        allow {lan_cidr};")
    L.append("        allow 127.0.0.1;")
    L.append("        allow ::1;")
    L.append("        deny all;")
    L.append("        auth_request_set $auth_user \"lan\";")        # ← 死配置
    L.append("        auth_request_set $auth_device $cookie_gw_device;")  # ← 死配置
```

**nginx 语义**：`auth_request_set` 只在 `auth_request` **执行之后**才给变量赋值。
`public_access=false` 分支**故意不生成 `auth_request`**（注释明写「不进认证」，
安全边界靠 `allow/deny` 的来源地址白名单）⇒ 这两行 `auth_request_set`
**永远不会给 `$auth_user` / `$auth_device` 赋值** ⇒ 变量恒保持
`app.py:11786-11788` 声明的默认 `""`。

**实测后果**（`.193`，974 行访问日志 + 面板生成的 nginx 配置）：

| 后果 | 证据 |
|---|---|
| 日志里 `auth_user` / `auth_dev` **零行非空** | `grep -c "auth_dev=\"[^\"]\+\""` ⇒ `0` |
| nginx 配置全文**没有任何 `auth_request` 指令** | `grep -n "auth_request "` 只命中 2 处**注释**（`:33`、`:227`） |
| 三个反代服务全是 `public_access=false` | `/fw/`、`/siyuan/`、`siyuan.fzyto.top` 的 `/` —— 全是「仅内网 192.168.100.0/24 可达」 |
| **往上游服务发的身份头是空字符串** | `app.py:11787-11788` 生成 `proxy_set_header X-Auth-User $auth_user;` / `X-Auth-Device $auth_device;` ⇒ 实测两者都是空 |

⇒ 最后一条是**真正的行为缺陷**：上游应用（思源笔记、防火墙面板）拿不到任何身份信息。
⇒ 同时**与代码注释不符**：`app.py:11786` 写着「认证身份变量默认值（服务 location 内
由 `auth_request_set` 覆盖）」—— 那个「覆盖」在 `public_access=false` 下**不存在**。

**消费方核实（决定了修法的代价）**：全项目 grep `X-Auth-Device` / `X-Auth-User`，
**只有生成方，没有任何消费方**：

| 位置 | 角色 |
|---|---|
| `backend/app.py:11987-11988` | nginx 侧生成（`proxy_set_header`） |
| `backend/auth_gateway.py:2023-2024` | 认证服务回头（LAN bypass 分支） |
| `backend/auth_gateway.py:2053-2054` | 认证服务回头（令牌分支） |

被反代的上游（思源笔记、另一台机器 `.232` 上的本项目面板）都**不读**这两个头
（同项目代码里没有消费点）。⇒ **修法 B/C 改变 header 值，对现有消费方零影响**。

**为什么本轮没修**（属于用户说的「有争议的先保留」）：

| 修法 | 效果 | 代价 / 风险 |
|---|---|---|
| A：删掉 else 分支那两行 | 代码与实际行为一致，注释不再骗人 | 零行为变化；丢掉作者「内网也标身份」的意图痕迹（**该意图本就没人消费**） |
| B：换成 `set $auth_user "lan";` | 内网请求带上 `lan` 身份，上游能区分「免认证内网访问」 | 改 header 值，但**零消费方 ⇒ 对现有部署无实际影响**；`lan` 是**服务端常量**，不可伪造 |
| C：连 `set $auth_device $cookie_gw_device;` 一起补上 | 内网也能带设备标识 | ⚠️ `$cookie_gw_device` 是**客户端自称的原始 cookie**（未签名、可伪造），把它当身份发给上游 ⇒ **给上游引入一个新的信任问题**，与公网分支签名的 `dev` 口径也不一致 |
| D：给 `public_access=false` 也加 `auth_request` | 内网也要认证 | **改变安全模型**（内网免认证是既有设计），超出本轮授权 |

B 与 C 都要改**对外可见的 header 值**（B 因零消费方，代价已降到很低），
C 还带一个伪造值的信任问题；D 动安全模型。
⇒ 按「有争议的先保留」的口径，等拍板。

**建议**：选 **B**。理由 —— 它让代码与 `app.py:11786` 的注释一致，
`lan` 是服务端写死的常量（不可伪造，不是客户端自称），
且全项目无消费方 ⇒ 实际行为零影响。
**不建议 C**：`$cookie_gw_device` 是未签名的客户端自称值，
把它当身份发给上游是**新增**的信任问题，与本项目 fail-closed 的取向相反。
**注意**：无论选哪个，内网侧的 `$auth_device` 都**不应该**有值 ——
第 8 批要的设备审计必须走 `public_access=true` 的**公网令牌分支**
（那里拿到的是认证服务签名的 `dev`）。

**给第 8 批的直接约束**：这一条与第八节第四条前置结论是**同一件事的两面** ——
第 8 批要审计 `device`，但 nginx 侧现在既没有 `$auth_dev`（日志）、
也没有有效的 `X-Auth-Device`（上游），**两个通道都是空的**。
⇒ 第 8 批开工前，得先定这条怎么修。

### 6.5 供应链条目 8：GitHub 安装包加 sha256 校验（fail-closed）

**位置**：`setup/setup.sh`（`deploy_project()` 的 GitHub 分支 + 工具函数区）

**修法**：
1. 新增 `sha256_of()`：优先 `sha256sum`，缺了退回 `openssl dgst -sha256`
   （`openssl-util` 是本安装器的硬依赖，coreutils 未必装了）。
2. tag 安装（`--version <tag>`）时，清单 URL 固定为
   `https://github.com/${GITHUB_REPO}/releases/download/<tag>/sha256sums.txt`。
3. 下载安装包后、**解包前**下载清单并比对：
   - 清单取不到 ⇒ **中止**（拒绝安装未经校验的安装包）

4. `main` 是开发分支、没有 release 资产 ⇒ 无清单可比，
   **明确警告但不阻断**（拒绝会把「装最新开发代码」这条正常路径堵死）。

**信任边界（必须写清楚）**：清单与安装包**同源**（都在同一个 release 上），
所以它防的是**传输损坏 / 中间人 / 资产被误改**，
**防不了 release 账号本身被攻破** —— 那需要签名，不在校验和的能力范围内。

   所以「长度比对」这条在 GitHub 上不可用，只能靠 curl 退出码 + 解包完整性判断；
② 「字节稳定」这条前提**只在下载完整时成立** ——
   任何只校验哈希的对比，在残包上都会得出假的不稳定结论。

#### 条目 43：规则集目录权限与加载前属主校验

**位置**：`backend/app.py`（新增 `_ruleset_perm_guard()`，在
`_apply_ruleset_locked()` 里调用 —— 这是**所有**规则下发的公共路径）

**问题**（`.193` 真机实测）：
- `/etc/nftables.d/99-custom-rules.nft.backup` 是 **0644 world-readable**
  —— 代码里的 `os.chmod(_rules_backup, 0o600)` 被 `if not os.path.exists(...)`
  短路 ⇒ **存量文件永远不会被修正**。备份里装的是完整 ruleset，
  含白/黑名单 IP 与信任 IP。
- 规则集所在目录由 `os.makedirs(..., exist_ok=True)` 建，**权限取决于 umask**，
  不由代码保证。
- nft 是**以 root 读** RULES_PATH 并加载的 ⇒ 文件或目录能被低权用户写/替换，
  就是让 root 执行自己内容的提权口子。

**修法**：
1. 目录 group/other 可写 ⇒ **收紧到 0755**（自愈，不拒绝 ——
   目录权限过宽通常是 umask/历史遗留，收紧不打断任何功能）。
2. 规则集文件属主不是 root ⇒ **拒绝加载**（fail-closed），并点名 uid。
   ⚠ 这条只在 `os.geteuid() == 0` 时生效：非 root 环境既加载不了 nft 规则，
   也没资格要求文件属主（否则开发机上的测试会被这条误伤）。
   `.193` 实测面板进程是 uid 0 ⇒ 实机上会生效。
3. 备份材料（`.backup` / `.lastgood`）group/other 可读 ⇒ **收口到 0600**
   （含存量文件）。

#### 条目 14：认证审计日志可被未认证者灌水挤掉

**位置**：`backend/auth_gateway.py`（`_audit_rotate_in_place()` +
新增 `_audit_line_is_always()`）

**问题**：`_AUDIT_ALWAYS = ("login_ok", "logout")` 原本只豁免了**限流**
（每 IP 120/60 秒），**没豁免轮转**。而攻击者换几十个源 IP 一分钟就能灌满
2 MiB 触发轮转 —— 就地轮转**只保留尾部 1 MB**，尾部全是刚灌的
`verify_denied`，更早的 `login_ok` 就此消失 ⇒ 事后「谁登录过」彻底查不到。

⚠ 这个缺口 `audit()` 的 docstring 里本来就写着
（「一个脚本几分钟就能把 2 MiB 的文件写满并触发轮转，把真正的登录成功记录挤掉」），
限流那一步补上了，轮转这一步没补。

**修法**：就地轮转时**字节预算优先给 ALWAYS 事件**，剩下的再按尾部给其它记录；
ALWAYS 自己超预算时从后往前留（最新的先留）；
输出按**原索引排序** ⇒ 审计记录的时间序不会被打乱。

#### 条目 55：改 auth_api_port 后不重启认证服务

**位置**：`backend/app.py`（`/api/gateway/config` 端点，`data.warning`）

**问题**：认证服务是**另一个进程**，监听端口在 import 时就固定了
（`auth_gateway.py:111` `BIND_PORT = int(os.environ.get("AUTH_API_PORT", "8444"))`），
改配置不会让它重读。而 nginx 的 `auth_request` 子请求地址是**面板生成配置时
按新端口写进去的** ⇒ 改完端口的瞬间：nginx 指向新端口、认证服务还在旧端口
⇒ **所有登录请求 502**。
而部署后的「端口真的在听吗」校验查的是对外的 `gateway_port` ⇒ 查不出来。

**修法**：比对新旧 `auth_api_port`，变了就在应答的 `data.warning` 里提示
「必须重启认证服务才生效（执行 /etc/init.d/nftables-web-auth restart）」。
前端 `app.js:2410-2413` 已经把 `data.warning` 用 toast 显示 ⇒ **前端零改动**。

**为什么只提示不自动重启**：重启认证服务要处理「新端口起不来」的回滚，
副作用面比提示大得多 —— 用户点了保存却发现网关瘫了，比没提示更难查。

### 6.8 IPv6 专项核实：入站阻断逻辑 + 四条新发现

本节是 2026-11-21 用户追问「当前规则会不会阻止所有 IPv6 入站」时触发的
专项核实，证据全部取自 `.193` 真机（`nft list ruleset` / `netstat` /
`uci show` / `ip -6 addr`），代码侧对应
`backend/app.py` 与 `backend/templates/nftables.conf`。

#### 6.8.1 结论一：外部 IPv6 入站默认被阻止，逻辑完整

`input` 链与 `forward` 链的 policy 都是 drop，两条链里
**没有任何一条无条件放行 IPv6 的规则**。完整判断链：

`input`（目标=路由器本机）：

| 顺序 | 规则 | 性质 |
|---|---|---|
| 1 | `udp dport {546,547} limit rate 100/second burst 200 accept` | 例外：DHCPv6，**不限来源接口** |
| 2 | `ct state {established, related} accept` | 例外：已建立会话 |
| 3 | 防伪源一组（pppoe-wan 的 `fe80::/10`、LAND-IP6、fragment 等） | 全部 drop |
| 4 | `iifname "pppoe-wan" jump input_wan` | 进子链 |
| 5 | `icmpv6 type {…} limit rate 10/second burst 20 accept` | 例外：ICMPv6 限速 |
| 6 | `udp dport {546,547} limit rate 15/minute burst 10 accept` | 例外：DHCPv6（见 N2） |
| 7 | `udp dport {12325,21710,31017,33074} jump knock_wan_v6` | 例外：敲门 |
| 8 | `ip6 saddr @allowed6 tcp dport @tcp_services` | 例外：白名单源+端口（见 N4） |
| 9 | `ip6 saddr @allowed6 udp dport @udp_services` | 例外 |
| 10 | **`meta nfproto ipv6 drop`** | **兜底：其余 IPv6 全丢** |

`forward`（目标=内网设备）：

| 规则 | 性质 |
|---|---|
| `ip6 saddr @blacklist6 drop` | 拦截 |
| `ct state {established, related} accept` | 例外 |
| `iifname "pppoe-wan" oifname "br-lan" icmpv6 {nd-ns,nd-na} drop` | 拦截 |
| `iifname "br-lan" oifname "br-lan" icmpv6 {nd-ns,nd-na} accept` | LAN 内部，非外部 |
| `ip6 saddr @allowed6 ip6 daddr @nas_ip6_i tcp/udp dport {…} accept` | 例外：IPv6 端口转发，**强制白名单源** |
| `iifname $LAN_IF oifname $WAN_IF accept` | LAN→WAN 方向，非入站 |
| **`meta nfproto ipv6 drop`** | **兜底：WAN→LAN 的 IPv6 全丢** |

有效的外部 IPv6 入口只有 4 个：DHCPv6、ICMPv6（限速）、
敲门四端口、白名单源+端口（当前失效，见 N4）。
`ct state established` 虽在例外里，但首包进不来就无从建立会话。

#### 6.8.2 结论二：还有一层比防火墙更靠前 —— 服务是否监听 IPv6

`.193` 实测 `netstat -lntup`：

```
tcp  0 0 192.168.100.193:5443  0.0.0.0:*  LISTEN  9614/python3   ← 面板：只听 IPv4
tcp  0 0 0.0.0.0:8443           0.0.0.0:*  LISTEN  2358/nginx      ← 网关：听 v4
tcp  0 0 :::8443                 :::*        LISTEN  2358/nginx      ← 网关：也听 v6
```

⇒ 公网 IPv6 连**面板**时，TCP 握手就被 RST（没有 v6 监听），
防火墙那一层根本用不上；**网关 8443** 才有 v6 监听，
那一层才轮到防火墙判定。审计 IPv6 暴露面时必须同时看这两层。

#### 6.8.3 结论三：设备上 IPv6 从未启用过（不是被挡住）

`.193` 实测：

- `network` 里**没有 wan6 接口**（firewall 的 wan zone 引用了不存在的 network）
- **没有 `dhcp6` / `reqprefix` / `reqaddress`** ⇒ 从未向 ISP 请求前缀委派
- `pppoe-wan` 无 IPv6 地址、无默认 IPv6 路由，PPPoE 未协商 IPv6CP
- `dhcp.lan` 却开着 `dhcpv6='server'` + `ra='server'` + `ra_slaac='1'`，
  但**没有 `ip6prefix`** ⇒ 客户端只拿到 link-local
- IPv6 邻居表 8 条全是 `fe80::`；conntrack 里 IPv6 会话仅 1 条
  ⇒ **没有任何客户端持有全球 IPv6 地址**

⇒ 「公网 IPv6 入站」这个场景目前不存在，IPv6 处于**半开空转**：
RA 在广播（客户端以为支持 v6 → 解析 AAAA 后先试 v6 → 路由器无 v6 路由
→ 每次连接为 v6 失败付回落等待），收益为零。

#### 6.8.4 N2：DHCPv6 两处限速矛盾，宽松的那条先生效

`input` 链第 9 行 `udp dport {546,547} limit rate 100/second burst 200 accept`
**没有 `iifname` 限制**，且位置在 `iifname "pppoe-wan" jump input_wan` **之前**
⇒ WAN 来的 DHCPv6 在这里就被 accept 了，
`input_wan` 里更严的 `limit rate 15/minute burst 10 accept` 是**永远走不到的死规则**。

实际生效的是 100/s，不是设计意图的 15/min。

#### 6.8.5 N3：`WAN_PREFIX6` 的写死回落值是「别人家宽带的前缀」

`backend/app.py` 的 `_auto_detect_network()` 会用
`ip -6 addr show dev <wan_if> scope global` 探测前缀，
探测不到才回落到 `DEFAULT_CONFIG` 的 `240e:390:4944:b191::/64`
（代码注释里自己写着「那是别人家宽带的前缀」）。

实测 `.193` 现在**没有**全球 IPv6 ⇒ 探测恒空 ⇒ 规则里用的是那个写死值：

```
iifname "pppoe-wan" ip6 saddr { 240e:390:4944:b191::/64, fd93:86bb:a142::/60, fe80::/10 } log prefix "[SPOOFED-IP6] " drop
iifname "br-lan"  ip6 saddr 240e:390:4944:b191::/64 log prefix "[LAN-PU-IP6] " drop
```

**残留风险**：若 ISP 真实前缀恰好就是这个值，而探测又失败
（例如 WAN 口只拿到非 `scope global` 的地址），则
**所有真实入站 IPv6 流量会被当伪造源丢弃，设备对外完全不可达且无报错**。
将来一旦启用 IPv6，必须确认探测命中（`WAN_PREFIX6` 不是那个写死值）。

#### 6.8.6 N4：白名单/敲门机制在当前配置下哑火

`input_wan` 里白名单放行的条件是
`ip6 saddr @allowed6 tcp dport @tcp_services` ——
**源在白名单里还不够，端口还必须在 `@tcp_services` 里**。

`.193` 实测四个集合**全是空的**：

```
set allowed4 / allowed6 / tcp_services / udp_services   ← 全部无 elements
```

原因（`backend/app.py` 的 `all_tcp` 收集逻辑）：
`tcp_services` = 端口转发规则的端口 + （网关模式下）`public_access=true`
的服务所占的 `gateway_port`。而 `.193` 的 `nat` 表是空的（无任何 DNAT），
3 个反代服务又**全部 `public_access=false`** ⇒ 连 8443 都没进集合。

⇒ 敲门四步 UDP（31017→21710→12325→33074）确实能把公网源加进
`allowed6`，但**加进去之后没有任何端口被放行**，公网仍然进不来。
要让「公网 IPv6 能访问」成立，前提是至少一条反代服务设成
`public_access=true`（8443 进集合），或配一条 IPv6 端口转发。

#### 6.8.7 N5：实机规则集与配置不同步

`.193` 配置里 `router_ip4 = 192.168.100.193`（等于设备实际 IP，正确），
但部署的 `/etc/nftables.d/99-custom-rules.nft`（Nov 18 18:45）里是：

```
define ROUTER_IP4 = 192.168.100.232      ← 旧值
```

配置文件的 mtime 是 Nov 20 11:03 ⇒ **配置改了、规则没重新生成**。

影响：当前 `__LAN_WAN_GENERAL__` 是「LAN→WAN 全放行」（
`dns_lan_resolver_enabled=false`），所以那条 DNS 定向规则
`ip daddr { …, 192.168.100.232, … } accept` 写错地址也**暂时无害**
（兜底 accept 兜住了）；但该规则语义上应当是「允许访问本机 DNS」，
现在放行的是访问 `.232` 的 DNS，名不副实。

另外发现一条**规则不对称**：`backend/templates/nftables.conf` 里
LAN→WAN 的两条 DNS 定向放行是 `meta nfproto ipv4 … ip daddr {…}`，
**只有 IPv4**；IPv6 版本是单独的 `IPV6_LAN_WAN_DNS_BLOCK`，
而它**只有 `router_ip6` 配了值才生成**（`backend/app.py` 的
`IPV6_LAN_WAN_DNS_BLOCK` 分支），`.193` 的 `router_ip6` 为空 ⇒ 未生成。
⇒ IPv6 的 DNS 现在能通，纯粹是靠兜底的全放行，不是靠专门规则。
反过来，打开「DNS 递归解析」开关后，收紧规则
`ip daddr != $ROUTER_IP4 drop` **同样只有 IPv4**
⇒ IPv6 的 DNS 反而还能直连公网 IPv6 DNS 绕过本机解析。

#### 6.8.8 处置

本轮 4 条（N2 / N3 / N4 / N5）**均为新发现，未改代码**，

N3 / N5 涉及 IPv6 启用路径，建议与「是否启用 IPv6」一并决策。

### 6.9 认证网关能不能承载飞牛这类应用（2026-11-21 评估，用户决定先不动）

起因：用户问「有些服务如果经过认证网关（比如飞牛），是不是就无法登录了，
只能走端口转发把原生端口直接暴露出来」。

**先纠正一个前提**：不是「无法登录」，是「**双层登录**」。
认证网关是 nginx 前置的一层认证，反代过去之后，**飞牛自己的登录照走**
（网关登录 → 飞牛登录）。真正会卡住的是下面这些具体门槛。

#### 6.9.1 逐条实测出来的门槛（全部取自 `backend/app.py` 的 nginx 生成代码）

| 门槛 | 代码实测行为 | 对飞牛的影响 |
|---|---|---|
| 上传体积 | `client_max_body_size` **默认 1M**（`DEFAULT_CLIENT_MAX_BODY`），每服务可配 | **必炸**：传照片/视频直接 413 |
| 超时 | `proxy_read_timeout 300s` / `proxy_send_timeout 300s` **硬编码**，界面改不了 | 大文件/长任务超 5 分钟 → 504 |
| HTTPS 上游 | 代码里**没有 `proxy_ssl_verify off`**（全项目 grep 无此指令） | 上游是 https + 自签证书 ⇒ **502**；飞牛上游只能走 http |
| 路径改写 | 前缀模式要 `api_path_prefix` + `proxy_redirect`；**host 模式（给服务配 `host` 字段）完全不用改写** | 飞牛是根路径应用 ⇒ **必须用 host 模式** |
| WebSocket | 默认开（`proxy_http_version 1.1` + `Upgrade`/`Connection` 头，`websocket_enabled` 默认 true） | 飞牛的实时通知/桌面可用 |
| Host 头 | `proxy_set_header Host $host:<服务端端口>` | host 模式下就是飞牛自己的域名，无影响 |
| 缓冲 | `proxy_buffering off` + `proxy_request_buffering off` | 流式/大文件友好 |

#### 6.9.2 一个比防火墙更硬的障碍：App 客户端过不了网关认证

`public_access=true` 的服务，未登录时 nginx 的动作是
`error_page 401 = @to_login` ⇒ **302 跳登录页**。

⇒ 浏览器走通（登网关 → 再登飞牛）；
⇒ **飞牛的桌面/手机 App 不会跳浏览器、拿不到网关会话 cookie ⇒ 走网关必然失败**。

#### 6.9.3 三种形态（结论：不是「只能端口转发」）

- **A｜只在内网用** ⇒ `public_access=false` ⇒ 走内网 `IP:端口`，
  **完全不过网关**，飞牛自己的登录就够。**最省事。**
- **B｜Web 面板要公网访问** ⇒ 反代 + **host 模式** + `public_access=true`
  ⇒ 可行。代价：双层登录 + 上传上限必须调大 + 上游得是 http + 5 分钟超时天花板。
  **比端口转发安全**（多一层网关认证、不暴露原生端口）。
- **C｜App/客户端要公网直连** ⇒ **必须端口转发**（或组网/VPN）——
  App 过不了网关认证这一关。

⇒ 典型形态是 **B + C 并存**：反代给浏览器，端口转发给 App。
但**端口转发那条务必带源限制**（IPv6 侧项目已强制源在 `allowed6` 白名单里）——
端口转发是绕过网关认证的原生端口暴露，应用自身的历史漏洞全在这个面上。

#### 6.9.5 为什么「端口转发」与「反代」对同一个后端是互斥的（机制说明）

起因：用户实测创建端口转发（端口 `5666` → `192.168.100.156`）时被拦，
提示「配置校验失败，未保存」。

**根因不是 bug，是 `_rp_forward_conflicts()` 在正确工作。**
用仓库真代码（`validate_config()`）+ `.193` 真实配置实测的矩阵：

| 场景 | 结果 |
|---|---|
| `5666 → .156`（只 TCP） | 通过 |
| TCP+UDP 都填 5666 | 通过 |
| 对照：`5667 → .156` | 通过 |
| 对照：`5666 → .157` | 通过 |
| 反代指向同 IP **不同端口**(5000) | 通过 |
| 反代存在但 `enabled=false` | 通过 |
| **反代已启用且指向 `.156:5666`** | **被拒** |

报错原文（`post_config` → `_ConfigRejected('INVALID_CONFIG', '配置校验失败，未保存', 400, …)`）：

> forward_rules[1]（端口 5666 → 192.168.100.156）会绕过认证：192.168.100.156:5666
> 已有已启用的反代规则承载该服务，端口转发走 nftables DNAT、不经过 nginx 的认证层，
> 会形成一条免登录的公网入口。建议删掉这条转发，改用反代访问该服务。

**判定条件是「目标 IP 相同」且「端口相同」** ⇒ 换端口、换 IP、禁用反代都放行，
只有「同一后端」这一组会撞上。

**为什么对飞牛是结构性互斥、不是配置能绕过去的**：
端口转发生成的是 `dnat to 192.168.100.156`（**不带端口**）⇒ nftables 的 DNAT
不改端口 ⇒ **公网 P 必然落到内网 P**。飞牛只有一个端口 5666，
要让它从公网可达，公网端口也必须是 5666 ⇒ 落点必然是 `.156:5666`
⇒ 与反代上游**是同一个地址** ⇒ 同一后端既有「经 nginx 认证」的路、
又有「经 nftables DNAT 免认证」的路 ⇒ 后者把前者架空。

⇒ 对「单端口 + 既有 Web 面板 + 又有原生 App」的应用（飞牛就是典型），
这两条路在当前项目里**只能留其一**。

#### 6.9.6 还有第三条路能同时保住两条（本次未采用，仅记录）

在飞牛那台机器上加一个端口转发器，让两条路的端口错开：

```bash
# 在 192.168.100.156 上
socat TCP-LISTEN:5667,fork,reuseaddr TCP:127.0.0.1:5666
```

- 反代仍指 `.156:5666`（浏览器走网关认证）
- 端口转发指 `5667 → .156:5667`（端口与反代不同 ⇒ **不冲突**）
- 飞牛 App 连公网 5667 ⇒ 落到 `.156:5667` ⇒ socat 转到 5666

代价：飞牛那台要装一个转发进程；App 那条路径仍然绕过网关认证
（App 本来就过不了认证，这正是需要它的原因）。

不想在飞牛上装东西的话，最简单的折中是**把飞牛那条反代禁用**
（`enabled=false`）—— 实测不冲突，代价是飞牛整体变成免登录公网暴露。

#### 6.9.7 新发现：这条冲突检测在「target_address 带 scheme」时**漏报**

`_rp_forward_conflicts()` 用 `_normalize_target_host()` 归一化后比较，
而该函数**不剥 scheme 前缀**：

```
_normalize_target_host('192.168.100.156')       = '192.168.100.156'
_normalize_target_host('http://192.168.100.156') = None     ← 规范化失败 ⇒ 冲突被静默跳过
```

实测确认：反代规则若写成 `target_address: "http://192.168.100.156:5666"`
（表单不会生成，但**手工编辑落盘配置**会），
**冲突检测直接失效** ⇒ 免登录公网入口能悄悄建起来。

方向与 6.9.5 相反（那边是被误伤，这边是漏网），但同属这条安全检查的缺陷。

修法方向（**未实施**）：`_normalize_target_host()` 先剥掉 `://` 及其后的 scheme，
再走原有的方括号 / 前导零 / 大小写归一化。

#### 6.10.2 一处不对称（这次没动，说明一下）

所以 IPv6 那两个公共 DNS 同样是「被前面的 accept 单独放行、再也落不到兜底 drop」
—— 修法一致，语义也就一并对齐了。

`iifname $LAN_IF oifname $WAN_IF accept`，上面两条 DNS 定向规则形同虚设（但也无害，
因为普通 LAN→WAN 本来就放行）。这次**不动**它 —— 那是「默认要不要强制递归解析」的

#### 6.11.3 修法

**网络侧：统一到一个容错底座**（不再手写段头正则）

- `_UCI_SECTION_RE` 改成容错版：
  `^[ \t]*config[ \t]+([A-Za-z0-9_.-]+)[ \t]*(.*?)[ \t]*$`

  返回 `(段内原文, 起始偏移, 结束偏移)`）/ `_uci_option_of` / `_uci_has_option`
  （只认 `option` 不认 `list` —— `list ipaddr 'x/24'` 与 `option ipaddr 'x'` 是两码事）
- `extract_uci_value` 改为**先剥引号再 strip**

  （不再 `content.replace` 全局替换）

- `NETWORK_CONF_PATH` 由硬编码常量改成可用环境变量覆盖

**证书侧**

- 新增 `_cert_dir_name(domain, wildcard)`：泛域名用 `<base>.wildcard`（**不含 `*`**，
  目录名带 `*` 在 shell 通配里是坑），存量普通证书目录名**不变**；

- `rp_request_cert` 判重不再 400：
  - 同 domain + **同 wildcard** ⇒ **原地替换并保留 id** ⇒ 默认证书自动指向新证书（「覆盖默认」）
  - 同 domain + **不同 wildcard** ⇒ **追加**（两张都留着，显示在下面可手动设默认）

- `rp_delete_cert` 默认证书不再硬拒 ⇒ **取消默认 + 放行删除**，并在删掉默认证书时
  重新下发 nginx（否则磁盘文件已删而 nginx.conf 还指着它 ⇒ 下次 reload 必失败）；
  消息说明「网关将回退到面板自签证书」
- 上传端点的「同 domain 手动证书」判定**补上 wildcard**：
  泛域名与普通证书现在分目录存放，是两张不同的证书；只按 domain 匹配会把普通证书的
  **条目**挤掉，而它的文件还留在磁盘上没人引用

#### 6.12.2 根因（全部实证）

现象 1 其实是**三处独立缺陷叠加**，缺一都不会变成「一直未知」：

**A. 前端从来没问过公网 IP**

| # | 根因 | 位置 | 后果 |
|---|---|---|---|
| A1 | `deviceInfo.publicIp` 只有 `loadPublicIp()` 会写，而它**只被「查询」按钮调用** | `frontend/app.js` `loadPublicIp` | 不点按钮 ⇒ 那一栏永远是「未知」 |
| A2 | 「查询」语义被当成「唯一的查询入口」 | `frontend/app.js` | 首屏自动刷新（5 秒一次）**故意不查外网**（合理），但**首屏也一次都不查**（不合理） |

`.1` 真机取证（只读，2026-11-24）：

- 面板日志里**只有** `GET /api/system/info`，**从未出现** `?public_ip=1`
  ⇒ 用户没点过「查询」按钮（不是按钮坏了）。
- 设备侧 `collect_public_ip()` **能**采到 `183.141.193.10`
  ⇒ **不是设备采不到**，是面板没去问。

**B. 接口表 IPv4 整列是「—」（后端采不到 PPPoE 口的地址）**

| # | 根因 | 位置 | 后果 |
|---|---|---|---|
| B1 | `_ipv4_by_iface()` 原来是「**fib_trie 采到了就 return，采不到才退 getifaddrs**」 | `backend/device_info.py` | **PPPoE 这类点到点接口永远采不到地址** |

为什么 PPPoE 采不到（这是本条的关键）：

- `_ipv4_from_fib_trie()` 的反查方式是「拿**接口的直连网段**去匹配 fib_trie 里的地址」；
- 而 PPPoE 接口在 `/proc/net/route` 里**只有默认路由**（`Destination`/`Mask` 全 0）
  ⇒ **没有直连网段** ⇒ 它的地址匹配不上任何网段；
- `.1` 实测：`fib_trie` 只给出 `br-lan`（`192.168.100.1`），
  `getifaddrs` 才给出 `pppoe-wan` 的 `183.141.193.10`

#### 6.12.3 修法

**后端**

- `_ipv4_by_iface()` 改成**两个来源合并去重**（不是二选一）：
  `getifaddrs()` 永远也要跑一趟 —— 它补齐的正是 fib_trie 采不到的

#### 6.13.4 WAN 面可达性：`.193` 的 80 在公网**不可达**

`.193` 生效规则集实测：

```
set tcp_services { type inet_service; flags interval; }      ← 空集合
chain input_wan {
    icmpv6 type {...} iifname "pppoe-wan" limit rate 10/second burst 20 packets accept
    udp dport { 546, 547 } limit rate 15/minute burst 10 packets accept
    meta nfproto ipv4 udp dport { 12325, 21710, 31017, 33074 } jump knock_wan_v4
    ip saddr @allowed4 tcp dport @tcp_services accept
    ip saddr @allowed4 udp dport @udp_services accept
    meta nfproto ipv6 drop
    meta nfproto ipv4 drop
}
```

- `tcp_services` **为空** ⇒ 没有任何 TCP 服务被放行到 WAN；
- `input_wan` 的 IPv4 最终归宿是 `drop`；
- 唯一能开 WAN 入向的是**敲门端口**（12325 / 21710 / 31017 / 33074，且 `@allowed4` 带
  `flags timeout; timeout 5h` ⇒ 5 小时自动过期）；

  认证网关的反代。⇒ 这就把审计重点从「防火墙有没有漏放行」转到了
  **「反代能不能把路由器自己的管理面发布出去」**。

#### 6.13.7 新发现（头号）：反代目标可以指向**路由器自己**

```nginx
    allow 192.168.0.0/16;
    allow 127.0.0.1;
    allow ::1;
    deny all;                                 # ← 这条分支**没有认证层**
    ...
}
```

**⇒ 管理员可以在认证网关上，把路由器自己的 LuCI（80/443）发布出去。**

风险分级（两条路径差别很大，不能一概而论）：

1. **`public_access=true`（发布到公网）—— 真正要紧的一条。**
   LuCI 的**登录页被搬到公网**。而 LuCI 登录本身**不限速、无锁定**（6.13.6 实测）⇒
   **root 密码的爆破面从内网搬到了互联网**。
   注意边界：产品自己的面板仍然是 LAN-only（`.193` 实测 `192.168.100.193:5443`），
   「面板没有公网入口」这条设计**没被破坏**；被搬出去的是**路由器 root 密码**，
   拿到 root 等于拿到这台机器的一切。

2. **`public_access=false`（仅内网）—— 不构成提权。**
   这条 location **完全没有认证层**（只有来源 allow/deny），LAN 内任何人可经网关访问 LuCI；
   但他们**本来就能直连 `192.168.100.193:80`** ⇒ **无新增权限**，只是多一个入口。
   值得记一笔的是「内网可达但无认证层」这个组合本身符合该分支的设计意图
   （认证层管不了「从哪来」，来源限制靠 nginx 的 allow/deny，见 `_nginx_service_location` 注释）。

3. **指向面板自己（`127.0.0.1:5443`）—— 已核实安全。**
   `_validate_rp_service` 同样放行，但请求经网关绕回来后，面板的对端是回环 ⇒
   面板 `_client_ip()` 会**采信**网关转发的 `X-Real-IP`（真实客户端 IP）⇒
   面板的访问边界照常按真实来源判定 ⇒ WAN 客户端被挡住。

**与既有设计的关系（重要，避免误判成「和已有功能打架」）**：
仓库里**本来就有**「把面板自己经网关反代出来」的**正规做法** ——
`/api/reverse-proxy/fw-console` 一键添加「防火墙控制」入口（`FW_CONSOLE_PREFIX='/fw'`，
`backend/app.py:13665`）。它的上游用的是**面板绑定的 LAN IP**
（`_fw_console_target()`，因为面板只绑 LAN IP、连不上 127.0.0.1），且 `public_access=False`。
⇒ 新发现**不与既有功能冲突**：既有功能走的是「面板的 LAN IP + 内网可达」，
新发现是「**手填的回环值**也能过校验」，差别就在**校验层少了一道约束**。

## 八、第 8 批（设备指纹页）的四条前置结论

用户已授权的方向是「关联 nginx 访问记录，审计 `device` ≡ nginx `auth_dev`」。
本轮把这四条查清了，直接影响实现：

| 结论 | 依据 | 对第 8 批的约束 |
|---|---|---|
| `device` 与 nginx `auth_dev` **不是同一个口径** | 公网分支 nginx 取认证服务回的头（app.py:11749），内网分支取 `$cookie_gw_device`（:11765）；认证服务在 LAN bypass 分支回的是**原始 cookie**（auth_gateway.py:1975），令牌分支才是签名的 `dev`（:2005） | 聚合时必须分别标注来源，不能混成一列 |
| 两者都**客户端自称、可伪造** | 见第五节 5.1 第 2 条 | 页面必须显式标注可信度，否则呈现的是假的审计视图 |
| 访客页的窗口口径不实 | 见第五节 5.1 第 3 条 | 第 8 批同样要读 nginx 日志，会踩同一个坑；要么一起修读法，要么一开始就别声称按窗口作答 |
| **当前部署形态下 nginx 侧根本没有可对照的数据** | `.193` 真机实测（详见 6.4）：nginx 配置**全文没有任何 `auth_request` 指令**（`grep` 只命中两处注释），三个反代服务全是 `public_access=false`（仅内网可达、不需认证）⇒ 模板不生成 `auth_request /_auth;` ⇒ 每处 `auth_request_set $auth_user "lan"` / `$auth_device $cookie_gw_device` 都是**死配置** ⇒ 974 行访问日志里 `auth_dev` **零行非空** | 要验证「`device` ≡ nginx `auth_dev`」，**必须先存在一个 `public_access=true` 的反代服务**（走令牌分支，认证服务回 `X-Auth-Device` 头）**并从公网侧产生真实流量**；纯内网测试环境验证不了这件事 |

**关于第 1 条的补充**（本轮实测后修正）：原表述说「内网分支取 `$cookie_gw_device`
（app.py:11765）」，那是**代码层**（认证服务回给 nginx 的头）的分支。
nginx 这层因为根本没有 `auth_request`，**连内网分支的 `$cookie_gw_device` 都不会被读**。
两层要分开看：

| 层 | 内网 | 公网 |
|---|---|---|
| app.py 侧（认证服务回给 nginx 的头） | 回**原始 cookie** | 回**签名的 `dev`** |
| nginx 侧（日志里的 `auth_dev`） | 恒空（无 `auth_request`） | 取认证服务回的头 |

⇒ 「两边口径不同」这个结论成立，但**错位点比原描述更靠后一层**。

实测证据：`.193` 的 `/etc/nginx/conf.d/00-nftables-web-gateway.conf`（面板生成，
生成时间 2026-11-04 21:08:56）与 `/var/log/nginx/nftables-web-gateway.access.log`（974 行）。
原始记录见 `tmp/pentest-20261120/batch8-recon-nginx-authdev.md`。
