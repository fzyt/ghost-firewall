# setup.sh 三个 apk 缺陷 —— `.232` 真机验证报告

- 日期：2026-11-05
- 设备：`192.168.100.232`（用户授权的测试机；OpenWrt 25.12.5 x86_64 / apk-tools 3.0.5 / BusyBox 1.37.0）
- 验证对象：`setup/setup.sh` 的三个 apk 缺陷修复（v0.19.1 的 CB-4）
- 结论：**三个缺陷的修复在真机上有两个真 bug**，已修复（v0.19.3）

---

## 一、为什么要做真机验证

v0.19.1 修的那三个 apk 缺陷，本地测试（`tests/test_setup_apk_fallback.py`，25 项）
是**全绿**的。但那套测试跑在开发机（Ubuntu）上，而开发机与目标设备有三处结构性差异：

| 维度 | 开发机 | OpenWrt 25.12.5 |
|---|---|---|
| `od` 命令 | 有 | **没有**（busybox 也不带这个 applet） |
| `.apk` 包格式 | —— | **ADB v3**（apk-tools 3.x），不是 gzip |
| `read -n` | dash 不支持、bash 支持 | busybox ash 支持 |

⇒ 这类问题**只能在目标设备上真跑才暴露**。本次验证就是去把它暴露出来。

## 三、发现的两个真 bug

### Bug ① `od` 在 OpenWrt 上不存在 ⇒ 魔数读出来是空串

```
$ od -An -tx1 -N2 /tmp/real.apk
sh: od: not found
```

原实现：

```sh
magic="$(od -An -tx1 -N2 "$f" 2>/dev/null | tr -d ' \n')"
[ "$magic" = "1f8b" ] || return 1
```

`od` 不存在 ⇒ `magic` 恒为空串 ⇒ `[ "$magic" = "1f8b" ]` 恒假
⇒ **`apk_file_looks_valid` 在真机上恒返回 false**
⇒ `apk_install_via_local_file` 永远走不下去 ⇒ 兜底安装路径等于**死代码**。

### Bug ② 包头根本不是 gzip 魔数

真机上的真实包：

```
$ hexdump -C -n 32 busybox-1.37.0-r6.apk
00000000  41 44 42 64 ec bd 09 7c  14 c5 f6 3f da 93 99 09  |ADBd...|...?....|
00000010  43 08 cc 00 19 08 0a 32  c2 20 41 59 32 8a 9a 00  |C......2. AY2...|
```

- 头 4 字节 = `41 44 42 64` = **"ADBd"** ⇒ apk-tools 3.x 的 **ADB v3** 格式
- `gzip -t` 对它报 **`gzip: invalid magic`** ⇒ 它根本不是 gzip 流
- 连**索引文件** `APKINDEX.*.tar.gz` 也是 ADB 格式（文件名带 `.tar.gz`，内容不是 gzip）

⇒ 即便 `od` 存在，判 `1f8b`（gzip）在 25.12 上也**永远为假**，合法包全被拒。
（apk-tools 2.x / OpenWrt 24.10 的包才是 tar.gz，所以**两种魔数都得认**。）

### 两个 bug 叠加的后果

`apk_file_looks_valid` 恒假 ⇒ **三个 apk 缺陷里的「缺陷二」其实并没有被修好**：
装包失败后既不会给出「这不是包」的可读原因，也永远走不到兜底安装。

### 真机对照（同一份文件，修复前 vs 修复后）

| 文件 | 修复前（v0.19.1） | 修复后（v0.19.3） |
|---|---|---|
| 真包 `busybox-1.37.0-r6.apk`（ADB v3） | ❌ INVALID | ✅ **VALID** |
| 404 HTML 错误页 | ❌ INVALID | ❌ INVALID |
| 空文件 | ❌ INVALID | ❌ INVALID |
| 头对但不足 64 字节 | ❌ INVALID | ❌ INVALID |
| 截断的包（头合法 + 半截身子） | ❌ INVALID | ✅ VALID（见下） |

⚠️ 截断包判 VALID 是**有意的**：它的包头是合法的，完整性由 apk 自己的哈希校验兜住
（实测 apk 对截断包报 `Connection aborted`）。本函数只负责挡「根本不是包」的文件。

## 四、修复内容

### 4.1 包头魔数：认 ADB v3，也认 gzip

```sh
case "$magic" in
    414442*|1f8b*) return 0 ;;   # ADB v3（apk-tools 3.x） / gzip（apk-tools 2.x）
esac
```

### 4.2 读字节：三层降级

| 层 | 工具 | 适用 |
|---|---|---|
| ① | `od` | 开发机 / 部分 Linux |
| ② | `hexdump` | **busybox applet，OpenWrt 必有**（实测 `/usr/bin/hexdump -> busybox`） |
| ③ | shell 内建 `read -r -n` | 最后的兜底，不依赖任何外部命令（busybox ash 实测支持读二进制字节） |

每层各自独立判定：某一层读到了**非空**结果就以它的结论为准（读空才继续降级）。

### 4.3 注释按真机事实更正（4 处）

| 位置 | 原来写的 | 真机实测 |
|---|---|---|
| `pkg_install_apk` 兜底段 | 「`apk fetch` 用的是 apk **自带**的下载器（不走外部 wget）」 | apk-tools 3.0.5 下载**索引和包体都会外调外部下载器** |
| `apk_install_via_local_file` 括注 | 「设备的 `/usr/bin/wget` 是 busybox 的 uclient-fetch 软链」 | `.232` 上是 **GNU Wget 1.25.0**；apk 用的 `-q -T 60 -O -` 这套参数**两种实现都接受** |
| 三处「ADB integrity error」 | 缺包体的报错写成 `ADB integrity error` | 实际是 **`file format is invalid or inconsistent`**；`ADB integrity error` 是**包体被截断**时 apk 自己的哈希校验说的话 |

## 五、三个缺陷的真机复验结论

### 缺陷一：`apk add` 没有超时保护

| 层 | 机制 | 真机实测 |
|---|---|---|
| 内层 | `apk add --timeout N` | `apk add --help` 确认 apk 3.0.5 **支持** `--timeout` ⇒ `apk_supports_timeout` 返回「支持」；且实测 `apk --timeout 5` 会把 `-T 5` 传给外部下载器 |
| 外层 | `run_with_timeout` | `run_with_timeout 3 sleep 300` ⇒ **退出码 124、耗时 3s、残留进程 0** |

⚠️ 一个**必须知道**的实测结论：内层 `--timeout` **管不住「卡在 TCP connect 阶段」的连接**
（GNU wget 的 `-T` 是读超时，connect 阶段另算）。对照实验：

| 跑法 | 对 `192.0.2.1`（TEST-NET-1 黑洞地址） | 结果 |
|---|---|---|
| `apk --timeout 5 ... update`（裸跑） | **248 秒** | 退出码 1 |
| `run_with_timeout 10 apk --timeout 5 ... update` | **10 秒** | 退出码 124，残留 apk 进程 0 |

⇒ **外层 `run_with_timeout` 才是真正兜底的那一层**，内层只是加分项。
（这正好也解释了为什么 setup.sh 必须保留外层这一层。）

### 缺陷二：镜像「索引全、包体缺」

- ✅ **识别**：`apk_file_looks_valid` 现在能正确区分真包与 404 HTML 页（见上表）
- ✅ **轮换**：`apk_rotate_mirror` 真机实测从 `mirrors.ustc.edu.cn` 切到 `mirror.nju.edu.cn`
  （日志 `已轮换 apk 源 → mirror.nju.edu.cn`），测完已把清单还原
- ✅ **报错原文**：真机装 HTML 页时 apk 报 `file format is invalid or inconsistent`
  （已同步更正注释）

### 缺陷三：兜底路径的注释与事实不符

- ✅ 注释已按真机事实更正（见 4.3）
- ✅ 顺带实测确认：apk 的下载确实外调外部下载器
  （`apk update` 调 8 次、`apk fetch` 调 1 次，参数 `-q -T 60 <url> -O -`）

### 附带实测：下载器对 404 的行为不一致

| 下载器 | 404 时 | 落盘 |
|---|---|---|
| GNU wget | rc=8 | **0 字节**（被 `[ -s ]` 挡掉） |
| busybox uclient-fetch | rc=8 | **0 字节** |
| curl（不带 `--fail`） | rc=0 | **193 字节的 HTML**（头两字节 `3c68`） |
| curl `-fsSL`（setup.sh 的 shim） | rc=22 | 0 字节 |

⇒ 魔数校验真正要挡的就是最后那种情况。

## 六、过程中的一次设备误伤（已完全修复）

验证 apk 是否外调 wget 时，我用 `cat > /usr/bin/wget` 写记录包装器 ——
**这个写法穿过软链，把 `/usr/libexec/wget-ssl` 的真二进制覆盖成了脚本**，
而脚本里又 `exec` 自己 ⇒ 无限递归。apk 随即挂死。

修复过程与结果：

1. 杀掉递归进程与挂死的 apk
2. `apk extract --allow-untrusted` 从已下载的官方 `.apk` 里取出**真二进制**（纯本地、不联网）
3. 写临时文件 → `rm` → `mv` 放回 `/usr/libexec/wget-ssl`（**不再写穿软链**）
4. `apk add` 让数据库与 world 对齐（中途发现 world 里 `busybox` 的约束被那次
   「装截断包」的实验钉到了坏文件上，用真包重新钉回）

设备最终状态（逐项核对）：

| 项 | 状态 |
|---|---|
| `/usr/libexec/wget-ssl` | ✅ 439541 字节官方二进制，`GNU Wget 1.25.0` |
| `/usr/bin/wget` | ✅ 软链 → `/usr/libexec/wget-ssl` |
| `/bin/busybox` | ✅ 405522 字节（用官方 `busybox-1.37.0-r6.apk` 重装过，sha256 已核对） |
| `apk update` | ✅ rc=0，`OK: 11270 distinct packages available` |
| `apk fetch busybox` | ✅ 正常下载 236272 字节 |
| `/etc/apk/world` | ✅ 167 行，约束已修正 |
| `/etc/apk/repositories.d/distfeeds.list` | ✅ 未改动（mtime 仍是 10 月 31 日） |
| `/var/cache/apk` | ✅ 3.0M，未污染 |
| 面板三个服务 | ✅ 在跑；`:8443/auth/portal` 与 `:5443/api/auth/status` 均 rc=0，JSON 正常 |
| overlay | ✅ 67.2M（与误伤前同量级） |

**教训**：在设备上替换任何**可能是软链**的路径时，必须「写临时文件 → `rm` 目标 → `mv`」，
绝不能 `cat >` / `>` 直接重定向到软链路径。

## 七、方法论沉淀

1. **「本地绿」不等于「设备上能用」**。凡是依赖目标平台特有工具/格式的代码，
   本地测试必须能**模拟**目标环境（本例：把 PATH 削到只剩 `wc`/`tr` 来模拟没有 `od`）。
2. **桩测试的覆盖面有天花板**：本地测试造的是 gzip 头的假包，恰好符合**错的**判据 ⇒
   结构性发现不了「真机包格式不同」这类问题。
3. **断言必须区分「静态存在」和「行为正确」**。本轮就因为重写测试文件时误删了两段
   行为断言，变异脚本立刻报 F-02 漏网 —— 这是变异覆盖的价值。
4. **注释里的报错原文也要核对**。写错的报错原文会让人照着错误信息去找错方向。
