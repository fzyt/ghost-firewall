- **依据**：`报告/需求评估-多eth接入br-lan-2026-11-09.md` 第三节 W1/W2

## 一、一句话结论

面板挑 WAN 口时，**只认带引号的 `list ports` 写法** ⇒ 多 eth 接入 br-lan 后，
手写成 `list ports eth1`（不带引号，UCI 合法）的那张卡**解析不到**
⇒ 被当成 WAN 候选 ⇒ **WAN 抢走 LAN 桥成员 ⇒ 整机失联**。

已修：判据改成三路证据取**并集**（配置声明 ∪ lan 的 option ifname ∪ sysfs master），
错误文案改成按实际口数生成。`.232` 真机已部署并验证。

## 二、W1 的前提：UCI 到底认不认无引号写法

这一条不能靠推测 —— 判据的全部依据都建立在「无引号写法合法」这个事实上。

`.232` 真机实测（2026-11-10，`uci -c /tmp/ucitest show network`）：

| 写法 | `uci show` 的解析结果 | 旧实现能否解析到 |
|---|---|---|
| `list ports 'eth0'` | `ports='eth0'` | 能 |
| `list ports "eth0"` | `ports='eth0'` | **不能**（旧代码只找单引号） |
| `list ports eth0` | `ports='eth0'` | **不能** |

⇒ **UCI 三种写法全合法**，旧实现只认其中一种。

旧实现（`backend/app.py`，修复前）：

```python
p = line.strip().split("'")[-2] if "'" in line else ''
```

⇒ 没有单引号就整个丢弃，那张卡**静默漏解析**。

### 这个漏解析怎么变成失联

`.232` 真实 `/etc/config/network`（实测原文）：

```
config device
	option name 'br-lan'
	option type 'bridge'
	list ports 'eth0'

config interface 'lan'
	option device 'br-lan'
	option proto 'dhcp'
```

⚠️ 注意 DSA 形态下 `list ports` 在 **`config device` 段**里，
不是 `config interface 'lan'` 段里 —— 只扫 lan 段的实现会完全漏掉。

用户在 `config device` 段加一行 `list ports eth1`（不带引号）后：

| 实现 | 解析出的 LAN 占用口 | 挑出的 WAN 口 | 后果 |
|---|---|---|---|
| 旧 | `{eth0}` | **eth1** | eth1 是 br-lan 成员 ⇒ WAN 抢桥 ⇒ 失联 |
| 新 | `{eth0, eth1}` | eth2（若存在） | 正确 |

这个对照在 `.232` 真机上跑过（见第四节）。

## 三、现在的判据：三路证据取并集

```
排除集合 = ① config device 段的 list ports / option ports
         ∪ ② config interface 'lan' 段的 option ifname
         ∪ ③ /sys/class/net/<if>/master 符号链接存在
```

| # | 来源 | 为什么算它 | 单独够不够 |
|---|---|---|---|
| ① | `config device` 段的桥成员声明 | DSA 形态的桥成员就声明在这里 | **不够**：文本可能漏写、写法可能怪 |
| ② | lan 段的 `option ifname` | swconfig 老写法：那套配置里**没有** `config device` 段 | **不够**：同上 |
| ③ | sysfs 的 `master` 符号链接 | **比文本解析更硬**：内核说了算「这个口挂在哪个桥上」 | 覆盖不到「改了配置还没重启」的窗口 |

**并集 = 宁可多排除，也绝不能少排除。** 任一路说它被占用，它就不能当 WAN 口。

### 两条刻意的保守行为（不是 bug）

1. **配置里声明了、即便 sysfs 说它没有 master，也照样排除。**
   代价：可能拒绝一次本可成功的保存（用户改完配置再重试即可）。
   收益：绝不会抢走桥成员（那是砖）。
2. **只看物理网卡**：VLAN 子接口（`eth0.10`）不算独立物理口。
   旧的 `startswith('eth')` 判定会把 VLAN 算进去 ⇒ 等于把 LAN 的 VLAN 抢走。

### 顺带收紧的物理网卡判定

| 旧判定 | 新判定 |
|---|---|
| `startswith('eth'/'ens'/'enp')` | 前缀 + 数字，且名字**不含 `.`** |

`.232` 实测的接口名：`eth0` / `eth1` / `br-lan` / `lo` —— 都在白名单内。
本机（开发机）`ens18` 也认得出来（`ens` + `18`）。

## 六、本轮踩过的坑（都写进了代码注释或测试）

1. **测试自身的样本污染**：所有假 sysfs 最初都建在同一个 `TMP/net` 下 ⇒
   后建的树叠在前一棵上（残留的 `eth1`/`eth2`、已存在的 master 符号链接）⇒
   判据测到的是「上一组留下的现场」。
   ⇒ 修法：每个假 sysfs 住自己的目录。
   这个坑的特征是**测试自己先红**，但红的原因不是被测代码 —— 差点误判成「修复无效」。
2. **样本设计与判据语义冲突**：曾用「配置声明 eth1 + sysfs 说 eth1 独立」的样本
   期待选出 eth2，但 eth1 只有两个候选时必然无候选。
   ⇒ 并集语义下「配置声明了就排除」是**刻意的保守行为**，已单独写成一条断言钉住。
3. **变异脚本里的引号嵌套**：三引号包裹的替换文本里再写双引号 ending，
   会拼出 `"""` 造成语法错误。⇒ 外层改用 `'''`。
4. **CHANGELOG 版本段顺序**：v0.19.9 段被放在 v0.19.8 段**下面**（批5 的遗留疏漏），
   本轮插入 v0.19.10 时才发现。⇒ 已顺移修正为 0.19.10 → 0.19.9 → 0.19.8。
