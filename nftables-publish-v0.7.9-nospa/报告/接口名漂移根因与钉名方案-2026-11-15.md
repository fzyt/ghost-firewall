# 接口名漂移：根因、活证据与钉名方案（2026-11-15）

对象：`.232`（OpenWrt 25.12.5，开机双网卡 + 运行期后加第三张 vNIC）
关联：用户 kirito 报告「自己主动加入 lan 之后，重启时 eth0/1/2 对应的接口会自动变动，
没有成功保存重启前的对应接口」

证据等级标注：`[实证]` = 真机实测有输出佐证；`[固定]` = 代码/设计已定；
`[待确认]` = 需要 Proxmox VM 复现验证。

---

## 一、先说结论

**接口名不是绑在物理口上的，是内核按「网卡出现的先后顺序」临时编的号。**

`/etc/config/network` 里绑的是**名字**（`list ports 'eth0'`），
名字一漂，配置就指向了错误的物理口 —— 这就是「接口对应关系变了」的机制。

OpenWrt **没有**按 MAC 绑定设备的能力 `[实证]`：
- `option macaddr` 是**覆盖 MAC 地址**，不是按 MAC 找设备
- `option device` 写 MAC 地址，netifd **不认**

⇒ 只能自己写：记一张「MAC → 固定名」的表，开机时按 MAC 找回接口并改名。

**已实现并在真机上跑通**（`.193`，2026-11-16）：
开机时按 MAC 把网卡改名成固定名（`S15` 钩子，卡在 `boot` 与 `network` 之间，
那时系统里还没有任何桥 ⇒ 改名绝对安全）；实测 `eth0 → lan0` 改名成功、
改名后桥与 IP 照常（`192.168.100.193/24` 不变）、面板与网关 200。

## 二、为什么名字会漂（内核机制）`[实证]`

Linux 给网卡编号的规则是**按驱动上报设备的顺序**，
而不是按 PCI 槽位、也不是按 MAC。

x86/Proxmox 场景的触发原因：

| 原因 | 机理 |
|---|---|
| **vNIC 热插** | 在 Proxmox 里加/删 vNIC，新网卡是**运行期**才被内核 enable 的，必然排在开机那批网卡后面 |
| **多 bridge / 多控制器** | 不同 PCI bridge 下的设备，探测完成顺序取决于驱动初始化时序 |
| **驱动加载竞态** | 不同网卡用不同驱动（virtio_net / igc / r8169…），谁先 probe 完谁拿小号 |
| **USB 网卡** | USB 枚举顺序极不稳定，社区最经典的复现场景 |

⇒ **同一台机器，每次重启后的 ethN↔物理口对应关系都可能不同。**

### 2.1 活证据：同一台机器上抓到的漂移现场 `[实证]`

`.232` 开机时只有两张网卡：

```
eth0  bc:24:11:48:32:5b  PCI 0000:06:12.0
eth1  bc:24:11:99:dd:bc  PCI 0000:06:13.0
```

后来在 Proxmox 加了**第三张 vNIC**（PCI `0000:06:14.0`，MAC `bc:24:11:54:ee:82`）。
内核日志：

```
[    8.809754] virtio_net virtio1 eth0: entered allmulticast mode       ← 开机时
[ 515592.924378] virtio-pci 0000:06:14.0: enabling device (0000 -> 0003) ← 5.9 天后
```

系统运行了 **6.0 天**，第三张网卡是在**开机 5.9 天后**才被 enable 的 ⇒ 它拿到 `eth2`。

```
现在的接口：
  eth0  bc:24:11:48:32:5b  PCI 0000:06:12.0   master=br-lan
  eth1  bc:24:11:99:dd:bc  PCI 0000:06:13.0
  eth2  bc:24:11:54:ee:82  PCI 0000:06:14.0   state DOWN  收包 0  发包 0
```

⇒ **槽位 14 > 12、13，但 eth2 是最后才出现的** ——
说明编号跟的是**出现顺序**，不是槽位大小。

### 2.2 为什么 `.232` 一直没漂 `[实证]`

两张原有网卡**都在同一个 PCI bridge 下**：

```
0000:06:12.0  →  pci0000:00/0000:00:1e.0/0000:05:01.0/0000:06:12.0
0000:06:13.0  →  pci0000:00/0000:00:1e.0/0000:05:01.0/0000:06:13.0
```

同一个 bridge、同一次探测、槽号 12 < 13 ⇒ 顺序恒定。

### 2.3 netifd 不支持按 MAC 绑定 `[实证]`

在 `.232` 上查 netifd 二进制：

```
$ strings /sbin/netifd | grep -iE "macaddr|hwaddr|permanent_mac"
peer_macaddr
```

只有 `peer_macaddr`（PPPoE 对端 MAC），**没有任何按 MAC 匹配设备的逻辑**。

## 三、方案：按 MAC 把接口钉成固定名字 `[固定]`

### 3.1 原理

MAC 地址是网卡的**硬件身份**，不会变；接口名是内核临时编的。
⇒ 开机时按 MAC 找回接口，把它**改名**成映射表里记下的那个名字，
   `/etc/config/network` 里的 `list ports 'eth0'` 就永远对应同一块卡。

实测改名可行、且 **MAC 跟着走** `[实证]`：

```
$ ip link set eth1 down && ip link set eth1 name wan-pin-test && ip link set wan-pin-test up
$ cat /sys/class/net/wan-pin-test/address
bc:24:11:99:dd:bc        ← MAC 没变
```

**固定名 = 每块卡第一次被看到时的名字** ⇒ 现有配置一个字都不用改。

### 3.2 落点

| 环节 | 位置 | 说明 |
|---|---|---|
| 钉名脚本 | `/opt/nftables-web-v2/setup/iface-pin.sh` | 按 MAC 找回接口并改名 |
| 映射表生成器 | `/opt/nftables-web-v2/setup/iface-pin-map.sh` | 生成/刷新「MAC → 固定名」 |
| 映射表 | `/etc/nftables/iface-pin.json` | `{"<mac>": "<固定名>"}` |
| 开机兜底 | `/etc/init.d/nftables-iface-pin`（`START=15`） | 开机时扫一遍全部接口并改名 |
| 配置变更刷新 | 同上（procd `config.change` 触发器） | `/etc/config/network` 一变就刷新映射表 |

`network` 是 S20、`boot` 是 S10 ⇒ `START=15` 的 init 脚本卡在中间，
既晚于内核建好网卡，又早于 netifd 读配置 `[实证]`：

```
S10boot  S10system  S11sysctl  S12log  S12rpcd  S13openssl
S15nftables-iface-pin      ← 本项目的钉名
S19dnsmasq  S19dropbear  S20acme  S20network  ← netifd 在这里才起
```

**为什么不用 hotplug 钩子** `[固定]`：
hotplug 的 `add` 事件是**逐个网卡**触发的 ⇒ 网卡还没全部出现时就开始改名 ⇒
结果不确定。init 脚本在 S15 跑，那时所有网卡都已出现 ⇒ 结果确定。
（早期版本用 hotplug + init 双保险，2026-11-15 实测后删掉 hotplug，删除优于新增。）

**⚠️ 落位时的硬要求：两个脚本在 git 里必须是 `100755`** `[实证]`
部署用 `tar -x` 传输，**保留文件权限** ⇒ git 索引里的 mode 直接决定设备上的 mode。
索引里是 `100644` ⇒ 设备上就是 0644 ⇒ `S15` 钩子 `Permission denied (rc=126)`
⇒ 保护静默失效且**不阻断启动** ⇒ 设备看起来一切正常。
（真实踩过，见 4.4。判据里有两条专门卡这个，另有 4 条文件状态类变异。）

### 3.3 三条硬约束

**约束一：只在开机时改名（安全窗口）** `[实证]`

运行期改名会**拆桥**：
1. 桥成员口改名时，内核把成员关系丢了 ⇒ 桥变空桥 ⇒ 桥上的 IP 跟着掉 ⇒ 整机断网
2. 桥的 MAC **继承自成员口** ⇒ 成员口改名后，桥本身在内核里也消失了
   （实测那次改名完 `br-lan` 直接从 `/sys/class/net` 里消失，`ip link set` 加不回去）

⇒ 结论：**运行期不能改名**。漂移是开机时发生的，修复也必须在开机时做。
   判据：系统里**没有任何桥**（`/sys/class/net/*/bridge` 目录都不存在）才允许改名。
   运行期手动跑这个脚本 ⇒ 整体跳过，只提示「下次重启生效」。

**约束二：绝不能给 bridge 改名** `[实证]`

有成员口的 bridge（`br-lan`）改名时，内核**既不拒绝也不返回** —— 命令**挂死**，
把网络拖垮（`.232` 就是这么失联的）。

判据：只看 `/sys/class/net/<name>/device` 是不是**真实子目录** ——
bridge / vlan / dummy 这类虚拟设备指向自己或不存在。

**约束三：改名失败不能中断整体** `[固定]`

一个口失败就跳到下一个，不能因为它把后面的口全跳过了。

### 3.4 边界情况的处理

| 情况 | 处理 | 依据 |
|---|---|---|
| 目标名已被别的接口占用 | **先腾位再改名**（把占位的口挪到临时名） | 互占时直接跳过 ⇒ 两块卡都纠正不回来（.232 实测：桥成员变成了 WAN 那块卡） |
| 映射表里的 MAC 当前不存在 | 跳过（那块卡没插或驱动没认领） | — |
| 当前名已经等于目标名 | 不做多余改名 | — |
| 改名失败 | 记日志，**继续处理其余接口** | 约束三 |
| 系统里已有桥 | **整体跳过**，提示下次重启生效 | 约束一 |

### 3.5 映射表什么时候刷新（很关键）`[固定]`

刷新**必须**发生在「名字还正确」的时刻：
- 装机时
- `/etc/config/network` 变化时（procd `config.change` 触发器，用户在 LuCI 里改了 LAN 成员口）
- 面板改 LAN 成员口时

**在「漂移已经发生」的时刻刷新，会把错名字固化成"正确名字"，比不刷更糟。**

映射表的合并规则：
1. 旧表里还插着的卡 ⇒ 固定名不变（MAC 是硬件身份，名字一旦定下就不该再变）
2. 旧表里没插着的卡（插槽换了卡）⇒ 名字交给现在占着它的卡
3. 后加的新卡 ⇒ 用当前名字补进表里
4. 腾位留下的临时名（`*-pin-tmp*`）**绝不**写进映射表

## 四、事故记录（三次真机事故，都是我的操作失误）`[实证]`

### 4.1 第一次：对 `br-lan` 执行改名 ⇒ 命令挂死 ⇒ `.232` 失联

测试脚本没排除 `br-lan`，`ip link set br-lan name xxx` 内核既不拒绝也不返回 ⇒
命令挂死 ⇒ 网络被拖垮 ⇒ `.232` 失联。**用户重启了网络恢复。**

⇒ 教训：bridge 绝不能改名（约束二）。

### 4.2 第二次：「目标名被占用 ⇒ 跳过」在互占时是死路

eth0 ↔ eth1 互相对调时，两个都「被对方占用」⇒ 两个都跳过 ⇒ 桥成员变成了 WAN 那块卡。

⇒ 教训：**先腾位再改名**（3.4 表格第一行）。

### 4.3 第三次：运行期改名 ⇒ 拆桥 ⇒ 桥上 IP 掉 ⇒ 面板 000

改名后桥变空桥 ⇒ 桥上的 IP 掉 ⇒ 面板 000。
进一步发现**桥的 MAC 继承自成员口** ⇒ 成员口改名后桥本身在内核里也消失。

⇒ 教训：**运行期不能改名**（约束一）。

三次事故的共同点：**都是在运行期改名**。
⇒ 这也是为什么最终设计把改名严格限制在「系统里没有任何桥」的安全窗口内。

### 4.4 第四次：脚本执行位是 `0644` ⇒ 保护**静默**失效 `[实证]`

这一次**没有造成事故**，但它是本轮最危险的一个缺陷 —— 因为它**悄无声息**。

**现场**：`.193`（用户重建网卡后的新设备）上，`/opt/nftables-web-v2/setup/iface-pin.sh`
是 `-rw-rw-r--`（0644）。手动执行 ⇒ `Permission denied`。
根因在**源码侧**：文件是我用写文件工具新建的，权限 0644，`git` 索引里记的是 `100644`。

**为什么这会静默失效**：

1. 部署用 `tar -x` 传输，**保留文件权限** ⇒ git 索引里的 mode 直接决定设备上的 mode；
2. `S15` 钩子由 `procd` 拉起，脚本不可执行 ⇒ 钩子 `Permission denied (rc=126)`；
3. `rc=126` 在开机序列里**不阻断启动** ⇒ 设备照常起来、照常联网、面板照常 200；
4. 而脚本的 `log()` 走 `logger` ⇒ **一行日志都不会有**。

⇒ 表现是「钉名保护好像在」，实际**从来没跑过**。
⇒ 只有手动跑过 `setup.sh`（里面有一句 `chmod 755`）才会被救回来 ——
   而没人会为了「确认保护还在」去跑一遍安装脚本。

**修复**：

| 位置 | 修复前 | 修复后 |
|---|---|---|
| `setup/iface-pin.sh` | `100644` | `100755` |
| `setup/iface-pin-map.sh` | `100644` | `100755` |

**防再犯**（两条判据 + 四条变异）：

- 判据：两个脚本在**磁盘上**必须可执行（`os.access(X_OK)`）；
- 判据：两个脚本在 **git 索引里**必须是 `100755`（部署保留权限 ⇒ 索引 mode 就是设备 mode）；
- 变异 `MODE-1/2`：把工作区文件的可执行位去掉 ⇒ 必须被抓；
- 变异 `MODE-3/4`：把 git 索引里的 mode 改成 `100644` ⇒ 必须被抓。

> ⚠️ 保险丝 `MutationGuard` 还原时**只比对文件内容**，mode 变了它看不出来
> ⇒ mode 类变异必须自己还原（脚本里用 `try/finally` 兜住了）。

**顺带补的一个洞**：脚本「所有口名字都已经对得上、一个都不用改」时是**零日志**的，
而「脚本压根没跑」也是零日志 —— 两种情况在 `logread` 里**长得一模一样**。
⇒ 现在每次执行固定留两句：`接口名钉定开始：…共 N 条` 和 `接口名钉定执行完毕：映射 N 条`。
⇒ 以后只要 `logread | grep iface-pin` 是空的，就知道保护没跑，而不是「大概跑过了」。

## 六、判据与变异验证 `[实证]`

- `tests/test_iface_pin.py`：**54 条断言**（静态结构 + 假 sysfs 树上真跑脚本）
- `tests/mutation_check_iface_pin.py`：**15 条变异全部被捕获（15/15）**

假 sysfs 树 + `ip` 命令桩（**桩会真的把假 sysfs 里的目录改名**）
⇒ 判据断言的是**最终状态**（谁叫什么名字），不是调用序列。

| 变异 | 捕获它的判据 |
|---|---|
| 去掉「虚拟设备不改名」的检查 | 唯一匹配的是 vlan 时拒绝改名 |
| 去掉「系统里有桥就整体跳过」 | 有桥时一个接口都不改名 |
| 改名失败时中断整体 | 第一个口失败后后面的口照样被改名 |
| 目标名被占用时直接跳过（不腾位） | 腾位之后真正的口能拿到目标名 |
| 按 MAC 找口时不物理口优先 | 与虚拟设备同 MAC 时固定名落在物理口上 |
| 去掉「开始」日志 | 名字全对时仍有「接口名钉定开始」 |
| 去掉「执行完毕」收尾日志 | 名字全对时仍有「接口名钉定执行完毕」 |
| 把 bridge 收进映射表 | bridge 不会被收进映射表 |
| 旧表固定名被当前名覆盖 | 旧表里的固定名保留 |
| 临时名被钉成固定名 | 临时名不会被钉成固定名 |
| 映射表不原子写入 | 映射表是原子写入 |
| ★ 工作区去掉可执行位 | 脚本在磁盘上可执行 |
| ★ 工作区去掉可执行位（映射表脚本） | 脚本在磁盘上可执行 |
| ★ git 索引 mode 变成 `100644` | 脚本在 git 索引里是 `100755` |
| ★ git 索引 mode 变成 `100644`（映射表脚本） | 脚本在 git 索引里是 `100755` |

## 八、复现命令

```bash
# 看接口 ↔ MAC ↔ PCI ↔ 桥成员 的完整映射
for i in /sys/class/net/*; do
    n=$(basename "$i")
    m=$(cat "$i/address" 2>/dev/null)
    mst=$(readlink "$i/master" 2>/dev/null)
    [ -n "$m" ] && echo "$n  $m  master=${mst##*/}  pci=$(basename $(dirname $(readlink -f "$i/device" 2>/dev/null)) 2>/dev/null)"
done

# 看内核什么时候 enable 各网卡（漂移的直接证据）
dmesg | grep -iE "virtio-pci.*enabling|renamed from"

# 确认 netifd 不支持按 MAC 绑定
strings /sbin/netifd | grep -iE "macaddr|hwaddr"

# 看钉名映射表
cat /etc/nftables/iface-pin.json

# 看 procd 的 config.change 触发器挂上没有
ubus call service list '{"name":"nftables-iface-pin","verbose":true}'

# 看系统里有没有桥（安全窗口判据）
for d in /sys/class/net/*; do [ -d "$d/bridge" ] && echo "有桥: $(basename $d)"; done
```
