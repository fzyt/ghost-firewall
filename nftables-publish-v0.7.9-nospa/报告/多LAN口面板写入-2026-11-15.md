# 多 LAN 口：面板里增删 br-lan 成员口（2026-11-15）

对象：`.232`（OpenWrt 25.12.5）
关联：用户 kirito 报告「自己主动加入 lan 之后，重启时接口对应关系会变」
配套：接口名漂移根因与钉名方案见《接口名漂移：根因、活证据与钉名方案-2026-11-15.md》

证据等级：`[实证]` = 真机实测有输出佐证；`[固定]` = 代码/设计已定；`[待确认]` = 需要复现验证。

---

## 一、这功能解决什么

用户在 OpenWrt 的 LuCI 里往 `br-lan` 加了一个口，但：
- 面板里看不到 `br-lan` 现在有哪些成员口（只能去读 `/etc/config/network`）；
- 改完也不能在面板里改，只能手工编辑配置文件 —— 手工编辑网络配置，
  一旦写错就是**整机失联**（路由器变砖）。

⇒ 在面板的「LAN 接口」卡片里加一块「LAN 桥成员口」：
勾选/取消物理口 → 保存 → 提示「需重启网络生效，期间会断网」。

**不改防火墙规则**：规则全用 `iifname $LAN_IF`（`br-lan`），
桥成员口的三层报文在桥上处理 ⇒ 一条规则覆盖全部成员口。

## 二、接口契约

### GET `/api/network/lan-members`

```json
{
  "success": true,
  "bridge": "br-lan",
  "members": ["eth0"],
  "candidates": [
    {"name": "eth0", "mac": "...", "state": "up",   "role": "lan"},
    {"name": "eth1", "mac": "...", "state": "up",   "role": "wan"},
    {"name": "eth2", "mac": "...", "state": "down", "role": "free"}
  ]
}
```

`role` 的含义：

| role | 含义 | 面板上 |
|---|---|---|
| `lan` | 当前在 LAN 桥里 | 已在 LAN |
| `wan` | WAN 口 | WAN 口（不可勾） |
| `reserved` | 被别的接口/桥占用 | 已被占用（不可勾） |
| `free` | 空闲物理口 | 空闲 |

### POST `/api/network/lan-members`

请求体 `{"members": ["eth0", "eth2"]}`；
成功返回 `{"success": true, "bridge": "br-lan", "members": [...], "message": "LAN 成员口已保存（需重启网络生效，期间会断网）"}`。

错误码：

| code | 含义 |
|---|---|
| `INVALID_MEMBERS` | 空列表 / 非物理网卡 / 本机不存在 |
| `PORT_RESERVED` | 该口已被 WAN 或其它接口占用 |
| `NO_LAN_BRIDGE` | 本机 LAN 不是桥配置（老式 swconfig 的 `option ifname`） |
| `INVALID_NETWORK` | 写入前的整体校验没过 |

## 三、失联保护（这块的失败模式是「整机失联」，不是「配置不对」）`[固定]`

写入一个成员口可能出的事：
- 把 WAN 口划进 LAN 桥 ⇒ WAN 没口了 ⇒ 断网；
- 把 LAN 桥的成员清空 ⇒ 桥没 IP ⇒ 管理口失联，路由器变砖；
- 写坏配置 ⇒ 变砖。

⇒ 写入路径按这个顺序走，每一步都能挡住一类事故：

| # | 动作 | 挡住什么 |
|---|---|---|
| 1 | 成员列表不能为空（两道拦截：请求体层 + 清洗后层） | 清空 LAN 桥 |
| 2 | 每个成员必须是**物理网卡**（名字匹配 `eth/ens/enp` + 不带 `.`） | 把 bridge / VLAN 混进成员口 |
| 3 | 每个成员必须**在本机真实存在** | 写入一个不存在的口 |
| 4 | 成员不得是「被占用口」 | 把 WAN/别的桥的口划走 |
| 5 | 写前备份 `/etc/config/network`（权限跟原文件一致，含 PPPoE 口令） | 出事没法回滚 |
| 6 | 内容校验（`_validate_network_config_content`）+ **原子写** | 写坏配置 |
| 7 | 写完**回读校验**，对不上立刻回滚到原文件 | 改写逻辑写错却报成功 |
| 8 | 写完刷新接口名钉定映射表 | 新口下次重启照样漂（白改） |

### 3.1 「被占用口」怎么认（四路证据的并集）`[固定]`

宁可多排除，也绝不能少排除：

1. **非 LAN 接口引用的口**（`config interface 'wan'` / `wan6` / `guest`… 的
   `option device` / `option ifname`）；
2. **其它桥段里的成员口**（那个桥还要用）；
3. **内核实况**：`/sys/class/net/<if>/master` 指向的不是 LAN 桥 ⇒ 它挂在别的桥上；
4. **默认路由走的那块物理口** ⇒ 它就是 WAN。

第 4 条是 `.232` 真机验证时补上的（见第五节）：**有些设备的 `wan` 段根本不写
`option device`**，靠 netifd 自动挑一块空闲物理口 ⇒ 配置里压根没有「WAN 口」
这个名字 ⇒ 只看配置认不出来 ⇒ 用户把它划进 LAN 桥就断网了。
「默认路由从哪块卡出去」是内核给的硬证据。

⚠ 默认路由走 LAN 桥（`br-lan`）的机器是**纯管理机/旁路网关**，本来就没有 WAN ⇒
那种机器上不该把任何口当 WAN 保护起来（`.232` 正是这种）。

### 3.2 二层环路：写入校验判断不了，只能提示 `[固定]`

**这条不是写入路径的保护，是物理连线的前提**，写错了会直接把网络打死：

同一二层域里出现两个 `br-lan` 成员口 ⇒ 两块卡互相转发对方的广播/ARP ⇒ **二层环路**。

Proxmox 上所有 vNIC 默认挂在**同一个 vmbr**（同一个二层域）⇒
直接把第二块 vNIC 也桥进 `br-lan` 就是环路。
⇒ 真要多 LAN 口，新口必须**单独一个 vmbr**（独立二层域），或走 **VLAN 子接口**。

**为什么不做成校验，只做提示** `[实证]`：

1. 「两个口是不是同一个二层域」这件事，**路由器自己判断不了** ——
   宿主机的 vmbr 归属在 guest 里看不见；
2. guest 侧唯一能探测的近似做法是「从新口能不能到达现有成员口网段的地址」，
   但新口在写入配置时**还没被拉起来**（要等重启网络），探测不到 ⇒ 写的时候没法判；
3. 真要判，只能放到**重启网络之后**再自检 —— 那是另一件事（自检 + 报警），
   不是写入路径的拦截。

⇒ 所以写入路径**不做**拦截（判不了，硬拦会误伤合法的多网段接法），
改成在面板勾选区上方**固定提示**这一条，让人在接线前就知道要求。

> 面板文案已加并真机下发（2026-11-16，`.193`）：
> 「注意：新口必须与现有成员口在不同的二层域，否则会形成二层环路。
> Proxmox 上 vNIC 默认都挂在同一个 vmbr —— 新口要单独一个 vmbr，或走 VLAN 子接口。」

## 四、改写配置的实现要点 `[固定]`

- 改的是 `config device` 段（`option name 'br-lan'`）里的 `list ports`；
- **先删掉该段里所有 `list/option ports` 行，再按 UCI 规范补成一行一条**
  （UCI 的 list 就是一行一个值）；
- 段尾的空行只是空行 —— **UCI 的段由下一个 `config` 行结束**，
  空行不会截断段 ⇒ ports 放空行前还是后对 uci 解析没有区别
  （这一条是变异脚本实测出来的等价变异，不是测试有洞）；
- 改写只碰桥段，其余段（`lan` / `wan` / `globals`）原样保留。

## 五、真机验证记录（`.232`，2026-11-15）`[实证]`

### 5.1 读

```
GET /api/network/lan-members → 200
bridge: br-lan
members: ['eth0', 'eth1']
  eth0  mac=bc:24:11:48:32:5b  state=up    role=lan
  eth1  mac=bc:24:11:99:dd:bc  state=up    role=lan
  eth2  mac=bc:24:11:54:ee:82  state=down  role=free
```

### 5.2 危险写入被拒

| 操作 | 结果 |
|---|---|
| 空列表 | 400 `INVALID_MEMBERS` |
| 把 `br-lan` 自己当成员 | 400 `INVALID_MEMBERS` |
| 不存在的口（`eth9`） | 400 `INVALID_MEMBERS` |
| VLAN 子接口（`eth0.10`） | 400 `INVALID_MEMBERS` |

### 5.3 无损写入（把当前成员口原样写回去）

```
原文件 md5: 5dd1771ceeff57bba827d1bf7cc40d42
新文件 md5: 5dd1771ceeff57bba827d1bf7cc40d42
★ 文件字节级不变: True
备份存在: True
```

⇒ 改写逻辑**幂等且无损**（这是最强的一条证据：同样的输入写回去，文件一个字节都没变）。

### 5.4 验证时发现并修掉的一个漏洞 `[实证]`

第一次真机验证时，「把 eth1 划进 LAN 桥」在 `.232` 上被**放行**了。
查下来原因是：`.232` **没有 wan 接口段**（它的默认路由走 `br-lan`，
是台纯管理机），所以 eth1 本来就不是 WAN —— 放行是**对的**。

但这个过程暴露了真问题：**`wan` 段不写 `option device` 的机器（WAN 由 netifd
自动挑），配置里没有 WAN 口的名字，只看配置认不出来。**
⇒ 补上了第 4 路证据（默认路由）→ 判据新增第 8 节 → 变异新增 LAN-10。

### 5.5 `.232` 的现状说明 `[实证]`

`.232` 的 `/etc/config/network` 里 `br-lan` 声明了 `eth0` + `eth1` 两个成员，
但**内核实况里 eth1 没有 master**（不在桥里）——
配置与运行态本来就不一致，这是本功能之前就存在的状态，本功能只是如实读出来。

### 5.6 `.193` 上真机用它清掉了一个隐患 `[实证]`

用户在 `.193`（重建网卡后的新设备）上删掉了全部网卡、只留一块新卡（MAC 全变）。
设备上 `/etc/config/network` 的 `br-lan` 里还留着**旧卡的成员口**：

```
config device
	option name 'br-lan'
	option type 'bridge'
	list ports 'eth0'
	list ports 'eth1'      ← 旧卡的口，设备上已不存在
```

**为什么这是隐患**：配置里还写着 `eth1`，将来 `eth1` 这个名字**又出现**
（比如又插一张网卡、或内核编号顺序变回去），它就会被 netifd 直接划进 `br-lan`
⇒ 在同一二层域里出现第二个桥成员口 ⇒ **二层环路**。

**用面板 API 清掉它**（`POST {"members": ["eth0"]}`）：

```
GET  → 200  bridge=br-lan  members=['eth0', 'eth1']
       候选 eth0  mac=bc:24:11:74:b0:3a  state=up  role=lan
POST → 200  {"bridge": "br-lan", "members": ["eth0"], "success": true}

清理前 md5: 5dd1771ceeff57bba827d1bf7cc40d42
清理后 md5: 3ef276a88cb5f1509ef0f30a967b1ed0
备份存在: True（备份 md5 = 清理前的 md5）
回读 GET → members=['eth0']
```

改完的桥段：

```
config device
	option name 'br-lan'
	option type 'bridge'
	list ports 'eth0'
```

⇒ 顺带证明了：**面板写的成员口列表 = 配置里实际存在的成员口列表**，
且备份、回读校验、映射表刷新都按预期工作（写完映射表自动刷成了新 MAC 的那条）。

| 变异 | 捕获它的判据 |
|---|---|

## 七、与「接口名钉定」的关系 `[固定]`

两件事共用同一份真值：

```
哪些口归 LAN  →  /sys/class/net/*/master 是不是 br-lan（内核视角，硬证据）
哪些口叫什么  →  /etc/nftables/iface-pin.json（MAC → 固定名）
```

面板改完成员口后必须刷新钉定映射表（`iface-pin-map.sh`）——
否则新加入的口不在表里，下次重启它照样漂 ⇒ 这次绑定又白改了。
