## 2. 严重（2 项）

### S1〔严重〕AAAA 中转文件缺失 ⇒ 把配置里的**旧地址**写回阿里云，且**永久不自愈**

**位置**：`backend/app.py` cron 模板第 6374-6377 行（`except Exception: pass`）

**现象**〔实证〕：
OpenWrt 的 `/tmp` 是 tmpfs，**重启即清空** ⇒ `/tmp/ddns-ipv6-0` 不存在时：

```python
value = str(rec.get("value", "") or "").strip()   # ← 配置里存的上一轮旧地址
...
        try:
            with open(os.path.join(RELAY_DIR, "ddns-ipv6-%s" % idx)) as f:
                value = f.read().strip()
        except Exception:
            pass          # ← 读不到 ⇒ value 仍是配置里的旧值
...
if not value:             # ← 旧值非空 ⇒ 不跳过
    continue
```

⇒ 旧地址非空 ⇒ 不跳过 ⇒ `UpdateDomainRecord` 把**过期 IPv6 写回阿里云**
⇒ 写回后每轮比较都相等 ⇒ **从此永远停在过期地址，不会自愈**。

**同一条规则在 A 记录上是实现了的**（模板 6380-6384「取不到公网 IPv4 ⇒ 跳过本轮」），
**AAAA 没实现** ⇒ D5 只做了一半。

⚠️ **两侧行为还相反**：面板「测试」按钮遇到同样的情况会返回 400 **拒写**（`app.py:6843-6847`），
cron 却照写 ⇒ **面板绿灯不代表 cron 正常**，而 cron 这条会写坏数据。

**修法**：读取失败即置空并跳过本轮（与 A 记录同构）。

### S2〔严重〕部署后**服务阶段被跳过** ⇒ 面板进程仍跑旧 `app.py` ⇒ D9 可原样复发

**位置**：`setup/setup.sh:1042-1048`（`stage_service_done`）、`setup/setup.sh:2675`（本轮新增的调用点）

**现象**〔实证〕：
`stage_service_done()` 只看「init 脚本在不在 + 面板端口有没有在听」：

```sh
stage_service_done() {
    [ -f "$INITD_SCRIPT" ] || return 1
    [ -f "$AUTH_INITD_SCRIPT" ] || return 1
    if netstat -lnt 2>/dev/null | grep -q ":${PANEL_PORT} "; then
        return 0        # ← 端口在听 ⇒ 判成「已完成」⇒ 服务阶段跳过 ⇒ 不 restart
    fi
```

`setup.sh` 里面板 restart **只有一处**（`:2317`，在 `setup_service` 里）⇒ 端口在听时**不会执行**。

⇒ 部署完新 `app.py` 后，**盘上**是新代码，**跑着的进程**还是旧代码。

⚠️ **`.232` 上已经实际发生**（本次审查实测）：

```
设备上 backend/app.py 的修改时间：Nov 11 12:54   （我部署 v0.19.12 的时刻）
面板进程 python3 app.py 已运行：  17769.9 秒 = 4.9 小时   （约 12:34 启动）
⇒ 面板跑的是 12:34 之前那版 app.py；我前两轮部署都没让服务加载新代码
```

**与本轮修复目标的冲突**：本轮把「重新生成」接进 `setup.sh`，
并在失败时提示「面板上点一次『保存配置并生成脚本』即可」——
⇒ 用户照着提示点那个按钮 ⇒ **旧 app.py 的 `_generate_ddns_update_script()` 把旧模板写回磁盘**
⇒ **D9 原样复发，现象与修复前一模一样**（本地全绿、真机跑旧行为）。

**修法**：让「代码变了就要重启」进入服务阶段的判据；
或与 `regen_ddns_script` 同理，在 `deploy_project` 拷完代码后**无条件** restart。

⚠️ **附带影响**：`.232` 上我此前报告的「设备端 md5 ＝ 本地」指的是**磁盘上**的文件 —— 没错；
但「面板侧行为已改变」这件事**当时并不成立**。cron 脚本的真机验证仍有效
（子进程读盘），但面板侧的一切改动都没在真机上生效过。

## 6. 文档与代码不符（7 处）

### D1〔高〕「40 项」实为 **41 项**

`报告/阿里云DDNS修复与真机验证-2026-11-11.md` 与 `CHANGELOG.md:52` 都写「**40 项**」，
实测 `通过 41 / 失败 0`。**旁证**：报告自己的总数 `4236 = 4195 + 41` ⇒ 总数对，「40」是笔误。

### D2〔高〕「⇒ 每轮一次 ⇒ 这一条单独就能解释现象」与 v0.19.10 真实行为**不符**

**这是本次审查最重要的一条纠正 —— 它推翻了我上一轮给出的结论。**

原话（报告 §2.1 + §6 第 1 条 + CHANGELOG v0.19.12 §二）：
> 旧代码只按 RR+Type 匹配 ⇒ 拿到非 default 那条就**删掉**、另**加**一条 default
> ⇒ **每轮一次** ⇒ 控制台表现正是「不断删除重新上传」
> ⇒ **这一条单独就能解释用户看到的现象**

`[历史]` v0.19.10 真实模板（`git show 4470c21`，第 6222-6231 行）：

```python
for r in result.get("DomainRecords", {}).get("Record", []):
    if r.get("RR") == rr and r.get("Type") == rtype:
        if r.get("Value") == value: found_same = True
        else: _api("DeleteDomainRecord", ...)
        break                       # ← 只看第一条，然后跳出
if not found_same:
    _api("AddDomainRecord", ...)   # 不带 Line ⇒ 默认 default
```

「只按 RR+Type 匹配」**成立**；「拿到非 default 那条就删掉、另加一条 default」**成立**；
但「**每轮一次**」**不成立** —— 那条非 default 记录在**第 1 轮就被删掉了**，第 2 轮起已不存在。

**〔实证〕** 我把 v0.19.10 的**真实**模板抽出来，配**有状态**假阿里云（删掉的记录下一轮就查不到），跑 3 轮：

| 场景 | 第 1 轮 | 第 2 轮 | 第 3 轮 |
|---|---|---|---|
| 阿里云上只有一条**电信**线路记录，值不同 | `Describe → Delete(2002) → Add(default)` | **只有 Describe** | **只有 Describe** |
| **公网 IPv4 每轮都变**（default 线路） | `Describe → Delete → Add` | `Describe → Delete → Add` | `Describe → Delete → Add` |

⇒ **非 default 线路只解释第一轮的删+加**；
⇒ **「每 10 分钟一对 Delete+Add」必须同时成立：公网 IPv4 每轮真的在变**。

⇒ 取证指引要改成**两条同时查**：① 那条记录的**线路** ② 本机公网 IPv4 **每 10 分钟是否真的在变**。

## 7. 已核查、确认无问题的项（明确列出）

1. **绝无 `DeleteDomainRecord` 调用** —— AST 提取生成脚本的全部 `_api(...)` 实参，Action 集合
   = {`DescribeDomainRecords`, `AddDomainRecord`, `UpdateDomainRecord`}。
2. **值未变时确实一个写接口都不调** —— IPv4/IPv6 场景实测调用序列恰为 `['DescribeDomainRecords']`。
3. **`Line` 判定的健壮性** —— `Line` 缺失 / `None` / 空串 / `Default` / `DEFAULT` 五种形态实测全部正确归入 default。
4. **单条失败隔离** —— cron 每条记录独立 `try/except`，首条失败不阻断其余。
5. **阿里云错误码不被静默吞掉** —— cron 记入摘要日志，面板返回 `success:False` + 500。
6. **签名算法与参数**（`_aliyun_sign` / `_aliyun_api`）与阿里云 RPC 规范一致。
7. **记录不存在时不会退回「删+增」** —— 面板侧缺 RecordId 直接抛错。
8. **取证脚本确实只读** —— 见第 5 节复核。
9. **AccessKeySecret 原文不进 stdout / 日志 / 命令行** —— 运行时动态实测；cron 条目无参数；ACME 侧走环境变量。
10. **配置落盘权限 0600 且显式 chmod** —— 内容写入发生在权限已正确之后，无「先 0644 再 chmod」窗口。
11. **`/api/aliyun-ddns/*` 受全局鉴权保护** —— 未登录返回 401。

## 8. 未能闭环的边界

## 9. 建议的修复顺序

| 批次 | 内容 | 理由 |
|---|---|---|
| **批 1（数据安全）** | S1（AAAA 旧值回写）、M4（TotalCount 截断⇒重复 Add）、M3（record_id 优先）、M1/M2（TTL/Line 回传） | 这几条都会**写坏阿里云上的数据**或**改错记录**，且都能用现有的行为级测试手法覆盖 |
| **批 2（部署语义）** | S2（部署后服务不重启）、L1（路径单一真源）、L7（生成失败兜底） | 直接决定「修复到底生不生效」 |
| **批 3（面板可用性）** | M5（CNAME/TXT 测试按钮）、L8（PageSize）、L12（归一化） | 功能退化，不写坏数据 |
