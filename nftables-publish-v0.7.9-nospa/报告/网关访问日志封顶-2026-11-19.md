# 网关访问日志封顶（2026-11-19）

## 这批做什么

网关的 nginx 访问日志一直只增不减 —— 设备上没有 logrotate，访问日志落在 tmpfs 上，
没人管它。给日志**封顶**：超过 20MB 就保留尾部 8MB 原地截断，cron 每 5 分钟查一次。

## 为什么不能挪去持久化路径（设备实测）

`.193` 上的存储实况（2026-11-19 测）：

```
/var → /tmp 软链 → tmpfs 492.9M，已用 468K，剩 492.5M    ← 访问日志现在在这
/overlay（持久化）: 86.4M 总量，77.5M 已用，仅剩 2.0M（97% 满）
/rom: 6.0M 100% 满（只读）
/boot: /dev/sda1 15.7M，剩 9.8M
无外接存储（/mnt 也在 overlay）
内存 985MB 总，132MB 已用，816MB 可用
```

两条路都不通：

- **挪去 overlay** ⇒ 2MB 的余量撑不了几天 ⇒ 路由器文件系统转只读 ⇒ 配置再也写不进去。
- **挪去别的持久化区** ⇒ 没有这样的区（`/boot` 只有 15.7M，`/rom` 是只读的 6M）。

访问日志还是持续追加写，落 flash 还磨损 flash。

⇒ 所以：**位置不动，给它封顶**。

## 封顶脚本：copytruncate，不能用 mv

脚本由面板自己生成、自己装（与 IPv6 更新脚本、证书续期脚本同一套路）：

```sh
LOG=${GATEWAY_ACCESS_LOG:-/var/log/nginx/nftables-web-gateway.access.log}
MAX=${NFT_LOG_TRUNCATE_MAX:-20971520}
KEEP=${NFT_LOG_TRUNCATE_KEEP:-8388608}
...
tail -c "$KEEP" "$LOG" 2>/dev/null | tail -n +2 2>/dev/null > "$LOG.tmp" || exit 0
if [ ! -s "$LOG.tmp" ]; then rm -f "$LOG.tmp" 2>/dev/null; exit 0; fi
: > "$LOG"
cat "$LOG.tmp" >> "$LOG"
rm -f "$LOG.tmp"
```

四个设计点，每一个都对应一个具体的坑：

1. **不能 `mv` 换文件**。nginx 一直握着日志文件的 fd（`O_APPEND`）——
   `mv` 换文件 ⇒ nginx 继续往已被 unlink 的旧 inode 写 ⇒ 新文件永远是空的
   ⇒ 访客页永远显示「没人来过」，而磁盘还在涨（涨的是那个没人看得见的旧 inode）。
   nginx 不报错、面板不报错 ⇒ 只能靠「截断前后 inode 不变」这种行为断言守住。
2. **保留尾部而不是头部**。访客页读的就是这个文件的最近内容；
   保留头部 ⇒ 页面显示的是几小时前来过的人，看着有数据、其实全是错的。
3. **丢掉切出来的第一行**。按字节切，切点必然落在行中间 ⇒ 第一行一定是半行。
4. **拷贝失败就不许往下走**。「先拷尾部、再截断、再贴回去」这个顺序里，
   拷贝失败却接着走 = 把访问日志**清空** —— 那比不封顶糟得多。

另外两条：

- `KEEP` 必须小于 `MAX`，否则截断完还是超标，每 5 分钟白跑一趟（脚本里钳到 `MAX/2`）。
- 三个参数都留了环境变量口子：运维临时换路径不用改面板；
  测试能用小阈值跑**真实脚本**，不必造 20MB 文件。

## 判据与变异

`tests/test_log_truncate.py`（60 条断言）分五组：

1. **阈值与常量**：上限 20MB、保留 8MB、保留量 < 上限、脚本路径、cron 频率 5 分钟、
   默认日志路径与历史硬编码一致。
2. **脚本内容（去注释版）**：不许出现 `mv`、不许出现 `head -c`、
   必须有 `: > "$LOG"` / `cat "$LOG.tmp" >> "$LOG"` / `tail -c "$KEEP"`、
   文件不存在时安静退出、大小非数字时退出、拷贝失败不许继续、三个参数都可用环境变量覆盖、
   脚本里嵌的默认值与 Python 常量一致。
3. **脚本真跑**（真的 `sh` 执行）：超阈值被截断且 ≤ 保留量、**inode 前后不变**、
   保留的是尾部、丢掉的是头部、每行都是完整行、不留临时文件；
   未超阈值一个字节都不动；文件不存在时退出码 0 且不凭空造文件；
   保留量 ≥ 上限时钳到一半；临时文件建不出来时**原日志保持原样**。
4. **`_ensure_log_truncate_cron()`**：脚本写到指定路径、权限 0755、内容一致；
   cron 按脚本路径去重只留一条；**原有条目一条没被抹掉**；重复安装不堆第二条；
   脚本写不出来 / cron 写不进去都返回 False 而不抛异常。
5. **接线**：面板启动时会调用它；nginx 配置用的是常量而不是写死的路径。

> 第 3 组里的**inode 断言**是这批的核心。它不是静态检查，是行为检查：
> 我专门加了一条变异（`rm`+`cp` 换文件，内容完全正确、脚本里也没有 `mv` 字样）
> 来证明这条断言**自己**有鉴别力 —— 静态断言抓不到它，只有 inode 断言能抓。
> 已独立验证：rm+cp ⇒ inode 从 2404331 变成 2404333；copytruncate ⇒ 2404334 → 2404334。

`tests/mutation_check_logtruncate.py`：22 条变异，**22/22 全捕获**，
覆盖四类失败模式：换文件而不是原地截断、留错内容、阈值判错、拷贝失败却往下走，
外加阈值常量、cron 接线、启动挂载、nginx 配置与脚本对得上。

## 顺带挖出并修掉的四个真问题（都在部署链路上）

这批功能本身只碰了后端一个文件，但**部署到真机时连续撞了四个坑**，
每一个都是「部署看起来失败、其实部署没问题」或者「会越用越糟」。

### 一、部署自检把「面板自己装的 cron」当成部署弄坏了 → 自动回滚

第一次部署直接判红：

```
❌ crontab 条数未变 —— 期望 3，实际 4
❌ 正在回滚：/root/nftables-web-backups/20261119-103949/restore.sh
```

那多出来的一条正是**面板启动时自己装的**（访问日志封顶脚本的 cron）——
部署本来就要重启面板，crontab 合法地多了一条。

根因是判据本身太粗：「crontab 条数未变」想守的是 P0-10 那类事故
（读 crontab 失败被当成「本来是空的」，接着用「只有自己那一条」覆盖整张表
⇒ acme 续期和证书续期双双消失）。**不变式的本意是「不许丢条目」，不是「不许加条目」**，
而「条数」这个量纲恰好把两件事混在了一起 ——
丢一条又加一条，条数照样不变，真正的漏网反而看不见。

改成三条更准的判据（`check_crontab_intact()`）：

1. 原有条目一条都没丢、也没被改（**逐行精确比对**，不再看条数）；
2. 同一条目没有被多装一遍；
3. 新增的条目只允许指向面板自己管的脚本目录（`/opt/nftables-web/`），且那个脚本必须可执行。

第 2 条一开始也写漏了：只盯着**部署前**的条目迭代 ⇒ 面板把自己那行写两遍时看不见。
而重复装的往往正是**新增**的那条 ⇒ 改成遍历部署后的列表，并比对新旧出现次数。

### 二、回滚只还原代码、不还原 crontab ⇒ 设备留在混合状态

第一次部署回滚之后，设备上是：代码是旧的，**cron 条目和封顶脚本却是新的**。
面板一启动就装、旧代码一启动就不装 —— 这种混合状态最坏：谁都说不清当前在跑哪套逻辑。

回滚脚本现在会还原 crontab（备份里本来就有 `crontab.txt`）：

```sh
if [ -s "$BK/crontab.txt" ]; then
    crontab "$BK/crontab.txt" 2>/dev/null || echo '   crontab 还原失败，请手动核对'
else
    echo '   备份里的 crontab 是空的，跳过还原（空文件会让 crontab - 清空整张表）'
fi
```

⚠ 那个 `-s` 判断不能省：`crontab <空文件>` 等于**清空整张表**，
而备份时 `crontab -l` 失败就会留下空文件。

### 三、设备的 /overlay 100% 满 ⇒ 备份阶段直接炸

第二次部署在**备份阶段**就死了：

```
cp: can't create '.../etc-nftables/backup/dhcp...': No space left on device
cp: write error: No space left on device
❌ 回滚脚本生成失败
```

设备的 `/overlay` 总共才 86.4M，而**每份部署备份 3.6MB**（backend+frontend 的代码），
当时堆了 7 份 ⇒ 25MB ⇒ 磁盘 100% 满。

现在备份前先做空间预检，不够就**提前说人话**：

```
❌ 设备可用空间不足 10MB（实际 5MB）—— 先清磁盘再部署（/overlay 总共才 86MB）
```

不预检的话，等 cp 报 "No space left on device" 时现场已经被写坏了一半
（备份残缺、回滚脚本也生成不出来），而报错还指向 cp，根本看不出真因是「磁盘满了」。

### 四、失败路径下备份目录只增不减 ⇒ 越失败越没空间

备份轮转原本**只在部署成功后**跑。部署失败 ⇒ 轮转没跑 ⇒ 这次失败的备份目录
**又留在设备上** ⇒ 设备更满 ⇒ 下一次部署连备份都做不完 —— 这是一个会自我加深的死循环。

现在备份**之前**先轮转（保留 `KEEP-1` 份，给新备份腾位置）：

```sh
prune_backups_keep "$((KEEP_BACKUPS - 1))"
```

轮转逻辑抽成 `prune_backups_keep()`，部署前后共用。

## 限制与已知边界

1. **审计日志没封顶**。`/var/log/nftables-web-auth.log`（每次登录尝试写一行）
   同样落在 tmpfs、同样只增不减。这批只做了访问日志（用户拍板的范围），
   但审计日志迟早也要封 —— 下一批补。
2. **nginx 的 error_log 也没封顶**。它是 `warn` 级别，长得慢，但同样没有上限。
3. **截断有一个很小的丢失窗口**：拷贝尾部到截断原文件之间新写入的行会丢
   （logrotate 的 copytruncate 有同样的竞态）。窗口是毫秒级，
   丢的也就是那几毫秒内的访问记录。
4. **面板上看不到日志大小**。这批没做 UI：封顶是后台维护动作，
   加一个「当前大小 / 上限」的显示属于下一批的锦上添花。
5. **只封一个文件**。脚本是单文件逻辑（一个 LOG 变量），要封第二个得改结构。
